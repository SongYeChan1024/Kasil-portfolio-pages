<b>Photon 네트워킹 고급 문제 해결 및 킬 카운터 UI 구현</b> 2026-05-22


## 요약


### 오늘 수업 핵심 요약

- <b>Photon 멀티플레이어 게임에서 발생하는 4가지 핵심 문제</b>와 실무적 해결 방법을 학습했습니다.
- <b>Custom Properties(룸 프로퍼티)</b>를 활용한 상태 기반 동기화가 Buffered RPC보다 소규모 팀에 적합한 이유를 이해했습니다.
- <b>Master Client Authority 모델</b>을 통해 아이템 획득 시 경쟁 조건(Race Condition)을 방지하는 방법을 배웠습니다.
- 모바일 환경의 일시적 단선을 처리하기 위한 <b>PlayerTTL과 EmptyRoomTTL 설정</b>을 학습했습니다.
- 실시간 <b>킬 카운터 UI 시스템</b>을 Custom Properties를 활용하여 직접 구현했습니다.

### 주요 개념 정리

- <b>RPC (Remote Procedure Call)</b>
  - 설명: 원격 함수 호출 이벤트로, 호출하는 순간 방에 있는 유저들에게만 데이터가 전달되고 사라집니다.
  - 사용되는 상황: 일회성 이벤트나 즉시 실행이 필요한 동작
  - 헷갈릴 수 있는 점: 레이트 조이너(Late-joiner)는 이전에 발생한 RPC 이벤트를 받을 수 없습니다.
- <b>Buffered RPC</b>
  - 설명: 서버가 이벤트를 기억해두었다가 신규 유저에게 재생(Playback)해주는 방식입니다.
  - 헷갈릴 수 있는 점: 게임이 길어질수록 서버에 RPC가 쌓여 과부하(RPC Flooding)가 발생하거나 실행 순서가 꼬일 수 있습니다.
- <b>Custom Properties (룸 프로퍼티)</b>
  - 설명: 이벤트가 아닌 상태(State)를 저장하는 방식으로, \{"Door\_01": "Open", "Chest\_02": "Destroyed"\} 같은 형태로 방의 현재 상태를 딕셔너리로 서버가 관리합니다.
  - 예시: 문이 열렸는지, 상자가 파괴되었는지 등의 상태 플래그를 저장
  - 사용되는 상황: 레이트 조이너에게 현재 게임 상태를 동기화할 때
  - 헷갈릴 수 있는 점: AI 친화적이며 상태 기반 코드 작성이 용이합니다.
- <b>Race Condition (경쟁 조건)</b>
  - 설명: 두 유저가 동시에 같은 아이템을 획득하려고 시도하여 아이템이 복사되거나 에러가 발생하는 상황입니다.
  - 사용되는 상황: 여러 클라이언트가 동시에 같은 리소스에 접근할 때
  - 헷갈릴 수 있는 점: 쓰레드 프로그래밍에서도 유사한 개념이 나타납니다.
- <b>Master Client Authority 모델</b>
  - 설명: 마스터 클라이언트가 서버 역할을 대행하여 단일 검증(Source of Truth)을 수행하는 방식입니다.
  - 예시: 아이템 획득 요청을 마스터 클라이언트가 순차적으로 처리하여 중복 획득 방지
  - 사용되는 상황: 경쟁 조건을 안전하게 방지해야 할 때
- <b>PlayerTTL (Player Time To Live)</b>
  - 설명: 유저가 단선되었을 때 방에서 즉시 내쫓지 않고 'Inactive(비활성화)' 상태로 서버가 캐릭터를 남겨두는 시간입니다.
  - 예시: 20,000 \~ 30,000 ms (20\~30초) 설정
  - 사용되는 상황: 지하철 등 모바일 환경에서 일시적 단선이 자주 발생할 때
- <b>EmptyRoomTTL</b>
  - 설명: 방에 있던 마지막 유저가 튕겼을 때 방이 공중분해되는 것을 막아주는 시간입니다.
  - 예시: 5,000 \~ 10,000 ms (5\~10초) 설정
- <b>Interpolation (보간)</b>
  - 설명: 데이터를 수신했을 때 즉시 반영하지 않고, 현재 위치에서 네트워크 위치까지 매 프레임 조금씩 부드럽게 이동시키는 기법입니다.
  - 예시: Vector3.Lerp, Vector3.MoveTowards 사용
  - 사용되는 상황: 캐릭터 위치 동기화 시 지터링(Jittering) 현상 방지
- <b>Extrapolation (예측)</b>
  - 설명: 패킷 지연 시 마지막으로 확인된 위치와 속도를 기반으로 캐릭터가 계속 부드럽게 움직이도록 예측 연산을 수행하는 기법입니다.
  - 예시: "마지막 위치 + (마지막 속도 \* 지연 시간)" 계산
  - 사용되는 상황: Wi-Fi 불안정으로 패킷이 제때 오지 않을 때
- <b>ExitGames.Client.Photon 네임스페이스</b>
  - 설명: 포톤의 가장 밑바닥(Low-Level) 핵심 엔진인 'Photon Realtime Core'의 기능들을 쓰기 위한 네임스페이스입니다.
  - 사용되는 상황: ① 포톤 전용 Hashtable 사용 시 ② 로우 레벨 이벤트 처리(RaiseEvent) 시

| 개념 | 방 |  |
| --- | --- | --- |
| Buffered RPC | 이벤트 기록 후 재생 | 간단한 구현 |
| Custom Properties | 상태(State) 저장 | AI 친화적, 유지 |

### 수업 흐름별 정리

### 1. 레이트 조인 및 상태 동기화 문제

- 설명: 게임 진행 중 뒤늦게 입장한 유저(Late-joiner)가 기존 유저들이 열어둔 문이나 파괴한 상자를 다시 닫혀있거나 멀쩡한 상태로 보는 문제입니다.
- 원인: 일반 RPC는 호출 순간 방에 있는 유저들에게만 전달되고 사라지기 때문입니다.
- 해결 방법: Custom Properties 방식을 강력히 권장합니다.
- 중요: Custom Properties는 상태 기반이므로 신규 유저가 들어오면 Photon이 자동으로 최신 상태를 동기화해줍니다.

### 2. 소유권(Ownership) 이전과 경쟁 조건

- 설명: 클라이언트 A와 B가 동시에 아이템을 줍기 위해 상호작용을 시도할 때 아이템이 복사되거나 서버 에러가 발생하는 문제입니다.
- 해결 방법: Master Client Authority 모델 사용
- 중요: 클라이언트가 직접 획득 처리하지 않고 마스터 클라이언트에게 RPC 요청 후 중복 검증을 거쳐야 합니다.

### 3. 모바일/무선 환경의 일시적 단선 처리

- 설명: 지하철 등 모바일 환경에서 일시적으로 연결이 끊어졌을 때 게임을 이어서 할 수 있도록 처리하는 방법입니다.
- 해결 방법: RoomOptions에서 PlayerTTL과 EmptyRoomTTL 값을 설정하고, PhotonNetwork.ReconnectAndRejoin() 사용
- 중요: 기본값은 0이라서 끊기자마자 터지므로 반드시 설정해야 합니다.

### 4. 캐릭터 위치 동기화 최적화 및 보간

- 설명: 패킷은 1초에 15\~20번(Serialization Rate)만 오는데 게임 화면은 60\~120 FPS로 그려지므로, 즉시 대입하면 지터링 현상이 발생합니다.
- 해결 방법: OnPhotonSerializeView로 받은 데이터를 저장해두고 Update 문에서 Lerp로 부드럽게 보간합니다.
- 중요: 위치(Position)뿐만 아니라 속도(Velocity)도 함께 보내 예측(Extrapolation)을 수행합니다.

### 5. ExitGames.Client.Photon 네임스페이스 설명

- 설명: 포톤 전용 Hashtable과 로우 레벨 이벤트 처리 기능을 사용하기 위한 네임스페이스입니다.
- 중요: Custom Properties에서 Key-Value 쌍 저장 시 필수적으로 사용됩니다.

### 6. 킬 카운터 UI 실습

- 설명: Custom Properties를 활용하여 각 플레이어의 킬 수를 실시간으로 표시하는 UI 시스템을 구현했습니다.
- 중요: 네트워크 유저끼리 킬한 것은 강사가 구현하고, 탱크가 아파치를 격추시킨 킬은 학생들이 직접 구현하는 과제입니다.

### 실습 / 작업 순서

#### 레이트 조이너 문제 해결 - Custom Properties 사용 순서

1. 상태 데이터를 딕셔너리 형태로 정의 (예: \{"Door\_01": "Open", "Chest\_02": "Destroyed"\})
2. 상태 변경 시 룸 프로퍼티 업데이트
3. OnRoomPropertiesUpdate 콜백에서 상태를 검사하여 오브젝트 외형 변경
4. 신규 유저 입장 시 Photon이 자동으로 최신 상태 동기화

#### 경쟁 조건 방지 - Master Client Authority 워크플로우

1. <b>상호작용 발생 (클라이언트 단)</b>: 클라이언트 A, B가 동시에 아이템 루팅 시도. 로컬 인벤토리에 즉시 넣으면 안 됩니다.
2. <b>마스터 클라이언트로 권한 요청 (RPC)</b>: 두 클라이언트가 마스터 클라이언트에게 "내가 이 아이템 ID를 줍고 싶어"라고 RPC 요청 전송
   - 예시: <code>photonView.RPC("RequestPickUp", RpcTarget.MasterClient, photonView.ViewID);</code>
3. <b>마스터의 단일 검증 (Source of Truth)</b>: 마스터 클라이언트가 RPC를 도착한 순서대로 처리하며 isPickedUp 플래그 확인
   - 먼저 도달한 클라이언트 A 요청: 플래그 false → 승인
   - 뒤에 도달한 클라이언트 B 요청: 플래그 이미 true → 무시/거절
4. <b>오브젝트 파괴 및 보상 지급</b>: 승인된 클라이언트에게 보상 RPC 전송 또는 룸 프로퍼티 갱신 후, 마스터 클라이언트가 PhotonNetwork.Destroy() 호출

#### 일시적 단선 처리 설정

1. <b>RoomOptions 설정</b>:
   - PlayerTTL: 20,000 \~ 30,000 ms 설정
   - EmptyRoomTTL: 5,000 \~ 10,000 ms 설정
2. <b>단선 감지 콜백 구현</b>:
   ```cs
   public override void OnDisconnected(DisconnectCause cause)
   {
       if (cause == DisconnectCause.ClientTimeout || 
           cause == DisconnectCause.ServerTimeout || 
           cause == DisconnectCause.DisconnectByServerLogic)
       {
           PhotonNetwork.ReconnectAndRejoin();
       }
   }
   ```
3. <b>재진입 성공 콜백</b>:
   ```cs
   public override void OnJoinedRoom()
   {
       Debug.Log("부드럽게 재접속 성공!");
   }
   ```
4. <b>재진입 실패 콜백</b>: TTL 만료 시 메인 메뉴로 이동

#### 킬 카운터 UI 구현 순서

1. Canvas 내에 Panel KillInfo 생성 (Top Left 위치, 크기 210x100)
2. Panel 내에 TextMeshPro 4개 생성 (최대 접속 인원 4명)
3. KillInfoUI.cs 스크립트 생성 및 Panel에 연결
4. 스크립트에 TextMeshPro 배열 선언 및 Inspector에서 연결
5. RefreshUI() 함수 작성: 플레이어 리스트 정렬 및 킬 수 표시
6. OnPlayerPropertiesUpdate() 콜백에서 RefreshUI() 호출
7. OnPlayerEnteredRoom(), OnPlayerLeftRoom() 콜백에서도 RefreshUI() 호출
8. TankDamage.cs에서 NotifyKillRPC() 함수 추가 및 킬 수 증가 처리

### 예시와 활용 사례

- <b>예시 1: Custom Properties를 활용한 문 상태 동기화</b>
  - 상황: 멀티플레이어 게임에서 한 유저가 문을 열었을 때
  - 설명: <code>{"Door_01": "Open"}</code> 형태로 룸 프로퍼티 저장
  - 왜 이 예시를 사용했는지: 레이트 조이너도 문이 열린 상태를 확인할 수 있어야 함
- <b>예시 2: Master Client Authority로 아이템 획득 처리</b>
  - 상황: 필드에 드랍된 아이템을 여러 유저가 동시에 줍기 시도
  - 설명: 클라이언트 → 마스터에 RPC 요청 → 마스터가 중복 검증 → 승인된 클라이언트만 획득
  - 왜 이 예시를 사용했는지: 경쟁 조건 방지를 위한 표준 패턴
- <b>예시 3: 지하철에서 일시적 단선 처리</b>
  - 상황: 서울 남양역에서 연결이 끊어짐
  - 설명: PlayerTTL 20\~30초 설정으로 재접속 시 캐릭터와 인벤토리 상태 유지
  - 왜 이 예시를 사용했는지: 모바일 게임에서 흔히 발생하는 실제 사용 사례
- <b>예시 4: 보간(Interpolation)을 통한 부드러운 이동</b>
  - 상황: 다른 유저의 탱크 위치가 네트워크로 수신됨
  - 설명: <code>transform.position = Vector3.Lerp(transform.position, latestNetworkPos, Time.deltaTime * 10f);</code>
  - 왜 이 예시를 사용했는지: 지터링 없이 부드러운 움직임 구현

### 헷갈릴 수 있는 부분

- <b>헷갈리는 개념</b>: Buffered RPC vs Custom Properties
- <b>헷갈리는 이유</b>: 둘 다 레이트 조이너 문제를 해결할 수 있지만, 방식이 다름
- <b>구분 방법</b>: Buffered RPC는 이벤트 재생 방식이고, Custom Properties는 상태 저장 방식입니다. 소규모 팀에서는 Custom Properties가 더 안전하고 유지보수가 쉽습니다.

- <b>헷갈리는 개념</b>: PhotonNetwork.Instantiate vs PhotonNetwork.InstantiateRoomObject
- <b>헷갈리는 이유</b>: 둘 다 네트워크 오브젝트를 생성하지만 소유권이 다름
- <b>구분 방법</b>: Instantiate는 특정 플레이어 소유(탱크), InstantiateRoomObject는 방 소유(아이템, 헬기)입니다.

---

- <b>헷갈리는 개념</b>: Interpolation(보간) vs Extrapolation(예측)
- <b>헷갈리는 이유</b>: 둘 다 부드러운 움직임을 위한 기법
- <b>구분 방법</b>: Interpolation은 현재→목표 위치로 부드럽게 이동, Extrapolation은 속도 정보로 다음 위치를 예측하는 것입니다.

---

- <b>헷갈리는 개념</b>: ActorNumber의 용도
- <b>헷갈리는 이유</b>: 단순한 번호처럼 보이지만 여러 용도로 사용됨
- <b>구분 방법</b>: ActorNumber는 각 플레이어의 고유 번호로 닉네임처럼 사용되며, 정렬이나 식별에 활용됩니다.

### 주요 개념 정리

- <b>ExitGames.Client.Photon 네임스페이스</b>
  - 설명: Photon의 가장 밑바닥(Low-Level) 핵심 엔진인 'Photon Realtime Core'의 기능들을 사용하기 위한 네임스페이스입니다.
  - 예시: <code>using ExitGames.Client.Photon;</code>을 코드 상단에 추가
  - 사용되는 상황: Photon 전용 Hashtable을 사용하여 Custom Properties를 설정할 때 필수적으로 필요합니다.
  - 헷갈릴 수 있는 점: 이 네임스페이스 없이 <code>Hashtable</code>만 사용하면 Unity가 <code>System.Collections.Hashtable</code>(C# 구버전 데이터 구조)로 인식하여 타입 불일치 오류가 발생합니다.
- <b>Photon Hashtable vs System.Collections.Hashtable</b>
  - 설명: Photon Custom Properties는 Photon 전용 Hashtable을 사용해야 하며, C# 시스템의 Hashtable과는 호환되지 않습니다.
  - 예시: <code>using ExitGames.Client.Photon;</code> 없이 코드 작성 시 컴파일 에러 발생

  - 헷갈릴 수 있는 점: 두 Hashtable 모두 이름이 같아서 어떤 것이 사용되는지 혼동하기 쉽습니다.

### 1. AI 코드 생성 시 발생하는 문제점

- 설명: ChatGPT, Claude, Gemini 등 AI에게 "Photon Custom Properties 바꾸는 코드 짜줘"라고 요청하면 AI가 십중팔구 <code>using ExitGames.Client.Photon;</code> 네임스페이스를 빼먹고 그냥 <code>Hashtable</code>만 써서 코드를 생성합니다.
- 중요: 이렇게 생성된 코드를 그대로 사용하면 Unity(C#)가 Photon의 Hashtable이 아니라 <code>System.Collections.Hashtable</code>로 인식해 버립니다.

### 2. 컴파일 에러 발생 원인

- 설명: 네임스페이스가 없으면 Unity는 C# 시스템의 구버전 데이터 구조인 <code>System.Collections.Hashtable</code>로 인식하게 됩니다.
- 결과: "타입이 맞지 않아 Photon 프로퍼티에 넣을 수 없다"는 컴파일 에러가 발생합니다.
- 중요: 초보자들이 이 문제로 많이 헤매는 대표적인 사례입니다.

### 3. 올바른 해결 방법

- 설명: 코드 파일 상단에 반드시 <code>using ExitGames.Client.Photon;</code> 네임스페이스를 추가해야 합니다.
