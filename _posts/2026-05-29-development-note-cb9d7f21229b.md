<b>Firebase와 Unity 연동 수업</b> 2026-05-29

## 요약

### 오늘 수업 핵심 요약

- <b>Firebase</b>와 <b>Unity</b>를 연동하는 방법과 Firebase의 요금제 체계(Spark vs Blaze)를 배웠습니다.
- Unity에서 <b>HP 시스템</b>, <b>스코어 매니저</b>, <b>애니메이션 시스템</b>을 구현하여 게임의 핵심 UI와 상태 관리 로직을 완성했습니다.
- Firebase는 구글 계정만 있으면 무료로 사용 가능하며, Spark 요금제는 소규모 프로젝트와 학습용으로 충분하지만, 실제 출시 시에는 Blaze 요금제로 업그레이드가 필요합니다.
- 실시간 멀티플레이 게임 개발 시 Firebase에 매 프레임 데이터를 저장하면 요금 폭탄을 맞을 수 있으므로, <b>Photon</b> 같은 전용 네트워크 엔진을 사용하고 Firebase에는 최종 결과만 저장해야 합니다.
- 게임이 종료되면 HP 게이지가 0 이하로 떨어질 때 블랙 패널과 게임 오버 패널이 표시되고, 아이템과 장애물 생성이 중단되도록 구현했습니다.

---

### 주요 개념 정리

- <b>Firebase</b>
  - 설명: Google에서 제공하는 백엔드 서비스 플랫폼으로, 데이터베이스, 인증, 스토리지, 호스팅 등 다양한 기능을 제공합니다.
  - 예시: 게임의 유저 로그인, 랭킹 시스템, 세이브 데이터 저장 등에 활용
  - 사용되는 상황: Unity 게임에서 서버 기능이 필요할 때, 별도의 서버 구축 없이 Firebase를 사용
  - 헷갈릴 수 있는 점: 기본적으로 무료지만 사용량에 따라 과금될 수 있으므로 요금제 이해 필수
- <b>Spark 요금제 vs Blaze 요금제</b>
  - 설명: Firebase의 두 가지 주요 요금제. Spark는 완전 무료이지만 기능과 용량 제한이 있고, Blaze는 종량제로 모든 기능 사용 가능
  - 예시: 수업 과제나 프로토타입은 Spark, 실제 출시 게임은 Blaze 권장
  - 사용되는 상황: Spark는 동시 연결 100개, 저장 1GB까지 무료. Blaze는 무료 한도 포함 + 초과 시 과금
  - 헷갈릴 수 있는 점: Blaze 요금제로 전환해도 Spark 수준의 무료 한도가 포함되어 있어 즉시 과금되지 않음
- <b>싱글턴 패턴 (Singleton)</b>
  - 설명: 게임 내에서 특정 객체의 인스턴스가 하나만 존재하도록 보장하는 디자인 패턴
  - 예시: HP 시스템, 스코어 매니저 등 게임 전체에서 하나만 필요한 관리 객체
  - 사용되는 상황: <code>public static</code> 인스턴스를 선언하고 <code>Awake()</code>에서 초기화
  - 헷갈릴 수 있는 점: <code>DontDestroyOnLoad()</code>를 사용하면 씬 전환 시에도 파괴되지 않음
- <b>Coroutine (코루틴)</b>
  - 설명: Unity에서 시간 지연이나 프레임 단위 처리를 위해 사용하는 함수. <code>IEnumerator</code> 타입 반환
  - 예시: <code>yield return new WaitForSeconds(0.15f)</code>로 0.15초 대기 후 다음 동작 실행
  - 사용되는 상황: 애니메이션 전환, 히트 이펙트 표시 등 일정 시간 후 상태 변경이 필요할 때
  - 헷갈릴 수 있는 점: FixedUpdate 내에서 즉시 실행하면 프레임이 빠르게 지나가 시각적 효과를 알아채기 어려움

### 수업 흐름별 정리

### 1. HP 시스템 및 스코어 매니저 구현

- 설명: 빈 오브젝트로 HP 시스템과 스코어 매니저를 생성하고 각각 스크립트 컴포넌트 추가
- 중요: HP 시스템은 <code>using UnityEngine.UI</code> 필수. HP 게이지(Image), 블랙 패널, 게임 오버 패널을 public 변수로 연결
- 싱글턴 패턴으로 구현하여 어디서든 <code>HPSystem.instance</code>로 접근 가능

### 2. HP 게이지 UI 구성

- 설명: HP 게이지는 Image의 <code>fillAmount</code> 속성을 사용하여 0\~1 사이 값으로 체력 표시
- HP가 0.05 이하로 떨어지면 블랙 패널과 게임 오버 패널 활성화
- <code>DecreaseHP()</code>와 <code>IncreaseHP()</code> 함수로 체력 감소/증가 구현

### 3. 게임 오버 UI 제작

- 설명: Canvas 하위에 블랙 패널(검은 반투명 배경)과 게임 오버 패널(갈색 배경 + 텍스트 + 메인 버튼) 생성
- 게임 시작 전에는 두 패널 모두 비활성화 상태로 설정
- 게임 화면에서 확인 후 씬 화면으로 돌아와 위치와 크기 조정

### 4. 스코어 시스템 구현

- 설명: 스코어 매니저도 싱글턴 패턴 적용. UI Text 컴포넌트로 점수 표시
- <code>Update()</code>에서 <code>Time.deltaTime</code>을 누적하여 1초마다 점수 1씩 증가
- 중요: <code>1f / 60f</code>은 약 0.0166초로, 60프레임 기준 1초를 의미
- 게임 오버 시 점수 증가 중단되도록 <code>if</code> 조건문으로 <code>liveStat</code> 체크 후 <code>return</code>

### 5. 플레이어 충돌 처리

- 설명: <code>OnTriggerEnter2D</code>에서 충돌 태그 확인. "Snow"면 HP 감소, "Heal"이면 HP 증가
- 태그가 정확히 설정되어 있는지 확인 필요

### 6. 애니메이션 시스템 구축

- 설명: Player에서 기존 Animator 컴포넌트 제거 후, Animation 윈도우에서 새로 생성
- <code>Unit1_Idle</code> (평소 상태)과 <code>Unit1_Hit</code> (피격 상태) 두 개의 Animation Clip 생성
- BG\_Idle 스프라이트와 BG\_Hit 스프라이트를 각각 타임라인에 드래그하여 애니메이션 구성

### 7. Blend Tree 및 파라미터 설정

- 설명: Animator 윈도우에서 Blend Tree 생성. 기본 "Blend" 파라미터 이름을 "SnowHit"으로 변경
- Add Motion Field에서 Unit1\_Idle과 Unit1\_Hit 애니메이션 클립 연결
- <code>SnowHit</code> 값이 0이면 Idle, 1이면 Hit 애니메이션 재생

### 8. 플레이어 애니메이션 제어

- 설명: PlayerController 스크립트에 <code>Animator</code> 컴포넌트 추가. <code>GetComponent&lt;Animator&gt;()</code>로 참조
- <code>isHit</code> 상태에 따라 <code>animator.SetFloat("SnowHit", 0 또는 1)</code> 호출
- 중요: FixedUpdate에서 즉시 전환하면 너무 빨라 시각적으로 확인 불가. 코루틴으로 0.15초 대기 후 원래 상태로 복귀

### 9. 게임 오버 시 오브젝트 생성 중단

- 설명: Prefab System과 Score Manager에서 게임 오버 시 눈과 아이템 생성 중단 처리
- Prefab System: <code>liveStat</code>이 true일 때만 Spawn 실행
- Score Manager: <code>liveStat</code>이 false면 <code>return</code>으로 점수 업데이트 중단

### 10. Firebase 요금제 이해

- 설명: Firebase는 구글 계정만 있으면 사용 가능. Spark(무료)와 Blaze(종량제) 두 가지 요금제 존재
- 중요: Blaze 요금제도 Spark 수준의 무료 한도 포함. 초과분만 과금
- 요금 폭탄 방지 방법: ① 예산 알림 설정, ② 실시간 멀티플레이 데이터는 Photon 사용, ③ Firebase에는 최종 결과만 저장

### 실습 / 작업 순서

#### HP 시스템 생성 및 설정

1. Hierarchy에서 빈 오브젝트 생성 → 이름: "HPSystem"
2. HPSystem 스크립트 생성 후 오브젝트에 추가
3. HPSystem 스크립트 열기 → <code>using UnityEngine.UI</code> 추가
4. <code>public Image hpGauge</code>, <code>public GameObject blackPanel</code>, <code>public GameObject gameOverPanel</code> 변수 선언
5. 싱글턴 패턴 구현: <code>public static HPSystem instance</code> 선언, <code>Awake()</code>에서 <code>instance = this</code> 설정
6. Inspector에서 각 UI 요소 드래그하여 연결

#### 블랙 패널 및 게임 오버 패널 제작

1. Canvas 하위에 빈 오브젝트 생성 → 이름: "BlackPanel"
2. BlackPanel에 Image 컴포넌트 추가 → 색상: 검은색, 투명도 조절
3. Rect Transform에서 전체 화면 덮도록 크기 조정
4. Canvas 하위에 Image 생성 → 이름: "GameOverPanel", 크기: 500x500, 색상: 갈색 계열
5. GameOverPanel 하위에 Legacy Text 생성 → "GameOver" 텍스트 입력, 크기 30, 가운데 정렬, 색상: Gold
6. GameOverPanel 하위에 Button 생성 → 이름: "Main2Btn"
7. Button 하위 Text에 "메인으로" 입력, 크기 25, Bold, 가운데 정렬
8. 게임 시작 전 BlankPanel과 GameOverPanel 비활성화

#### HP 감소/증가 함수 구현

1. HPSystem 스크립트에서 <code>public void DecreaseHP()</code> 함수 생성 → <code>hpGauge.fillAmount -= 0.25f</code>
2. <code>public void IncreaseHP()</code> 함수 생성 → <code>hpGauge.fillAmount += 0.1f</code>
3. <code>Update()</code>에서 <code>if (hpGauge.fillAmount &lt; 0.05f)</code> 조건 추가 → 블랙 패널과 게임 오버 패널 활성화

#### 스코어 매니저 설정

1. Hierarchy에서 빈 오브젝트 생성 → 이름: "ScoreManager"
2. ScoreManager 스크립트 생성 및 추가
3. <code>using UnityEngine.UI</code> 추가, <code>public Text scoreText</code> 변수 선언
4. Canvas 하위에 Text 생성 → Inspector에서 ScoreManager의 scoreText에 연결
5. <code>Update()</code>에서 시간에 따라 점수 증가 로직 작성 → <code>score += Time.deltaTime</code>, <code>scoreText.text = "Score: " + (int)score</code>

#### 플레이어 애니메이션 설정

1. Player 선택 → 기존 Animator 컴포넌트 제거 (Remove Component)
2. Window → Animation 열기 → Player 선택 상태에서 Create 클릭
3. Animation 폴더 생성 → "Unit1\_Idle" 이름으로 저장
4. Assets → Sprites → Bolt2DPlatformWorld → BG\_Idle 스프라이트 찾아 타임라인에 드래그
5. Create New Clip 클릭 → "Unit1\_Hit" 이름으로 저장
6. BG\_Hit 스프라이트를 타임라인에 드래그
7. Window → Animator 열기 → 우클릭 → Create State → From New Blend Tree
8. Blend Tree 더블클릭 → Add Motion Field에서 Unit1\_Idle, Unit1\_Hit 추가
9. Parameters 탭 → "Blend" 파라미터 이름을 "SnowHit"으로 변경
10. Ctrl+S로 저장

#### 플레이어 스크립트에 애니메이션 제어 추가

1. PlayerController 스크립트 열기 → <code>Animator animator</code> 변수 선언, <code>GetComponent&lt;Animator&gt;()</code> 호출
2. <code>Update()</code> 또는 <code>FixedUpdate()</code>에서 <code>isHit</code> 상태 확인 후 <code>animator.SetFloat("SnowHit", isHit ? 1f : 0f)</code> 호출
3. 코루틴 함수 <code>IEnumerator HitCoroutine()</code> 생성 → <code>yield return new WaitForSeconds(0.15f)</code> 후 <code>isHit = false</code>
4. 충돌 시 <code>StartCoroutine(HitCoroutine())</code> 호출
5. 빌드 후 테스트

#### Firebase 프로젝트 준비 (점심 후 실습 예정)

1. 웹 브라우저에서 "firebase" 검색 → Firebase 콘솔 접속
2. 우측 상단에서 언어를 "한국어"로 변경
3. "콘솔로 이동" 클릭
4. 새 프로젝트 생성 예정 (수업 재개 후 진행)

### 예시와 활용 사례

- <b>예시 1: HP 게이지 fillAmount 활용</b>
  - 상황: 플레이어가 눈에 맞았을 때 체력 감소 표시
  - 설명: <code>hpGauge.fillAmount -= 0.25f</code>로 Image의 fillAmount를 줄여 시각적으로 HP 감소 표현
  - 왜 이 예시를 사용했는지: fillAmount는 0\~1 사이 값으로 UI Image의 채워진 정도를 쉽게 조절 가능
- <b>예시 2: 시간에 따른 점수 증가</b>
  - 상황: 게임 진행 중 매 초마다 점수 1씩 증가
  - 설명: <code>score += Time.deltaTime</code>으로 누적 후 <code>(int)score</code>로 정수 변환하여 표시
  - 왜 이 예시를 사용했는지: 프레임 독립적으로 정확히 1초당 1점씩 증가. 60fps든 30fps든 동일한 속도 보장
- <b>예시 3: 코루틴을 활용한 히트 이펙트</b>
  - 상황: 플레이어 피격 시 잠깐 빨간색 스프라이트 표시 후 원래 상태로 복귀
  - 설명: <code>StartCoroutine(HitCoroutine())</code>으로 0.15초간 Hit 애니메이션 재생 후 Idle로 복귀
  - 왜 이 예시를 사용했는지: FixedUpdate에서 즉시 전환하면 시각적으로 확인 불가. 코루틴으로 시간 지연 구현
- <b>예시 4: Firebase 요금제 선택</b>
  - 상황: Unity 수업 과제로 로그인 시스템과 간단한 DB 테스트 필요
  - 설명: Spark 요금제 사용. 동시 연결 100개, 저장 1GB까지 무료
  - 왜 이 예시를 사용했는지: 소규모 학습용 프로젝트는 Spark로 충분. 비용 걱정 없이 연습 가능
- <b>예시 5: Photon + Firebase 조합</b>
  - 상황: 실시간 탱크 대전 게임 개발
  - 설명: 탱크 위치, 체력 등 실시간 데이터는 Photon으로 처리. 전투 종료 후 최종 승패, 킬수, 코인만 Firebase에 저장
  - 왜 이 예시를 사용했는지: Firebase에 매 프레임 데이터를 저장하면 요금 폭탄. Photon은 실시간 동기화 전용, Firebase는 결과 저장용으로 역할 분담

### 헷갈릴 수 있는 부분

- <b>헷갈리는 개념: Spark 요금제와 Blaze 요금제</b>
  - 헷갈리는 이유: Spark는 무료, Blaze는 유료라고 생각하기 쉬움
  - 구분 방법: Blaze 요금제도 Spark 수준의 무료 한도가 포함되어 있음. 무료 한도 초과분만 과금. 즉, Blaze로 전환해도 즉시 요금이 발생하는 것은 아님
- <b>헷갈리는 개념: fillAmount vs transform.localScale</b>
  - 헷갈리는 이유: 둘 다 크기를 조절하는 것처럼 보임
  - 구분 방법: <code>fillAmount</code>는 UI Image의 채워진 정도(0\~1), <code>localScale</code>은 오브젝트 자체의 크기. HP 게이지는 fillAmount 사용
- <b>헷갈리는 개념: Update()에서 즉시 애니메이션 전환 vs 코루틴 사용</b>
  - 헷갈리는 이유: 둘 다 애니메이션 전환이지만 시각적 결과가 다름
  - 구분 방법: FixedUpdate나 Update에서 즉시 전환하면 프레임이 빠르게 지나가 사용자가 인지 불가. 코루틴으로 일정 시간 유지해야 시각적 효과 확인 가능
- <b>헷갈리는 개념: Firebase에 모든 게임 데이터 저장</b>
  - 헷갈리는 이유: Firebase가 만능 서버처럼 보여서 모든 데이터를 저장하려 함
  - 구분 방법: 실시간 멀티플레이 동기화는 Photon 사용. Firebase는 최종 결과, 유저 정보, 세이브 데이터 저장 용도. 역할 분담 필수

## Firebase Spark vs Blaze 비교

| 구분 | Spark 요금제 | Blaze 요금제 |
| --- | --- | --- |
| 기본 성격 | 무료 요금제 | 사용량 기반 종량제 |
| 결제 수단 | 필요 없음 | Cloud Billing 계정 필요 |
| 과금 방식 | 무료 한도까지만 사용 | 무료 한도 초과분 과금 |
| 무료 사용량 | 있음 | Spark의 무료 사용량 포함 |
| 확장성 | 테스트, 학습, 소규모 프로젝트용 | 실제 출시, 유저 증가 대응용 |
| 사용 가능한 서비스 범위 | 일부 서비스 제한 | 더 많은 서비스와 높은 사용량 사용 가능 |
| 비용 위험 | 거의 없음 | 사용량이 많으면 요금 발생 |
| 예산 알림 | 보통 불필요 | 반드시 설정 추천 |
| 추천 상황 | 개발 연습, 프로토타입, 수업 과제 | 실제 서비스, 출시 게임, 유저가 늘어날 프로젝트 |

| <b>Cloud Storage</b> | 현재 Spark에서는 접근 불가. Cloud Storage for Firebase는 Blaze 필요 | 무료 구간은 있으나 초과 시 과금. 기존 <code>*.appspot.com</code> 버킷은 5GB 저장, 1GB/일 다운로드 등 무료 구간 유지 가능 |
| <b>Hosting</b> | 저장 10GB, 데이터 전송 360MB/일 | 저장 10GB 무료 후 \$0.026/GB, 데이터 전송 360MB/일 무료 후 \$0.15/GB |
| <b>FCM, Analytics, Crashlytics, Remote Config 등</b> | 무료 | 무료 제품으로 제공되는 항목은 Blaze에서도 무료로 사용 가능 |

<b>Firebase 데이터베이스 URL 설정 및 Unity 연동 실습</b> 2026-05-29

## 요약

### 오늘 수업 핵심 요약

- <b>Firebase 프로젝트</b>와 <b>Unity</b>를 연동하기 위한 데이터베이스 URL 설정 방법을 배웠습니다.
- Unity의 <b>Project Settings</b>에서 패키지 이름을 설정하고, Firebase에서 <b>Android 앱 등록</b>을 진행했습니다.
- <b>google-services.json</b> 파일을 다운로드하여 Unity 프로젝트의 Assets 폴더에 추가하고, <b>Firebase Unity SDK</b>를 임포트했습니다.
- Firebase Console에서 <b>Realtime Database</b>를 생성하고, 데이터베이스 URL을 복사하여 Unity 스크립트에서 사용할 수 있도록 준비했습니다.
- 데이터베이스 <b>보안 규칙</b>을 테스트 모드로 설정하여 읽기와 쓰기가 모두 가능하도록 구성했으며, 실제 배포 시에는 보안 규칙을 강화해야 한다는 점을 확인했습니다.

---

### 주요 개념 정리

- <b>Firebase Realtime Database</b>
  - 설명: Google의 NoSQL 클라우드 데이터베이스로, 실시간으로 데이터를 동기화할 수 있는 서비스
  - 예시: 게임의 유저 정보, 점수, 코인, 캐릭터 보유 목록 등을 저장
  - 사용되는 상황: Unity 게임에서 서버 없이 실시간 데이터 저장 및 불러오기가 필요할 때
  - 헷갈릴 수 있는 점: 보안 규칙을 설정하지 않으면 누구나 데이터를 읽고 수정할 수 있음
- <b>google-services.json</b>
  - 설명: Firebase와 Unity 간의 데이터 통신을 위한 구성 파일
  - 예시: Firebase 프로젝트 정보와 API 키가 포함된 JSON 파일
  - 사용되는 상황: Firebase SDK가 어떤 프로젝트와 연결되는지 식별하기 위해 필요
  - 헷갈릴 수 있는 점: 반드시 Assets 폴더에 직접 배치해야 하며, 플레이 모드에서 추가하면 프로젝트 저장 시 사라질 수 있음
- <b>Firebase Unity SDK</b>
  - 설명: Unity에서 Firebase 기능을 사용할 수 있도록 하는 패키지
  - 예시: <code>FirebaseDatabase.unitypackage</code> 파일을 임포트하여 Realtime Database 기능 사용
  - 사용되는 상황: Firebase의 다양한 서비스(Database, Auth, Storage 등)를 Unity에서 사용할 때
  - 헷갈릴 수 있는 점: 필요한 SDK만 선택적으로 임포트해야 하며, 모든 SDK를 다 넣으면 빌드 크기가 커짐
- <b>데이터베이스 보안 규칙</b>
  - 설명: Firebase Realtime Database에서 누가 데이터를 읽고 쓸 수 있는지 제어하는 규칙
  - 예시: <code>".read": true, ".write": true</code>는 모든 사람이 읽고 쓸 수 있음
  - 사용되는 상황: 테스트 모드에서는 모두 허용하지만, 실제 출시 시에는 인증된 사용자만 접근하도록 설정
  - 헷갈릴 수 있는 점: 테스트 모드로 배포하면 해킹 위험이 있으므로 반드시 규칙을 수정해야 함

### 수업 흐름별 정리

### 1. Unity Project Settings에서 패키지 이름 설정

- 설명: Firebase에 앱을 등록하기 위해 Unity 프로젝트의 패키지 이름을 설정
- <b>중요:</b> 패키지 이름에 언더바(\_)가 있으면 Firebase 등록 시 문제가 발생할 수 있으므로 제거 필요
- Edit > Project Settings > Player > Android 탭에서 Package Name 수정

### 2. Firebase Console에서 프로젝트 생성

- 설명: Firebase 콘솔에서 새 프로젝트를 생성하고 Unity 앱 추가
- 프로젝트 이름 입력 후 Google Analytics 사용 설정 선택
- Unity 아이콘 선택 후 Android 앱으로 등록

### 3. Android 앱 등록 및 패키지 이름 입력

- 설명: Firebase에서 Android 앱으로 등록하고 Unity의 패키지 이름 복사하여 입력
- Unity Project Settings의 Package Name을 복사하여 Firebase 등록 화면에 붙여넣기
- 앱 닉네임은 선택 사항

### 4. google-services.json 파일 다운로드 및 배치

- 설명: Firebase에서 제공하는 구성 파일을 다운로드하여 Unity Assets 폴더에 배치
- <b>중요:</b> 플레이 모드가 아닌 상태에서 파일을 추가해야 저장됨
- 파일을 Assets 폴더 최상위에 드래그 앤 드롭

### 5. Firebase Unity SDK 다운로드 및 임포트

- 설명: Firebase Unity SDK를 다운로드하고 필요한 패키지만 선택하여 임포트
- 압축 해제 후 <code>FirebaseDatabase.unitypackage</code>만 Unity로 드래그하여 임포트
- Import 완료 후 Console 창에서 오류 확인

### 6. Firebase Realtime Database 생성

- 설명: Firebase Console에서 Realtime Database 생성 및 위치 선택
- 데이터베이스 위치는 미국, 유럽, 싱가포르 중 선택 (강의에서는 미국 선택)
- 테스트 모드로 시작하여 보안 규칙 작성 가능 상태로 설정

### 7. 데이터베이스 URL 복사 및 저장

- 설명: 생성된 데이터베이스의 URL을 복사하여 메모장에 저장
- URL 형식: <code>https://프로젝트이름-default-rtdb.firebaseio.com/</code>
- 이 URL은 Unity 스크립트에서 데이터베이스 연결 시 사용

### 8. 보안 규칙 설정

- 설명: 데이터베이스 규칙 탭에서 읽기와 쓰기 권한을 true로 설정
- <b>중요:</b> 테스트용으로만 사용하고, 실제 배포 시에는 반드시 보안 규칙 수정 필요
- 현재설정은 누구나 데이터를 읽고 수정할 수 있어 해킹 위험 있음

### 실습 / 작업 순서

#### Unity에서 패키지 이름 설정

1. Unity에서 Edit > Project Settings 선택
2. Player 탭 선택 후 Android 플랫폼 선택
3. Package Name 항목에서 언더바(\_) 제거
4. 수정한 Package Name 복사

#### Firebase 프로젝트 생성

1. 웹 브라우저에서 Firebase 검색 후 Console 접속
2. 언어를 한국어로 변경
3. "프로젝트 추가" 또는 "새 프로젝트" 클릭
4. 프로젝트 이름 입력 (예: firebase-project)
5. Google Analytics 사용 설정 선택
6. Analytics 계정 선택 또는 새로 생성
7. "프로젝트 만들기" 클릭

#### Unity 앱 등록

1. Firebase 프로젝트 생성 완료 후 "앱 추가" 클릭
2. Unity 아이콘 선택
3. "Android 앱으로 등록" 체크
4. Unity에서 복사한 Package Name 붙여넣기
5. "앱 등록" 클릭

#### google-services.json 다운로드 및 배치

1. Firebase에서 "google-services.json 다운로드" 클릭
2. 다운로드 폴더에서 파일 확인
3. Unity로 돌아와서 Play 모드가 아닌지 확인
4. Assets 폴더를 선택한 상태에서 google-services.json 파일을 드래그하여 배치
5. Assets 폴더에 파일이 추가되었는지 확인
6. Firebase Console에서 "다음" 클릭

#### Firebase Unity SDK 임포트

1. Firebase Console에서 "Firebase Unity SDK 다운로드" 클릭
2. 다운로드 폴더에서 SDK 압축 파일 찾기
3. 마우스 오른쪽 버튼 > "압축 풀기"
4. 압축 해제된 폴더 내부에서 <code>FirebaseDatabase.unitypackage</code> 찾기
5. Unity로 돌아와서 해당 파일을 Project 창으로 드래그
6. Import Unity Package 창에서 "Import" 클릭
7. Console 창에서 빨간 오류 메시지 확인
8. Play 버튼을 눌러 오류 발생 여부 테스트
9. Firebase Console에서 "다음" 클릭 후 "콘솔로 이동"

#### Realtime Database 생성

1. Firebase Console 좌측 메뉴에서 "Realtime Database" 선택
2. "데이터베이스 만들기" 클릭
3. 데이터베이스 위치 선택 (미국, 벨기에, 싱가포르 중 선택)
4. "테스트 모드에서 시작" 선택
5. "사용 설정" 클릭

#### 데이터베이스 URL 복사 및 보안 규칙 설정

1. 생성된 데이터베이스 URL 주소 복사
2. 메모장 열어서 URL 붙여넣기 및 저장
3. Firebase Console에서 "규칙" 탭 선택
4. 기존 규칙을 모두 삭제하고 다음과 같이 수정:
   ```javascript
   {
     "rules": {
       ".read": true,
       ".write": true
     }
   }
   ```
5. "게시" 버튼 클릭

### 예시와 활용 사례

- <b>예시 1: 데이터베이스 URL 사용</b>
  - 상황: Unity 스크립트에서 Firebase Database에 연결할 때
  - 설명: <code>FirebaseDatabase.GetInstance("URL")</code> 형태로 데이터베이스 URL 전달
  - 왜 이 예시를 사용했는지: Firebase는 프로젝트마다 고유한 URL을 가지므로 정확한 URL이 필요함
- <b>예시 2: 테스트 모드 보안 규칙</b>
  - 상황: 개발 및 테스트 단계에서 빠르게 데이터 읽기/쓰기 테스트
  - 설명: <code>.read</code>와 <code>.write</code>를 모두 <code>true</code>로 설정하여 인증 없이 접근 가능
  - 왜 이 예시를 사용했는지: 개발 초기에는 빠른 테스트가 중요하지만, 배포 전 반드시 보안 강화 필요

### 헷갈릴 수 있는 부분

- <b>헷갈리는 개념: Unity Package Name과 Firebase 앱 등록</b>
  - 헷갈리는 이유: Package Name에 특수문자가 포함되면 등록이 안 됨
  - 구분 방법: Unity의 Package Name은 Firebase 등록 시 그대로 사용되므로, 언더바(\_) 등 특수문자를 미리 제거해야 함
- <b>헷갈리는 개념: SDK 임포트 시 전체 vs 선택적 임포트</b>
  - 헷갈리는 이유: Firebase SDK는 여러 기능이 패키지로 분리되어 있음
  - 구분 방법: 현재 필요한 기능(Database)만 임포트하면 빌드 크기를 줄일 수 있음
- <b>헷갈리는 개념: 테스트 모드 보안 규칙의 위험성</b>
  - 헷갈리는 이유: 테스트 모드는 편리하지만 누구나 데이터 접근 가능
  - 구분 방법: 데이터베이스 URL만 알면 해킹 가능하므로, 실제 배포 시에는 인증 기반 보안 규칙으로 변경 필요

<b>Firebase Realtime Database와 Cloud Firestore를 사용할 수 있습니다.</b>

<b>두 데이터베이스의 구조적 차이점(데이터 저장 방식)을 비교하고,</b>

<b>잦은 상태 업데이트가 필요한 멀티플레이어 환경에서는 둘 중 어떤 것이</b>

<b>더 적합할지 본인의 생각을 서술해 보세요.</b>

Realtime Database는 하나의 큰 JSON 나무나 중첩 딕셔너리처럼 경로를 따라 데이터가 연결된 구조이고, Firestore는 컬렉션 안에 문서들이 나뉘어 있어서 딕셔너리처럼 각 문서를 ID로 구분하는 구조에 가깝다.<br />잦은 상태 업데이트가 필요한 멀티플레이어 환경에서는 Cloud Firestore보다 Firebase Realtime Database가 더 적합하다고 생각한다. Realtime Database는 하나의 JSON 트리 구조에서 데이터가 변경되면 연결된 클라이언트에게 빠르게 반영되기 때문이다,  반면 Cloud Firestore는 유저 정보, 인벤토리, 재화처럼 문서 단위로 정리해서 저장하는 데이터에 더 적합하다.

<b>문제 2</b>

<b>Firebase Realtime Database나 Firestore에서 데이터가 변경되는 것을 감지하기 위해 리스너(Listener)를</b>

<b>부착했습니다. 데이터 변경 이벤트가 발생하여 콜백(Callback) 함수가 호출되었을 때,</b>

<b>이 콜백 내부에서 유니티의 UI(예: 점수 텍스트 업데이트)나 게임 오브젝트(GameObject)를</b>

<b>직접 제어하려고 하면 에러가 발생합니다. 이 에러가 발생하는 원인(스레드 관점)은 무엇이며,</b>

<b>이를 해결하기 위해 유니티 클라이언트에서 어떤 방식을 사용해야 하는지 서술해 보세요.</b>

Firebase Realtime Database나 Firestore의 리스너 콜백은 비동기적으로 실행되며, Unity의 메인 스레드가 아닌 백그라운드 스레드에서 호출될 수 있다. 하지만 Unity의 UI, Transform, GameObject 같은 객체들은 메인 스레드에서만 안전하게 접근할 수 있다. 그래서 Firebase 콜백 내부에서 바로 <code>Text.text</code>를 변경하거나 <code>GameObject.SetActive()</code>를 호출하면 스레드 충돌로 에러가 발생할 수 있다.

이를 해결하기 위해서는 Firebase 콜백 안에서 Unity 오브젝트를 직접 제어하지 말고, <code>ContinueWithOnMainThread()</code>나 <code>UnityMainThreadDispatcher.Enqueue()</code>를 사용해 UI 갱신과 GameObject 제어 코드를 Unity 메인 스레드에서 실행해야 한다. 즉, Firebase 콜백은 데이터만 받아오고, 실제 화면 변경은 메인 스레드로 넘겨 처리하는 방식이 안전하다.

<b>\[문제 3: 유니티 스크립트에서의 DB 참조(Reference) 및 비동기 처리 구성\]</b>

<b>유니티 C# 스크립트에서 Firebase Realtime Database에 연동하여 특정 유저의 데이터를 읽거나 쓰려면, 가장 먼저 데이터가 위치한 주소를 가리키는 참조(Reference)를 구성해야 합니다.</b>

<b>FirebaseDatabase.DefaultInstance.RootReference를 사용하여 특정 유저(예: UID가 “user123”인 유저) 노드 하위의 “gold” 스탯 경로로 접근하는 참조 객체 구성 과정을 설명해 보세요. 또한, 이 참조 경로에 새로운 값을 덮어쓸 때 사용하는 SetValueAsync() 메서드가 왜 ‘비동기(Async)’ 방식으로 설계되어 있으며, 게임 클라이언트(메인 스레드) 관점에서 이것이 왜 필수적인지 서술해 보세요.</b>

<code>FirebaseDatabase.DefaultInstance.RootReference</code>는 Realtime Database의 최상위 경로를 가리키는 참조이다. 특정 유저의 <code>gold</code> 값에 접근하려면 <code>RootReference</code>에서 시작해 <code>Child("users").Child("user123").Child("gold")</code> 순서로 하위 경로를 따라 내려간다. 이렇게 하면 <code>users/user123/gold</code> 위치를 가리키는 <code>DatabaseReference</code> 객체를 만들 수 있다.

이 참조 위치에 값을 저장할 때는 <code>SetValueAsync()</code>를 사용한다. 예를 들어 <code>goldRef.SetValueAsync(1000)</code>을 호출하면 <code>users/user123/gold</code> 위치의 값이 <code>1000</code>으로 덮어써진다. 이 메서드가 비동기 방식인 이유는 Firebase 저장 작업이 Unity 내부에서 바로 끝나는 작업이 아니라, 네트워크를 통해 서버에 요청을 보내고 응답을 기다려야 하는 작업이기 때문이다.

만약 이 과정을 동기 방식으로 처리하면 서버 응답을 기다리는 동안 Unity의 메인 스레드가 멈추게 된다. 그러면 게임 화면이 끊기거나 입력이 지연될 수 있다. 따라서 게임 클라이언트에서는 Firebase 읽기와 쓰기 작업을 비동기로 처리하여 게임 흐름은 계속 유지하고, 저장이 완료된 뒤 콜백에서 결과를 처리해야 한다.

# 1. Realtime Database의 저장 방식

Realtime Database는 데이터를 <b>JSON 트리</b> 형태로 저장해.

공식 문서에서도 Realtime Database의 모든 데이터는 JSON 객체로 저장되며, 클라우드에 호스팅된 JSON 트리처럼 생각할 수 있다고 설명해. SQL처럼 테이블이나 레코드가 있는 게 아니라, JSON 구조 안에 노드가 계속 붙는 방식이야.

예를 들면 이렇게 생겼어.

```txt
{
  "UserInfo": {
    "user001": {
      "NickName":"Kasil",
      "Coin":500,
      "Score":0
    }
  },

  "Rooms": {
    "room001": {
      "state":"playing",
      "playerCount":2,
      "players": {
        "playerA": {
          "hp":80,
          "ready":true
        },
        "playerB": {
          "hp":100,
          "ready":false
        }
      }
    }
  }
}
```

여기서 중요한 건 데이터가 <b>하나의 큰 나무처럼 이어져 있다</b>는 점이야.

예를 들어:

```txt
Rooms / room001 / players / playerA / hp
```

이런 식으로 경로를 따라 들어가서 값을 읽고 쓰는 구조야.

---

# 2. Cloud Firestore의 저장 방식

Firestore는 데이터를 <b>컬렉션과 문서</b>로 저장해.

공식 문서에서는 Firestore를 NoSQL 문서 지향 데이터베이스라고 설명하고, SQL처럼 테이블과 행이 있는 게 아니라 <b>문서를 컬렉션 안에 저장하는 방식</b>이라고 설명해. 각 문서는 key-value 필드를 가지고, 문서 안에는 중첩 객체나 서브컬렉션도 둘 수 있어.

예를 들면 이런 구조야.

```txt
users 컬렉션
 └─ user001 문서
     ├─ NickName: "Kasil"
     ├─ Coin: 500
     └─ Score: 0

rooms 컬렉션
 └─ room001 문서
     ├─ state: "playing"
     ├─ playerCount: 2
     └─ createdAt: timestamp

rooms / room001 / players 서브컬렉션
 ├─ playerA 문서
 │   ├─ hp: 80
 │   └─ ready: true
 └─ playerB 문서
     ├─ hp: 100
     └─ ready: false
```

즉 Firestore는 이런 식으로 생각하면 돼.

```txt
컬렉션 → 문서 → 필드
컬렉션 → 문서 → 서브컬렉션 → 문서
```

Realtime Database가 <b>큰 JSON 나무</b>라면, Firestore는 <b>여러 개의 문서 묶음</b>이야.

---

# 3. 가장 중요한 구조적 차이

## Realtime Database

```txt
전체 데이터가 하나의 JSON 트리
```

예시:

```txt
Rooms/room001/players/playerA/hp
```

특징은 <b>경로 중심</b>이야.

그래서 특정 위치의 값이 바뀌면 그 경로를 구독하고 있던 클라이언트들이 바로 변화를 받을 수 있어. Firebase 문서도 Realtime Database는 데이터가 JSON으로 저장되고, 연결된 모든 클라이언트에 실시간으로 동기화된다고 설명해.

---

## Firestore

```txt
컬렉션 안에 문서가 있고, 문서 안에 필드가 있음
```

예시:

```txt
rooms 컬렉션
  → room001 문서
      → players 서브컬렉션
          → playerA 문서
```

특징은 <b>문서 중심</b>이야.

그래서 유저별 정보, 아이템별 정보, 랭킹 데이터처럼 “하나의 객체를 문서로 관리하는 데이터”에 잘 어울려.

---

# 4. 실시간 멀티플레이어 상태에는 뭐가 더 적합할까?

<b>잦은 상태 업데이트가 필요한 방 상태(Room State)라면 Realtime Database가 더 적합한 편이야.</b>

이유는 Realtime Database가 단순한 JSON 구조를 빠르게 동기화하는 데 강하고, 공식 비교 문서에서도 <b>단순한 데이터 모델, 간단한 조회, 낮은 지연 시간 동기화가 필요한 앱에 적합하다</b>고 설명해. 또 Realtime Database는 일반적인 응답 시간이 10ms 이하이며, <b>frequent state-syncing</b>, 즉 잦은 상태 동기화에 이상적인 선택지라고 안내하고 있어.

예를 들어 이런 데이터는 Realtime Database에 잘 맞아.

```txt
{
  "Rooms": {
    "room001": {
      "state":"playing",
      "currentTurn":"playerA",
      "timer":27,
      "players": {
        "playerA": {
          "ready":true,
          "hp":80
        },
        "playerB": {
          "ready":true,
          "hp":60
        }
      }
    }
  }
}
```

방 상태, 준비 여부, 현재 턴, 간단한 HP, 매칭 상태처럼 <b>계속 바뀌고 모두가 바로 알아야 하는 값</b>은 Realtime Database 쪽이 더 자연스러워.

---

# 5. 그럼 Firestore는 언제 더 좋을까?

Firestore는 데이터가 조금 더 복잡하고, 검색이나 필터링이 필요한 경우에 좋아.

예를 들어:

```txt
유저 인벤토리
보유 재화
퀘스트 진행도
구매 기록
랭킹
캐릭터 성장 정보
아이템 도감
```

이런 데이터는 Firestore가 더 관리하기 좋아. 공식 비교 문서에서도 Firestore는 컬렉션과 문서로 데이터를 저장하고, 복잡한 계층 데이터는 문서 안의 서브컬렉션으로 규모 있게 구성하기 쉽다고 설명해. 반대로 Realtime Database는 하나의 큰 JSON 트리라 복잡한 계층 데이터는 규모가 커질수록 관리가 어려울 수 있다고 설명하고 있어.

---

# 6. 게임 기준으로 정리하면

| 게임 데이터 | 추천 |
| --- | --- |
| 플레이어 닉네임 | Firestore 또는 Realtime Database 둘 다 가능 |
| 인벤토리 | Firestore 추천 |
| 재화 | Firestore 추천 |
| 유저 계정 정보 | Firestore 추천 |
| 방 상태 | Realtime Database 추천 |
| 준비 완료 여부 | Realtime Database 추천 |
| 현재 턴 정보 | Realtime Database 추천 |
| 접속 중 / 접속 종료 상태 | Realtime Database 추천 |
| 랭킹 | Firestore 추천 |
| 게임 중 위치 동기화 | Firebase보다는 Photon/Fusion 같은 네트워크 엔진 추천 |

특히 접속 상태, 즉 누가 온라인인지 오프라인인지 확인하는 <b>Presence 기능</b>은 Realtime Database가 기본 지원하고, Firestore는 기본 지원하지 않는다고 공식 비교 문서에 나와 있어. 그래서 멀티플레이어의 방 상태나 접속 상태에는 Realtime Database가 더 잘 맞는 편이야.

---

## 답안 느낌으로 쓰면

Firebase Realtime Database는 데이터를 하나의 큰 JSON 트리 구조로 저장한다. 따라서 <code>Rooms/room001/players/playerA/hp</code>처럼 경로를 따라 데이터에 접근하며, 특정 노드의 값이 바뀌면 연결된 클라이언트들이 실시간으로 변경 사항을 받을 수 있다.

반면 Cloud Firestore는 데이터를 컬렉션과 문서 단위로 저장한다. 예를 들어 <code>users</code> 컬렉션 안에 <code>user001</code> 문서를 만들고, 그 문서 안에 닉네임, 재화, 점수 같은 필드를 저장하는 방식이다. 복잡한 데이터는 문서 안에 서브컬렉션을 만들어 구조화할 수 있다.

따라서 인벤토리, 재화, 유저 정보처럼 구조화된 데이터를 관리할 때는 Cloud Firestore가 더 적합하고, 방 상태, 준비 상태, 접속 상태처럼 값이 자주 바뀌고 빠르게 동기화되어야 하는 멀티플레이어 환경에서는 Firebase Realtime Database가 더 적합하다고 생각한다. 다만 캐릭터 위치처럼 매우 빠르게 변하는 실시간 액션 데이터는 Firebase보다는 Photon Fusion 같은 네트워크 엔진을 사용하는 것이 더 적절하다.

<b>문제 2</b>

<b>Firebase Realtime Database나 Firestore에서 데이터가 변경되는 것을 감지하기 위해 리스너(Listener)를</b>

<b>부착했습니다. 데이터 변경 이벤트가 발생하여 콜백(Callback) 함수가 호출되었을 때,</b>

<b>이 콜백 내부에서 유니티의 UI(예: 점수 텍스트 업데이트)나 게임 오브젝트(GameObject)를</b>

<b>직접 제어하려고 하면 에러가 발생합니다. 이 에러가 발생하는 원인(스레드 관점)은 무엇이며,</b>

<b>이를 해결하기 위해 유니티 클라이언트에서 어떤 방식을 사용해야 하는지 서술해 보세요.</b>

> <b>Firebase 콜백은 Unity의 메인 스레드가 아닌 다른 스레드에서 실행될 수 있는데, Unity UI나 GameObject는 메인 스레드에서만 안전하게 제어할 수 있다.</b>

Unity는 보통 사용자 코드가 <b>메인 스레드</b>에서 실행되고, 멀티스레드 작업은 별도의 worker thread에서 실행된 뒤 결과를 메인 스레드와 동기화하는 구조를 가진다고 설명해. 또한 Unity 문서에서도 다른 스레드에서 실행될 수 있는 핸들러에서는 thread-safe한 코드만 사용해야 하며, 허용된 Unity API만 접근해야 한다고 안내하고 있어.

---

## 쉽게 말하면

Firebase가 데이터 변경을 감지하면 콜백을 불러.

```txt
reference.ValueChanged+=HandleValueChanged;
```

그런데 이 콜백이 Unity의 평소 <code>Update()</code>처럼 메인 스레드에서 안전하게 실행되는 게 아니라, <b>Firebase의 비동기 작업 흐름 안에서 실행될 수 있어.</b>

그래서 콜백 안에서 바로 이렇게 하면 문제가 생길 수 있어.

```txt
scoreText.text="100";
gameObject.SetActive(false);
```

Unity 입장에서는 이런 상태야.

> “잠깐, UI랑 GameObject는 내가 관리하는 메인 스레드에서 건드려야 하는데, 왜 다른 스레드에서 만지고 있어?”

그래서 에러가 나는 거야.

---

## 해결 방법

Firebase 콜백 안에서는 데이터를 받아오기만 하고,

<b>UI 변경이나 GameObject 제어는 Unity 메인 스레드로 넘겨서 실행</b>해야 해.

대표적인 방법은 2가지야.

| 방법 | 사용 상황 |
| --- | --- |
| <code>ContinueWithOnMainThread()</code> | <code>GetValueAsync()</code>, <code>SetValueAsync()</code> 같은 Task 작업 후 처리 |
| <code>UnityMainThreadDispatcher.Enqueue()</code> | 리스너 콜백 안에서 UI / 오브젝트 제어할 때 |

Firebase 공식 Realtime Database Unity 문서에서도 <code>GetValueAsync()</code> 예제에서 <code>ContinueWithOnMainThread()</code>를 사용하고, Firebase Unity 참조 문서에는 이 메서드가 Task 이후 작업을 메인 스레드에서 실행하도록 돕는 확장 메서드로 제공돼.

---

## 예시 1. <code>ContinueWithOnMainThread()</code> 사용

```txt
usingFirebase.Extensions;

reference.Child("Score").GetValueAsync().ContinueWithOnMainThread(task=>
{
if (task.IsCompleted)
    {
intscore=int.Parse(task.Result.Value.ToString());

// 메인 스레드에서 실행되므로 UI 수정 가능
scoreText.text=score.ToString();
    }
});
```

---

## 예시 2. 리스너에서는 Dispatcher 사용

```txt
voidStart()
{
reference.Child("Score").ValueChanged+=HandleScoreChanged;
}

voidHandleScoreChanged(objectsender,ValueChangedEventArgsargs)
{
if (args.DatabaseError!=null)
    {
Debug.LogError(args.DatabaseError.Message);
return;
    }

stringscore=args.Snapshot.Value.ToString();

UnityMainThreadDispatcher.Instance().Enqueue(()=>
    {
scoreText.text=score;
    });
}
```

여기서 중요한 건 이 부분이야.

```txt
UnityMainThreadDispatcher.Instance().Enqueue(()=>
{
scoreText.text=score;
});
```

이렇게 하면 Firebase 콜백에서 받은 작업을 <b>Unity 메인 스레드 줄서기 목록에 넣고</b>, Unity가 안전한 타이밍에 UI를 바꿔줘.

---

## 답안식으로 쓰면

Firebase Realtime Database나 Firestore의 리스너 콜백은 비동기적으로 실행되며, Unity의 메인 스레드가 아닌 <b>백그라운드 스레드</b>에서 호출될 수 있다. 하지만 Unity의 UI, Transform, GameObject 같은 객체들은 메인 스레드에서만 안전하게 접근할 수 있다. 그래서 Firebase 콜백 내부에서 바로 <code>Text.text</code>를 변경하거나 <code>GameObject.SetActive()</code>를 호출하면 스레드 충돌로 에러가 발생할 수 있다.

이를 해결하기 위해서는 Firebase 콜백 안에서 Unity 오브젝트를 직접 제어하지 말고, <code>ContinueWithOnMainThread()</code>나 <code>UnityMainThreadDispatcher.Enqueue()</code>를 사용해 UI 갱신과 GameObject 제어 코드를 Unity 메인 스레드에서 실행해야 한다. 즉, Firebase 콜백은 데이터만 받아 오고, 실제 화면 변경은 메인 스레드로 넘겨 처리하는 방식이 안전하다.

응, 이 둘은 둘 다 **“Firebase 쪽 비동기 결과를 Unity 메인 스레드에서 처리하게 해주는 방법”**이야.

하지만 쓰는 위치와 목적이 조금 달라.

핵심부터 말하면:

<blockquote markdown="1">

<b><code>ContinueWithOnMainThread()</code></b><b>는 Firebase Task 전용 자동 배달</b>

<b><code>UnityMainThreadDispatcher.Enqueue()</code></b><b>는 직접 메인 스레드 줄서기에 넣는 수동 배달</b>

</blockquote>

Unity는 대부분의 UI, GameObject, Transform API를 메인 스레드에서만 안전하게 호출할 수 있어. Unity 공식 문서에서도 대부분의 Unity API는 thread-safe하지 않고 메인 스레드에서만 호출 가능하다고 설명해.

---

# 1. 두 방식 한눈에 비교

| 구분 | <code>ContinueWithOnMainThread()</code> | <code>UnityMainThreadDispatcher.Enqueue()</code> |
| --- | --- | --- |
| 소속 | Firebase SDK에서 제공 | 별도 Dispatcher 스크립트 / 라이브러리 |
| 사용 대상 | Firebase의 <code>Task</code> 작업 | Firebase뿐 아니라 모든 백그라운드 콜백 |
| 대표 사용처 | <code>GetValueAsync()</code>, <code>SetValueAsync()</code> 완료 후 | <code>ValueChanged</code> 리스너, 일반 Thread, 외부 SDK 콜백 |
| 실행 방식 | Task가 끝난 뒤 이어지는 코드를 메인 스레드에서 실행 | 원하는 코드를 메인 스레드 큐에 직접 넣음 |
| 코드 느낌 | “작업 끝나면 메인 스레드에서 이어서 실행해줘” | “이 코드를 메인 스레드에서 실행하도록 예약해줘” |
| 준비물 | <code>using Firebase.Extensions;</code> | 씬에 <code>UnityMainThreadDispatcher</code> 오브젝트 필요 |
| 추천 상황 | Firebase 작업 1회성 처리 | 리스너, 반복 콜백, Firebase 외부 비동기 처리 |

Firebase 공식 Unity 참조에서도 <code>ContinueWithOnMainThread()</code>는 Task가 완료된 뒤 continuation, 즉 이어지는 함수를 Unity의 메인 스레드에서 호출하게 해주는 확장 메서드라고 설명해.

<code>UnityMainThreadDispatcher</code>는 다른 스레드에서 Unity UI 함수나 Unity가 메인 스레드로 제한한 작업을 호출할 때 메인 스레드로 dispatch하기 위한 도구라고 설명되어 있어.

---

# 2. <code>ContinueWithOnMainThread()</code>는 언제 쓰는가?

Firebase에서 데이터를 <b>한 번 읽거나</b>, <b>한 번 저장하거나</b>, <b>로그인 결과를 받거나</b>, <b>의존성 체크를 끝낸 뒤</b> 무언가를 할 때 좋아.

예를 들면 이런 작업들:

```txt
GetValueAsync()
SetValueAsync()
SetRawJsonValueAsync()
CheckAndFixDependenciesAsync()
GetSnapshotAsync()
```

이런 함수들은 대부분 <code>Task</code>를 반환해.

그래서 이렇게 쓸 수 있어.

```txt
usingFirebase.Extensions;

reference.Child("Score").GetValueAsync().ContinueWithOnMainThread(task=>
{
if (task.IsFaulted)
    {
Debug.LogError("점수 불러오기 실패");
return;
    }

DataSnapshotsnapshot=task.Result;
scoreText.text=snapshot.Value.ToString();
});
```

이 코드는 이런 흐름이야.

```txt
Firebase에서 Score 읽기 시작
        ↓
비동기 작업 진행
        ↓
읽기 완료
        ↓
ContinueWithOnMainThread 실행
        ↓
Unity 메인 스레드에서 scoreText 변경
```

즉, <b>Firebase 작업이 끝난 뒤 바로 UI를 바꾸고 싶을 때</b> 가장 깔끔해.

---

# 3. <code>UnityMainThreadDispatcher.Enqueue()</code>는 언제 쓰는가?

<code>Enqueue()</code>는 Firebase Task에만 묶여 있지 않아.

<b>다른 스레드에서 실행된 코드라면 무엇이든 Unity 메인 스레드로 넘길 수 있어.</b>

예를 들면:

```txt
FirebaseRealtimeDatabase의ValueChanged리스너
FirestoreSnapshotListener
일반Thread
Socket통신콜백
외부SDK콜백
서버응답콜백
```

이런 상황에서 좋아.

예시:

```txt
reference.Child("Score").ValueChanged+= (sender,args)=>
{
if (args.DatabaseError!=null)
    {
Debug.LogError(args.DatabaseError.Message);
return;
    }

stringscore=args.Snapshot.Value.ToString();

UnityMainThreadDispatcher.Instance().Enqueue(()=>
    {
scoreText.text=score;
    });
};
```

흐름은 이렇게 돼.

```txt
Firebase에서 데이터 변경 감지
        ↓
ValueChanged 콜백 실행
        ↓
콜백이 Unity 메인 스레드가 아닐 수 있음
        ↓
Enqueue로 UI 변경 코드를 예약
        ↓
UnityMainThreadDispatcher가 Update에서 실행
        ↓
메인 스레드에서 scoreText 변경
```

즉, <code>Enqueue()</code>는 <b>메인 스레드 작업 대기열에 넣는 방식</b>이야.

말하자면 “Unity에게 이 일 좀 안전한 시간에 처리해줘” 하고 쪽지를 넣는 우편함 같은 구조야. 📮

---

# 4. 네 코드에서는 어떤 방식을 쓰고 있나?

네가 올린 <code>UserRegister</code> 코드는 현재 이런 구조야.

```txt
reference.Child("UserInfo")
    .OrderByChild("NickName")
    .EqualTo(NickName)
    .GetValueAsync()
    .ContinueWith(task=>
{
dispatcher.Enqueue(()=>
    {
CheckText.text="중복된 닉네임입니다.";
    });
});
```

즉, 현재는:

```txt
Firebase 작업 완료
        ↓
ContinueWith 실행
        ↓
그 안에서 dispatcher.Enqueue 사용
        ↓
UI 변경
```

이 방식이야. 네 코드에서는 <code>UnityMainThreadDispatcher</code>를 가져오고, Firebase 작업 결과에 따라 <code>CheckText.text</code> 변경이나 <code>SceneManager.LoadScene("MainScene")</code>을 <code>dispatcher.Enqueue()</code> 안에서 실행하고 있어.

이 방식은 안전해.

다만 더 간단하게 바꾸면 이렇게도 가능해.

```txt
usingFirebase.Extensions;

reference.Child("UserInfo")
    .OrderByChild("NickName")
    .EqualTo(NickName)
    .GetValueAsync()
    .ContinueWithOnMainThread(task=>
{
if (task.IsFaulted)
    {
Debug.LogError("데이터 조회 중 오류 발생: "+task.Exception);
return;
    }

DataSnapshotsnapshot=task.Result;

if (snapshot.HasChildren)
    {
CheckText.text="중복된 닉네임입니다.";
    }
});
```

이렇게 하면 <code>dispatcher.Enqueue()</code>를 따로 안 써도 돼.

왜냐하면 <code>ContinueWithOnMainThread()</code> 자체가 이미 메인 스레드에서 이어지는 코드를 실행해주기 때문이야.

---

# 5. 둘 중 뭘 써야 할까?

## 상황 1. Firebase 작업을 한 번 실행하고 결과를 받을 때

예:

```txt
GetValueAsync()
SetValueAsync()
SetRawJsonValueAsync()
CheckAndFixDependenciesAsync()
```

이럴 때는 <b><code>ContinueWithOnMainThread()</code></b><b> 추천</b>.

```txt
reference.Child("UserInfo").GetValueAsync().ContinueWithOnMainThread(task=>
{
CheckText.text="불러오기 완료";
});
```

이게 가장 깔끔해.

---

## 상황 2. 데이터 변경 리스너를 붙였을 때

예:

```txt
ValueChanged
ChildAdded
ChildChanged
FirestoreListen
```

이럴 때는 <b><code>UnityMainThreadDispatcher.Enqueue()</code></b><b>를 쓰는 식으로 이해하면 좋아.</b>

```txt
reference.Child("RoomState").ValueChanged+= (sender,args)=>
{
stringstate=args.Snapshot.Value.ToString();

dispatcher.Enqueue(()=>
    {
roomStateText.text=state;
    });
};
```

리스너는 “작업 한 번 끝남”이 아니라 <b>언제든 계속 호출되는 이벤트</b>라서, <code>ContinueWithOnMainThread()</code>보다 <code>Enqueue()</code> 개념이 더 잘 맞아.

---

## 상황 3. Firebase가 아닌 다른 비동기 작업에서 Unity UI를 바꿀 때

예:

```txt
Thread
Socket
외부서버콜백
외부SDK이벤트
```

이럴 때는 <b><code>UnityMainThreadDispatcher.Enqueue()</code></b>.

```txt
dispatcher.Enqueue(()=>
{
gameObject.SetActive(false);
});
```

<code>ContinueWithOnMainThread()</code>는 Firebase Task 확장 메서드라서, 일반 콜백에는 바로 쓰기 어렵기 때문이야.

---

# 6. 둘을 같이 써야 할까?

대부분은 <b>같이 안 써도 돼.</b>

## 보통은 이렇게 선택하면 돼

```txt
Firebase Task 결과 처리
→ ContinueWithOnMainThread()

Firebase 리스너 / 일반 콜백 / 외부 스레드
→ UnityMainThreadDispatcher.Enqueue()
```

예를 들어 이건 중복 느낌이야.

```txt
reference.Child("Score").GetValueAsync().ContinueWithOnMainThread(task=>
{
dispatcher.Enqueue(()=>
    {
scoreText.text="100";
    });
});
```

이미 <code>ContinueWithOnMainThread()</code> 안에 들어왔으면 메인 스레드라서, 다시 <code>Enqueue()</code>할 필요가 거의 없어.

---

# 7. 메모용 정리

```txt
ContinueWithOnMainThread()
- Firebase Task 작업이 끝난 뒤 실행할 코드를 Unity 메인 스레드에서 실행해주는 방식이다.
- GetValueAsync(), SetValueAsync(), CheckAndFixDependenciesAsync()처럼 한 번 실행하고 결과를 받는 Firebase 비동기 작업에 적합하다.
- using Firebase.Extensions; 가 필요하다.
- UI Text 변경, GameObject 제어, 씬 전환을 안전하게 처리할 수 있다.

UnityMainThreadDispatcher.Enqueue()
- 다른 스레드에서 실행 중인 코드를 Unity 메인 스레드에서 실행되도록 큐에 넣는 방식이다.
- Firebase 리스너, 일반 Thread, Socket, 외부 SDK 콜백처럼 Task 형태가 아니거나 반복적으로 호출되는 콜백에 적합하다.
- 씬 안에 UnityMainThreadDispatcher 오브젝트가 필요하다.
- Enqueue 안에 넣은 코드는 Unity의 메인 스레드에서 실행된다.

선택 기준
- Firebase의 GetValueAsync(), SetValueAsync() 결과 처리 → ContinueWithOnMainThread()
- Firebase의 ValueChanged 같은 리스너 처리 → UnityMainThreadDispatcher.Enqueue()
- Firebase가 아닌 다른 백그라운드 콜백 처리 → UnityMainThreadDispatcher.Enqueue()
```

---

# 8. 답안식으로 쓰면

<code>ContinueWithOnMainThread()</code>와 <code>UnityMainThreadDispatcher.Enqueue()</code>는 모두 Unity의 메인 스레드에서 UI나 GameObject를 안전하게 제어하기 위해 사용된다. 차이점은 <code>ContinueWithOnMainThread()</code>는 Firebase의 비동기 Task가 완료된 뒤 이어지는 코드를 메인 스레드에서 실행해주는 Firebase 제공 방식이고, <code>UnityMainThreadDispatcher.Enqueue()</code>는 다른 스레드에서 실행 중인 작업을 직접 메인 스레드 큐에 넣어 실행시키는 방식이라는 점이다.

따라서 <code>GetValueAsync()</code>나 <code>SetValueAsync()</code>처럼 한 번 실행하고 결과를 받는 Firebase 작업에는 <code>ContinueWithOnMainThread()</code>를 사용하는 것이 좋다. 반면 <code>ValueChanged</code> 같은 데이터 변경 리스너나 일반 Thread, 외부 SDK 콜백처럼 언제 호출될지 모르는 이벤트에서는 <code>UnityMainThreadDispatcher.Enqueue()</code>를 사용해 UI 변경이나 GameObject 제어 코드를 메인 스레드에서 실행하도록 처리하는 것이 안전하다.

<b>\[문제 3: 유니티 스크립트에서의 DB 참조(Reference) 및 비동기 처리 구성\]</b>

<b>유니티 C# 스크립트에서 Firebase Realtime Database에 연동하여 특정 유저의 데이터를 읽거나 쓰려면, 가장 먼저 데이터가 위치한 주소를 가리키는 참조(Reference)를 구성해야 합니다.</b>

<b>FirebaseDatabase.DefaultInstance.RootReference를 사용하여 특정 유저(예: UID가 “user123”인 유저) 노드 하위의 “gold” 스탯 경로로 접근하는 참조 객체 구성 과정을 설명해 보세요. 또한, 이 참조 경로에 새로운 값을 덮어쓸 때 사용하는 SetValueAsync() 메서드가 왜 ‘비동기(Async)’ 방식으로 설계되어 있으며, 게임 클라이언트(메인 스레드) 관점에서 이것이 왜 필수적인지 서술해 보세요.</b>

# 1. Reference가 뭔가?

Firebase Realtime Database에서 <b>Reference</b>는 데이터가 있는 위치를 가리키는 주소야.

예를 들어 DB 구조가 이렇게 있다고 해보자.

```txt
{
  "users": {
    "user123": {
      "gold":500
    }
  }
}
```

여기서 <code>user123</code> 유저의 골드 값 위치는:

```txt
users/user123/gold
```

이 경로가 돼.

Unity C#에서는 이 경로를 <code>DatabaseReference</code>로 만들어서 읽거나 쓸 수 있어.

---

# 2. RootReference에서 gold까지 접근하는 과정

```txt
usingFirebase.Database;
usingUnityEngine;

publicclassUserGoldManager :MonoBehaviour
{
privateDatabaseReferencereference;

voidStart()
    {
stringuid="user123";

reference=FirebaseDatabase.DefaultInstance.RootReference;

DatabaseReferencegoldRef=reference
            .Child("users")
            .Child(uid)
            .Child("gold");
    }
}
```

이 코드는 이렇게 해석하면 돼.

```txt
FirebaseDatabase.DefaultInstance.RootReference
```

Firebase Realtime Database의 <b>최상위 위치</b>를 가리켜.

```txt
.Child("users")
```

<code>users</code> 노드로 들어감.

```txt
.Child(uid)
```

<code>user123</code> 유저 노드로 들어감.

```txt
.Child("gold")
```

그 유저의 <code>gold</code> 값 위치로 들어감.

즉 전체 경로는:

```txt
users/user123/gold
```

이 되는 거야.

Firebase 공식 문서에서도 Unity에서 <code>FirebaseDatabase.DefaultInstance.GetReference("Leaders")</code>처럼 특정 경로의 참조를 만든 뒤 데이터를 읽는 예시를 보여주고 있어. 또한 <code>GetValueAsync()</code>는 특정 경로의 데이터를 한 번 읽어오는 방식이라고 설명해.

---

# 3. gold 값을 쓰는 코드

특정 유저의 골드를 <code>1000</code>으로 덮어쓰고 싶다면 이렇게 해.

```txt
usingFirebase.Database;
usingFirebase.Extensions;
usingUnityEngine;

publicclassUserGoldManager :MonoBehaviour
{
privateDatabaseReferencereference;

voidStart()
    {
stringuid="user123";

reference=FirebaseDatabase.DefaultInstance.RootReference;

DatabaseReferencegoldRef=reference
            .Child("users")
            .Child(uid)
            .Child("gold");

goldRef.SetValueAsync(1000).ContinueWithOnMainThread(task=>
        {
if (task.IsFaulted)
            {
Debug.LogError("골드 저장 실패: "+task.Exception);
return;
            }

if (task.IsCompleted)
            {
Debug.Log("골드 저장 성공");
            }
        });
    }
}
```

여기서 핵심은 이 부분이야.

```txt
goldRef.SetValueAsync(1000);
```

<code>goldRef</code>가 가리키는 위치:

```txt
users/user123/gold
```

에 <code>1000</code>을 저장하는 거야.

Firebase 공식 문서에 따르면 <code>SetValueAsync()</code>는 지정한 Reference 위치에 데이터를 저장하며, 해당 경로에 기존 데이터가 있으면 그 값을 대체해. 즉 <code>gold</code>가 500이었다면 1000으로 덮어써지는 방식이야.

---

# 4. 왜 <code>SetValueAsync()</code>는 비동기일까?

<code>SetValueAsync()</code>는 Firebase 서버에 데이터를 보내는 작업이야.

즉, Unity 안에서 변수 하나 바꾸는 것처럼 즉시 끝나는 작업이 아니야.

```txt
intgold=1000;
```

이건 게임 안 메모리 값을 바꾸는 거라 거의 바로 끝나.

하지만:

```txt
goldRef.SetValueAsync(1000);
```

이건 이런 과정을 거쳐.

```txt
Unity 클라이언트
    ↓
인터넷 연결
    ↓
Firebase 서버에 요청
    ↓
서버에서 데이터 저장
    ↓
저장 성공 / 실패 결과 반환
    ↓
Unity에서 결과 처리
```

네트워크 상태가 느리거나 끊길 수도 있고, 서버 응답을 기다려야 할 수도 있어. 그래서 이 작업을 동기 방식으로 처리하면 Unity 메인 스레드가 멈춰버릴 수 있어.

---

# 5. 게임 클라이언트에서 Async가 필수인 이유

Unity 게임은 매 프레임 계속 돌아가야 해.

```txt
입력 처리
캐릭터 이동
충돌 처리
애니메이션
UI 갱신
렌더링
```

이 모든 게 메인 스레드에서 빠르게 반복돼.

그런데 Firebase 저장이 끝날 때까지 메인 스레드를 멈춰버리면?

```txt
버튼 클릭
    ↓
SetValue 동기 저장 시작
    ↓
서버 응답 기다림
    ↓
게임 화면 멈춤
    ↓
입력 안 먹음
    ↓
프레임 끊김
```

이렇게 돼.

그래서 <code>SetValueAsync()</code>는 서버 응답을 기다리는 동안 게임을 멈추지 않고, 저장 결과가 도착했을 때 콜백으로 후처리할 수 있게 설계된 거야.

Unity 공식 문서도 비동기 프로그래밍은 오래 걸리는 작업을 수행하는 동안 메인 스레드를 막지 않고 앱이 계속 반응하도록 해준다고 설명해.

---

# 6. 단, 결과 처리 시 메인 스레드 주의

Firebase 저장이 끝난 뒤 UI를 바꾸고 싶다면:

```txt
resultText.text="저장 성공";
```

이런 코드는 Unity 메인 스레드에서 실행해야 해.

Unity 공식 문서에서는 대부분의 Unity API가 thread-safe하지 않고 메인 스레드에서만 호출 가능하다고 설명해.

그래서 보통 이렇게 써.

```txt
goldRef.SetValueAsync(1000).ContinueWithOnMainThread(task=>
{
if (task.IsCompleted)
    {
resultText.text="골드 저장 성공";
    }
});
```

<code>ContinueWithOnMainThread()</code>를 쓰면 Firebase 작업이 끝난 뒤 이어지는 코드를 Unity 메인 스레드에서 실행할 수 있어. Firebase의 Unity 문서 예제에서도 <code>GetValueAsync()</code> 뒤에 <code>ContinueWithOnMainThread()</code>를 붙여 결과를 처리하는 형태를 보여줘.

---

# 7. 답안식으로 정리

Firebase Realtime Database에서 특정 유저의 데이터를 읽거나 쓰기 위해서는 먼저 데이터가 위치한 경로를 가리키는 <code>DatabaseReference</code>를 만들어야 한다. 예를 들어 UID가 <code>user123</code>인 유저의 <code>gold</code> 값에 접근하려면 <code>FirebaseDatabase.DefaultInstance.RootReference</code>에서 시작해 <code>Child("users").Child("user123").Child("gold")</code> 순서로 참조를 구성한다. 이렇게 하면 전체 경로는 <code>users/user123/gold</code>가 된다.

이 경로에 새로운 값을 저장할 때는 <code>SetValueAsync()</code>를 사용한다. 예를 들어 <code>goldRef.SetValueAsync(1000)</code>을 호출하면 <code>users/user123/gold</code> 위치의 값이 1000으로 덮어써진다. 이 메서드가 비동기 방식인 이유는 데이터 저장이 Unity 내부에서 즉시 끝나는 작업이 아니라, 네트워크를 통해 Firebase 서버에 요청을 보내고 응답을 기다리는 작업이기 때문이다. 만약 이 과정이 동기 방식으로 처리된다면 서버 응답을 기다리는 동안 Unity의 메인 스레드가 멈추고, 게임 화면 정지나 입력 지연이 발생할 수 있다.

따라서 게임 클라이언트에서는 Firebase 읽기와 쓰기 작업을 비동기 방식으로 처리해야 한다. 저장 결과를 받은 뒤 UI를 변경하거나 게임 오브젝트를 제어해야 한다면 <code>ContinueWithOnMainThread()</code> 같은 방식을 사용해 Unity 메인 스레드에서 후처리해야 한다.
