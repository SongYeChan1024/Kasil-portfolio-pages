## 요약


### 오늘 수업 핵심 요약

- <b>메타버스Metaverse</b>의 정의와 현실-비현실 연결 방식을 배웠다. 메타버스는 Meta초월와 Universe세계의 합성어로, 공간적·정신적·사회적·경제적·정보적 연결을 통해 현실과 가상을 이어준다. 
- <b>한국 인터넷 발전사</b>를 살펴보며 미국과 거의 동시에 시작한 인터넷 인프라와 싸이월드, 아이폰, 카카오톡 등 주요 서비스의 등장 시점을 이해했다. 
- <b>블록체인Blockchain</b> 기술의 핵심 개념을 배웠다. 블록체인은 모두가 공동으로 관리하는 수정 불가능한 디지털 장부로, 탈중앙화를 통해 투명성과 불변성을 제공한다. 
- 메타버스의 4가지 유형증강현실AR, 라이프로깅, 거울세계, 가상세계과 지속 가능한 메타버스 경제 생태계의 조건을 학습했다.

### 주요 개념 정리

- <b>메타버스 Metaverse</b>
  - 설명: Meta초월, 가상와 Universe세계, 우주의 합성어로, 현실을 넘어선 가상의 세계 또는 현실과 연결된 확장된 디지털 세계를 의미한다. 
  - 예시: 싸이월드의 미니홈피와 아바타 시스템이 초기 메타버스 형태였다. 
  - 사용되는 상황: VR 게임, 가상 회의, 디지털 전시관, 메타버스 플랫폼 등
  - 헷갈릴 수 있는 점: 단순한 가상현실VR과 달리 메타버스는 현실과의 다층적 연결경제적, 사회적, 정보적을 포함한다.
- <b>블록체인 Blockchain</b>
  - 설명: 모두가 공동으로 관리하는 수정 불가능한 디지털 장부. 특정 중앙기관이 데이터를 독점하는 것이 아니라 네트워크 참여자 모두가 동일한 장부를 나누어 가지는 탈중앙화 기술이다. 
  - 예시: 각 블록이 체인처럼 연결되어 있어서 하나의 블록이 해킹당하거나 사라져도 다른 블록에 동일한 정보가 남아있다. 
  - 사용되는 상황: 가상자산 거래, NFT 소유권 증명, 투명한 투표 시스템, 농산물 이력 추적 등 
  - 헷갈릴 수 있는 점: 블록체인과 비트코인은 다르다. 비트코인은 암호화폐일 뿐이고, 블록체인은 더 넓은 개념의 기술 플랫폼이다. 
- <b>디지털 트윈 Digital Twin</b>
  - 설명: 현실세계와 똑같은 가상세계를 만들어서 시뮬레이션하는 기술. Twin쌍둥이의 의미처럼 현실과 동일한 디지털 복제본을 만든다. 
  - 예시: 월성 원자력발전소 해체 작업을 위해 가상세계에 동일한 발전소를 구현하고 수십 차례 시뮬레이션하여 가장 안전하고 효율적인 해체 방법을 찾았다. 
  - 사용되는 상황: 공장 설비 최적화, 건물 시공 시뮬레이션, 위험 작업 사전 테스트 등
- <b>탈중앙화 Decentralization</b>
  - 설명: 중앙 서버에 데이터를 집중시키는 대신 네트워크에 연결된 모든 노드PC에 데이터를 복사해서 분산 관리하는 방식 
  - 예시: 은행 서버가 해킹당하면 모든 잔고 정보가 사라질 수 있지만, 블록체인은 각자가 동일한 장부를 가지고 있어서 하나가 문제가 생겨도 괜찮다. 
  - 사용되는 상황: 블록체인 네트워크, P2P 파일 공유
  - 헷갈릴 수 있는 점: 완전한 탈중앙화는 아직 현실화되기 어렵다. 대기업과 기존 기득권이 탈중앙화를 막으려는 경향이 있다. 
- <b>NFT Non-Fungible Token</b>
  - 설명: 대체 불가능한 토큰. 블록체인 기술을 활용해 디지털 자산의 고유한 소유권을 증명하는 방식 
  - 예시: 가상세계의 아이템, 디지털 아트, 게임 아이템 등의 소유권을 증명
  - 사용되는 상황: 메타버스 경제 활동, 디지털 콘텐츠 거래

### 수업 흐름별 정리

### 1. 메타버스의 정의와 연결 방식

- 메타버스는 Meta초월와 Universe세계의 합성어이다. 
- 현실과 비현실을 5가지 방식으로 연결한다:
  - <b>공간적 연결</b>: 증강현실AR과 확장현실XR로 현실 공간을 가상공간으로 확장 
  - <b>데이터적 연결</b>: 디지털 트윈과 IoT사물인터넷로 현실 데이터를 가상세계에 반영 
  - <b>경제적 연결</b>: 가상자산과 NFT, 블록체인으로 가상-현실 경제 활동 연결 
  - <b>정체성 연결</b>: 아바타를 통한 자아 표현 
  - <b>사회적 연결</b>: 가상세계에서의 인간관계와 커뮤니티 활동

### 2. 한국 인터넷 발전 역사

- <b>1990년대</b>: 인터넷 상용화 시작, 미국과 거의 동시에 발전 
- <b>2000년</b>: 싸이월드 서비스 시작. 미니홈피, 미니미 아바타, 도토리 사이버머니 시스템으로 초기 메타버스 형태 구현 
- <b>2009년</b>: 아이폰 국내 출시KT. 스마트폰 시대 시작 
- <b>2010년</b>: 카카오톡 서비스 시작. 문자에서 데이터 기반 채팅으로 전환, 마케팅 시장 변화 
- <b>2010년 이후</b>: PC 중심에서 모바일 중심으로 디바이스 시장 전환 
- <b>현재</b>: 5G와 사물인터넷IoT 발전, 전 세계 최고 수준의 인터넷 속도 

중요: 한국은 인터넷 발전에서 미국과 거의 동시에 시작했고, 현재 전 세계 최강의 인터넷 인프라를 보유하고 있다. 

### 3. 사물인터넷과 미디어 환경 변화

- <b>사물인터넷IoT</b>: 사물에 통신 모듈을 달아 사물 간 정보 교환 및 상호 소통이 가능한 환경 
- 예시: 버스 정류장에서 버스 도착 시간 실시간 확인 
- <b>1인 미디어 시대</b>: 인터넷 속도 향상으로 유튜브 등 1인 미디어 활성화. 10만 구독자 기준으로 월 500-800만원 수익 가능했던 시기5-6년 전 
- 스마트폰으로 UHD 촬영까지 가능해져 진입 장벽 낮아짐 

### 4. 블록체인 기술 심화

<ul>
<li>
<b>핵심 구조</b>: 블록과 체인. 데이터 덩어리블록들이 사슬처럼 엮여있는 구조 
</li>
<li>
<b>탈중앙화</b>: 중앙 서버가 아닌 네트워크 참여자 모두가 동일한 디지털 장부를 보유 
</li>
<li>
<b>블록체인이 핵심적인 이유</b>:

- 투명성: 누구나 정보를 확인 가능 
- 불변성: 한 번 기록된 정보는 삭제하거나 수정 불가능 
- 중개인 부재: 은행, 부동산 같은 중개자 없이 개인 간 직접 거래 가능, 수수료 절감 
</li>
<li>
<b>활용 사례</b>: 

- 농산물 재배 이력 추적 조작 불가
- 투표 시스템 조작 방지
- 아이템, 소유권, 명함 등 가상자산 관리 
</li>
</ul>

중요: 블록체인 기술의 현실화는 아직 어렵다. 기존 대기업과 기득권이 탈중앙화를 막으려는 경향이 있다. 

### 5. 메타버스 4가지 유형

- <b>증강현실AR</b>: 현실 공간 위에 가상 정보를 덧붙이는 기술 
- <b>라이프로깅Life Logging</b>: 현실에서 나를 기록하고 공유하는 기술 
- <b>거울세계Mirror World</b>: 현실세계를 디지털 공간에 그대로 복제한 기술 
- <b>가상세계Virtual Reality</b>: 현실과는 다른 가상의 공간에서 아바타를 통해 활동하는 기술

### 예시와 활용 사례

- <b>싸이월드 사례</b>:
  - 상황: 2000년 출시된 한국 최초의 메타버스형 서비스 
  - 설명: 미니홈피, 미니미 아바타, 도토리 사이버머니 시스템을 통해 가상세계에서 아바타 꾸미기, BGM 설정, 아이템 거래 등이 가능했다. 
  - 왜 이 예시를 사용했는지: 20년 전에 이미 메타버스 세계관과 동일한 구조아바타, 가상 공간, 경제 활동가 한국에서 구현되었음을 보여준다. 
- <b>원자력발전소 해체 사례</b>:
  - 상황: 월성 원자력발전소 노후화로 안전한 해체 방법 필요 
  - 설명: 디지털 트윈 기술로 현실과 똑같은 가상 발전소를 만들고 수십\~수백 차례 시뮬레이션하여 가장 안전하고 효율적이며 비용이 적게 드는 해체 방법을 도출 
  - 왜 이 예시를 사용했는지: 디지털 트윈이 실제 산업 현장에서 어떻게 활용되는지 구체적으로 보여준다.
- <b>은행 해킹 vs 블록체인 사례</b>:
  - 상황: 중앙 서버 방식의 위험성 설명 
  - 설명: 농협에 3000만원을 예금했는데 은행 서버가 해킹당해 모든 데이터가 삭제되면 돈이 있다는 것을 증명할 방법이 없다. 블록체인에서는 여러 곳에 동일한 장부가 분산되어 있어서 하나가 문제 생겨도 다른 곳에 기록이 남아있다. 
  - 왜 이 예시를 사용했는지: 탈중앙화의 필요성과 블록체인의 장점을 실생활 예시로 이해하기 쉽게 설명한다.

### 헷갈릴 수 있는 부분

- <b>헷갈리는 개념</b>: 블록체인과 비트코인
- <b>헷갈리는 이유</b>: 둘을 같은 개념으로 혼동하는 경우가 많다.
- <b>구분 방법</b>: 비트코인은 단순히 암호화폐일 뿐이다. 블록체인은 아이템, 소유권, 명함, 계약 등 다양한 가상자산을 관리할 수 있는 더 넓은 개념의 기술 플랫폼이다. 
- <b>헷갈리는 개념</b>: 메타버스와 VR가상현실
- <b>헷갈리는 이유</b>: VR을 메타버스와 동일하게 생각하는 경우가 있다.
- <b>구분 방법</b>: VR은 메타버스의 4가지 유형 중 하나일 뿐이다. 메타버스는 VR뿐 아니라 AR, 라이프로깅, 거울세계를 모두 포함하며, 현실과의 경제적·사회적·정보적 연결까지 포괄하는 더 넓은 개념이다.
- <b>헷갈리는 개념</b>: 언택트Untact의 의미
- <b>헷갈리는 이유</b>: 새로운 용어라 정확한 의미 파악이 어렵다.
- <b>구분 방법</b>: Contact접촉의 반대인 Un-contact비접촉로, 비대면을 의미한다.

## 1. Metaverse는 무엇의 합성어인가?

<b>Metaverse</b>는 <b>Meta</b>와 <b>Universe</b>의 합성어이다.

- <b>Meta</b>: 초월, 가상, 현실을 넘어선 것
- <b>Universe</b>: 세계, 우주

따라서 <b>Metaverse</b>는 “현실을 넘어선 가상의 세계” 또는 “현실과 연결된 확장된 디지털 세계”를 의미한다.

## 2. Metaverse는 현실과 비현실을 어떻게 연결하는가?

### 1. 공간적 연결

현실의 공간을 가상공간으로 옮기거나 확장하는 것이다.

예를 들어 현실의 교실, 회의실, 도시, 공연장을 가상세계에 구현하거나, AR처럼 현실 공간 위에 가상 정보를 덧붙이는 방식이 있다.

### 2. 정신적 연결

사용자가 아바타를 통해 가상세계 안에서 자신을 표현하고, 다른 사람들과 감정과 경험을 공유하는 것이다.

가상세계에서의 대화, 협업, 게임, 공연 경험이 현실의 감정이나 인간관계에도 영향을 줄 수 있다.

### 3. 사회적 연결

현실의 인간관계가 가상세계로 확장되는 것이다.

사람들은 메타버스 안에서 친구를 만나고, 회의나 수업을 하고, 함께 게임이나 행사를 즐기며 사회적 관계를 이어간다.

### 4. 경제적 연결

가상세계 안에서 아이템, 아바타 의상, 공간, 콘텐츠 등을 사고파는 경제 활동이 이루어지는 것이다.

가상세계의 거래가 현실의 돈이나 가치와 연결될 수 있기 때문에 현실 경제와도 관련된다.

### 5. 정보적 연결

현실의 데이터나 정보를 가상세계에 반영하는 것이다.

예를 들어 지도 앱, 디지털 트윈, 온라인 쇼핑몰, 가상 전시관처럼 현실의 정보를 디지털 공간에서 확인하고 활용할 수 있다.

- <b>포신 상하 회전</b>을 마우스 휠로 제어하는 시스템을 만들었다. Input System에 Scroll 액션을 추가하고, 이벤트 기반으로 포신의 X축 회전을 제어하며, Euler Angles로 회전 각도를 제한했다. 
- <b>레이저 빔 발사 시스템</b>을 구현했다. Line Renderer를 사용해 발사 위치에서 적중 위치까지 시각적 피드백을 제공하고, 코루틴으로 0.1초간 빔을 표시한 후 비활성화하도록 만들었다. 
- <b>성능 최적화 개념</b>인 <code>sqrMagnitude</code>와 <code>magnitude</code>의 차이를 배웠다. 루트 연산을 생략한 <code>sqrMagnitude</code>는 근사값이지만 빠르고, <code>magnitude</code>는 정확하지만 느리다. 게임에서는 대부분 <code>sqrMagnitude</code>를 사용하고, 시뮬레이션처럼 정확한 값이 필요한 경우에만 <code>magnitude</code>를 사용한다.

### 주요 개념 정리

- <b>InverseTransformPoint</b>
  - 설명: 월드 좌표를 특정 Transform의 로컬 좌표로 변환하는 함수. 부모 오브젝트의 좌표계를 기준으로 위치를 재계산한다.
  - 예시: 터렛이 탱크의 자식이므로, Raycast로 맞은 월드 좌표를 터렛의 로컬 좌표로 변환하여 터렛만 독립적으로 회전시킬 수 있다.
  - 사용되는 상황: 부모-자식 관계에서 자식만 독립적으로 움직여야 할 때
  - 헷갈릴 수 있는 점: Transform.InverseTransformPoint와 Transform.TransformPoint는 반대 기능이다. TransformPoint는 로컬 → 월드, InverseTransformPoint는 월드 → 로컬 변환이다.
- <b>Quaternion.LookRotation vs Euler Angles</b>
  - 설명: <code>Quaternion.LookRotation</code>은 특정 방향을 바라보도록 회전값을 계산하는 함수이고, <code>Euler Angles</code>는 특정 각도로 회전을 제한할 때 사용한다.
  - 예시: 터렛이 타겟을 계속 바라보려면 <code>LookRotation</code>을 사용하고, 포신의 상하 각도를 -30도\~0도로 제한하려면 <code>eulerAngles</code>를 사용한다.
  - 사용되는 상황: LookRotation은 자동 추적, Euler Angles는 회전 제한에 사용
  - 헷갈릴 수 있는 점: <code>Quaternion.RotateTowards</code>는 부드러운 회전에 사용하며, <code>Quaternion.Slerp</code>보다 일정한 속도로 회전한다. Slerp는 목표에 가까워질수록 느려진다.
- <b>sqrMagnitude vs magnitude</b>
  - 설명: <code>sqrMagnitude</code>는 벡터 크기의 제곱값(루트 미적용), <code>magnitude</code>는 실제 벡터 크기(루트 적용)
  - 예시: 거리 비교만 필요한 경우 <code>sqrMagnitude</code>로 충분하고, 실제 거리 값이 필요한 경우 <code>magnitude</code>를 사용한다.
  - 사용되는 상황: sqrMagnitude는 게임 로직, magnitude는 시뮬레이션이나 정확한 계산
  - 헷갈릴 수 있는 점: sqrMagnitude는 근사값이 아니라 정확한 제곱값이다. 다만 실제 거리가 아니므로 비교 용도로만 사용해야 한다.
- <b>Mathf.Sign</b>
  - 설명: 양수면 1, 음수면 -1, 0이면 0을 반환하는 함수
  - 예시: 마우스 휠의 스크롤 방향을 판단하여 포신을 위/아래로 회전시킬 때 사용
  - 사용되는 상황: 방향 판단이 필요한 모든 경우
- <b>OnDrawGizmos vs OnDrawGizmosSelected</b>
  - 설명: <code>OnDrawGizmos</code>는 항상 기즈모를 표시하고, <code>OnDrawGizmosSelected</code>는 오브젝트를 선택했을 때만 표시한다.
  - 예시: 공격 범위, 추적 범위를 시각화할 때 Selected를 사용하면 선택 시에만 범위가 표시된다.
  - 사용되는 상황: 디버깅용 시각화, 에디터 작업 시 위치 확인
  - 헷갈릴 수 있는 점: Gizmos는 빌드에 포함되지 않으며 에디터에서만 표시된다.

### 수업 흐름별 정리

### 1. 터렛 마우스 추적 시스템 구현

- Input System에서 마우스 포지션을 가져와 <code>Camera.ScreenPointToRay</code>로 레이를 생성한다. 
- <code>Physics.Raycast</code>로 충돌 감지를 하고, 150 범위 내에서 Train 레이어를 가진 오브젝트를 감지한다. 
- 맞은 위치(<code>hit.point</code>)를 터렛 부모의 <code>InverseTransformPoint</code>로 로컬 좌표로 변환한다. 
- 로컬 좌표의 Y값을 0으로 설정하여 터렛이 수평으로만 회전하도록 제한한다. 
- <code>Quaternion.LookRotation</code>으로 타겟 방향을 계산하고, <code>Quaternion.RotateTowards</code>로 부드럽게 회전시킨다. 

중요: 터렛은 탱크 바디와 독립적으로 회전해야 하므로 <code>localRotation</code>을 사용한다. 

### 2. 포신 마우스 휠 제어 구현

- Input System에 Scroll 액션을 추가하고, 마우스의 Scroll을 바인딩한다. 
- TankInput 스크립트에 <code>onScrollEvent</code> 이벤트를 추가한다. 
- CannonCtrl 스크립트에서 스크롤 이벤트를 구독하고, <code>OnEnable</code>/<code>OnDisable</code>에서 등록/해제한다. 
- <code>Mathf.Sign</code>으로 스크롤 방향을 판단하고, 회전 속도를 곱해 X축 회전값을 계산한다. 
- <code>Quaternion.Euler</code>로 회전을 적용한다. 

### 3. 포신 회전 각도 제한

- <code>eulerAngles</code>로 현재 회전값을 가져온다. 
- X값이 180도보다 크면 360을 빼서 음수로 변환한다 (330도 → -30도). 
- <code>Mathf.Clamp</code>로 상한(-30도)과 하한(-5도) 범위로 제한한다. 
- 제한된 값으로 새 <code>Vector3</code>를 만들어 <code>eulerAngles</code>에 적용한다. 

중요: 360도 회전 시스템에서 음수 각도를 다루려면 180도 기준으로 변환해야 계산이 편하다. 

### 4. Gizmos를 활용한 위치 표시

- <code>MyGizmo</code> 스크립트를 만들어 <code>OnDrawGizmos</code> 함수를 구현한다. 
- <code>Gizmos.color</code>로 색상을 설정하고, <code>Gizmos.DrawSphere</code>로 구체를 그린다. 
- FirePos에 MyGizmo를 붙여 발사 위치를 시각적으로 확인한다. 

### 5. 레이저 빔 시각화 구현

- Line Renderer를 사용하여 발사 위치에서 적중 위치까지 선을 그린다. 
- <code>Use World Space</code>를 체크하여 월드 좌표 사용 (로컬 변환 불필요). 
- Material은 URP Particle 셰이더를 사용하거나 Mobile/Particles/Additive를 사용한다. 
- <code>LaserBeam</code> 스크립트에서 <code>Physics.Raycast</code>로 적중 여부를 판단한다. 
- 적중 시 <code>hit.point</code>, 미적중 시 <code>ray.GetPoint(rayDistance)</code>를 사용한다. 
- 코루틴 <code>ShowRay</code>에서 0.1초 동안 빔을 표시하고 비활성화한다. 

### 6. 탱크 발사 시스템 구현

- TankInput에 <code>onFireEvent</code>를 추가하고, Fire 액션과 연결한다. 
- TankFire 스크립트를 만들어 발사 로직을 구현한다. 
- <code>nextFireTime</code>으로 발사 간격을 제어한다 (0.5초). 
- Layer Mask에 Train, Tank, Apache를 모두 설정한다. 

중요: 탱크 게임은 터렛과 포신이 독립적으로 회전하고, 회전 제한도 있어서 구현 난이도가 높다.

### 예시와 활용 사례

- <b>예시 1: 터렛의 부모 좌표계 활용</b>
  - 상황: 터렛이 탱크 바디의 자식으로 구성되어 있음
  - 설명: <code>InverseTransformPoint</code>로 월드 좌표를 터렛의 로컬 좌표로 변환하여 탱크가 회전해도 터렛은 독립적으로 타겟을 추적할 수 있다.
  - 왜 이 예시를 사용했는지: 부모-자식 관계에서 독립적인 회전을 구현하는 핵심 패턴이다.
- <b>예시 2: 360도 각도를 음수로 변환</b>
  - 상황: 포신 회전 각도를 제한할 때 330도를 -30도로 변환
  - 설명: <code>if (currentRotate.x &gt; 180) currentRotate.x -= 360</code>을 사용하여 180도 이상의 각도를 음수로 변환한다.
  - 왜 이 예시를 사용했는지: Euler Angles에서 각도 제한을 쉽게 계산하기 위한 표준 방법이다.
- <b>예시 3: sqrMagnitude로 성능 최적화</b>
  - 상황: 터렛이 움직이는지 확인할 때
  - 설명: <code>relativeVector.sqrMagnitude &gt; 0.001</code>로 체크하여 루트 연산을 생략한다.
  - 왜 이 예시를 사용했는지: 매 프레임 실행되는 코드에서 작은 최적화도 누적되면 큰 차이를 만든다.

### 헷갈릴 수 있는 부분

- <b>헷갈리는 개념</b>: rotation과 localRotation
- <b>헷갈리는 이유</b>: 언제 어느 것을 사용해야 하는지 불명확하다.
- <b>구분 방법</b>: 부모 오브젝트와 함께 회전해야 하면 <code>rotation</code>, 부모와 독립적으로 회전해야 하면 <code>localRotation</code>을 사용한다. 터렛처럼 탱크 바디와 별도로 회전해야 하는 경우 반드시 <code>localRotation</code>을 사용한다.
- <b>헷갈리는 개념</b>: Quaternion.Slerp와 Quaternion.RotateTowards
- <b>헷갈리는 이유</b>: 둘 다 부드러운 회전을 제공한다.
- <b>구분 방법</b>: <code>Slerp</code>는 목표에 가까워질수록 속도가 느려지고, <code>RotateTowards</code>는 일정한 속도로 회전한다. 일정한 속도가 필요한 경우 <code>RotateTowards</code>를 사용한다.
- <b>헷갈리는 개념</b>: eulerAngles의 180도 기준
- <b>헷갈리는 이유</b>: 270도와 -90도가 같은 회전인데 다르게 표현된다.
- <b>구분 방법</b>: Unity의 eulerAngles는 0\~360 범위이므로, 음수 각도로 작업하려면 180도 기준으로 변환해야 한다. 180도 이상이면 360을 빼서 음수로 만든다.

# Unity 오브젝트 풀링에서 List 방식과 Queue 방식 정리

## 1. 오브젝트 풀링이란?

<b>오브젝트 풀링 Object Pooling</b>은 게임 오브젝트를 필요할 때마다 <code>Instantiate</code>로 새로 만들고 <code>Destroy</code>로 없애는 대신, 미리 여러 개 만들어두고 재사용하는 방식이다.

예를 들어 총알, 폭발 이펙트, 데미지 숫자, 몬스터 같은 오브젝트는 게임 중에 자주 생성되고 사라진다. 이때 매번 생성과 삭제를 반복하면 성능 부담이 생길 수 있다.

그래서 오브젝트 풀링에서는 오브젝트를 미리 만들어두고,

```txt
필요할 때 꺼내서 사용
사용이 끝나면 비활성화 후 다시 보관
다시 필요할 때 재사용
```

하는 구조를 사용한다.

---

# 2. Queue 방식이 선호되는 이유

<code>Queue</code>는 <b>먼저 들어온 데이터가 먼저 나가는 구조</b>이다.

이를 <b>FIFO, First In First Out</b>이라고 한다.

오브젝트 풀링의 흐름과 Queue의 구조는 잘 맞는다.

```txt
Enqueue = 오브젝트를 풀에 다시 넣기
Dequeue = 오브젝트를 풀에서 꺼내기
```

예를 들어 총알 오브젝트 풀이라면,

```txt
총알을 미리 만들어 Queue에 넣어둠
발사할 때 Queue에서 하나 꺼냄
총알이 사라질 때 다시 Queue에 넣음
```

이런 식으로 관리할 수 있다.

## Queue 방식의 장점

Queue는 현재 사용 가능한 오브젝트만 보관하는 방식으로 사용할 수 있다.

그래서 필요할 때 바로 하나를 꺼낼 수 있다.

```txt
GameObjectobj=poolQueue.Dequeue();
```

List처럼 매번 비활성화된 오브젝트를 찾기 위해 전체를 반복문으로 검사할 필요가 적다.

즉, Queue 방식은 다음과 같은 경우에 좋다.

```txt
아무 오브젝트나 하나 꺼내 쓰면 되는 경우
오브젝트를 빠르게 꺼내고 다시 넣는 구조
총알, 이펙트, 데미지 텍스트처럼 자주 재사용되는 오브젝트
```

---

# 3. List 방식이 적합한 경우

<code>List</code>는 여러 오브젝트를 순서대로 저장하고, 인덱스로 접근할 수 있는 구조이다.

List 방식은 단순히 하나를 꺼내는 것보다, <b>특정 오브젝트를 찾거나 전체 오브젝트를 관리해야 할 때</b> 좋다.

예를 들어 풀 안에 있는 오브젝트 중 비활성화된 오브젝트를 직접 찾아서 사용하려면 List를 사용할 수 있다.

```txt
for (inti=0;i<poolList.Count;i++)
{
if (!poolList[i].activeSelf)
    {
returnpoolList[i];
    }
}
```

## List 방식이 어울리는 경우

```txt
특정 조건에 맞는 오브젝트를 찾아야 할 때
전체 오브젝트를 순회해야 할 때
활성화된 오브젝트와 비활성화된 오브젝트를 모두 관리해야 할 때
몬스터, NPC, UI 슬롯, 설치형 오브젝트처럼 상태 관리가 필요한 경우
```

예를 들어 모든 몬스터를 한 번에 비활성화해야 한다면 List가 편하다.

```txt
foreach (GameObjectobjinpoolList)
{
obj.SetActive(false);
}
```

# 4. 데이터 시프트란?

<b>데이터 시프트 Data Shift</b>는 List 같은 배열 기반 자료구조에서 중간이나 앞쪽 데이터를 삭제했을 때, 뒤에 있던 데이터들이 앞으로 한 칸씩 밀리는 현상을 말한다.

예를 들어 이런 List가 있다고 해보자.

```txt
List<string>list=newList<string>() {"A","B","C","D" };
```

처음 상태는 다음과 같다.

```txt
인덱스:  0   1   2   3
데이터:  A   B   C   D
```

여기서 맨 앞의 데이터를 삭제하면,

```txt
list.RemoveAt(0);
```

<code>A</code>가 사라지고 뒤에 있던 데이터들이 앞으로 당겨진다.

```txt
인덱스:  0   1   2
데이터:  B   C   D
```

즉,

```txt
B는 1번에서 0번으로 이동
C는 2번에서 1번으로 이동
D는 3번에서 2번으로 이동
```

이렇게 뒤에 있는 데이터들의 위치가 바뀌는 것이 <b>데이터 시프트</b>이다.

---

# 5. 데이터 시프트가 문제가 되는 이유

오브젝트가 적을 때는 큰 문제가 되지 않는다.

하지만 총알이나 이펙트처럼 자주 꺼내고 반납하는 오브젝트가 많아지면, List 앞쪽에서 계속 삭제하는 방식은 부담이 될 수 있다.

예를 들어 아래 코드는 비효율적일 수 있다.

```txt
list.RemoveAt(0);
```

겉으로는 맨 앞 데이터 하나만 지우는 것처럼 보이지만, 내부적으로는 뒤에 있는 데이터들을 앞으로 옮겨야 한다.

그래서 오브젝트 수가 많거나 자주 반복되는 구조에서는 성능 비용이 쌓일 수 있다.

반면 Queue는 앞에서 꺼내고 뒤에 넣는 구조가 기본이기 때문에, 오브젝트 풀링의 재사용 흐름과 잘 맞는다.

```txt
queue.Dequeue();// 앞에서 꺼냄
queue.Enqueue(obj);// 뒤에 다시 넣음
```

그래서 단순한 재사용 풀에서는 Queue 방식이 자주 선호된다.

---

# 6. List가 무조건 나쁜 것은 아니다

List 방식이 항상 나쁜 것은 아니다.

특히 List의 마지막 요소를 꺼내는 방식은 데이터 시프트가 거의 발생하지 않는다.

```txt
GameObjectobj=list[list.Count-1];
list.RemoveAt(list.Count-1);
```

이 경우에는 맨 뒤 요소를 제거하기 때문에, 뒤의 데이터를 앞으로 당기는 과정이 필요 없다.

즉, 문제는 <b>List 자체가 나쁘다</b>가 아니라, <code>RemoveAt(0)</code>처럼 앞쪽이나 중간 요소를 자주 삭제해서 데이터 시프트가 발생하는 방식이 비효율적일 수 있다는 것이다.

---

# 7. Queue와 List를 같이 쓰는 방식

실제로는 Queue와 List를 같이 쓰기도 한다.

```txt
Queue: 현재 사용 가능한 오브젝트 보관
List: 전체 오브젝트 목록 보관
```

예를 들어 이런 구조를 만들 수 있다.

```txt
privateQueue<GameObject>availablePool=newQueue<GameObject>();
privateList<GameObject>allObjects=newList<GameObject>();
```

오브젝트를 처음 만들 때는 Queue와 List에 모두 넣는다.

```txt
GameObjectobj=Instantiate(prefab);
obj.SetActive(false);

availablePool.Enqueue(obj);
allObjects.Add(obj);
```

사용할 때는 Queue에서 빠르게 꺼낸다.

```txt
GameObjectobj=availablePool.Dequeue();
obj.SetActive(true);
```

전체 초기화가 필요할 때는 List를 순회한다.

```txt
foreach (GameObjectobjinallObjects)
{
obj.SetActive(false);
}
```

이렇게 하면 Queue의 빠른 재사용 구조와 List의 전체 관리 기능을 둘 다 사용할 수 있다.

# 8. 정리

| 구분 | Queue 방식 | List 방식 |
| --- | --- | --- |
| 구조 | 먼저 들어온 것이 먼저 나감 | 인덱스로 자유롭게 접근 |
| 장점 | 꺼내고 반납하는 흐름이 단순함 | 특정 오브젝트 검색과 전체 관리가 쉬움 |
| 단점 | 특정 오브젝트 검색에는 불편함 | 앞쪽 삭제 시 데이터 시프트 발생 가능 |
| 적합한 대상 | 총알, 이펙트, 데미지 텍스트 | 몬스터, NPC, UI 슬롯, 설치형 오브젝트 |
| 사용 목적 | 아무 오브젝트나 하나 꺼내 쓰기 | 조건에 맞는 오브젝트 찾기, 전체 순회 |

# 최종 결론

오브젝트 풀링에서 <b>Queue 방식은 사용 가능한 오브젝트를 바로 꺼내고 다시 넣는 구조에 적합</b>하다. 그래서 총알, 이펙트, 데미지 텍스트처럼 자주 생성되고 사라지는 오브젝트에 많이 사용된다.

반면 <b>List 방식은 특정 오브젝트를 찾거나 전체 오브젝트를 관리해야 할 때 적합</b>하다. 몬스터, NPC, UI 슬롯처럼 상태를 검사하거나 전체를 순회해야 하는 경우에는 List가 더 편리하다.

또한 List에서 앞쪽 데이터를 삭제하면 뒤에 있는 데이터들이 앞으로 이동하는 <b>데이터 시프트</b>가 발생할 수 있다. 이 때문에 <code>RemoveAt(0)</code>처럼 앞쪽 요소를 자주 삭제하는 방식은 성능상 불리할 수 있다.

따라서 오브젝트 풀링에서는 보통 다음처럼 선택하면 된다.

```txt
단순히 꺼내 쓰고 반납하는 구조라면 Queue
특정 오브젝트 검색이나 전체 관리가 필요하다면 List
둘 다 필요하다면 Queue와 List를 함께 사용
```

즉, 오브젝트 풀링의 핵심은 자료구조를 무조건 하나로 정하는 것이 아니라, <b>오브젝트를 어떤 방식으로 재사용하고 관리할 것인지에 맞게 선택하는 것</b>이다.
