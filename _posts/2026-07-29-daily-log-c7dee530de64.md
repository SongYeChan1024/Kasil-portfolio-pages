- [x] mos.A.I.c와 DarkDock 포트폴리오 페이지를 최종 결과 중심으로 리뉴얼하기
- [x] Git 저장소와 Notion 자료를 교차 확인하여 실제 담당 범위를 명확히 정리하기
- [x] 대표 구현 스크립트와 전체 코드 열람 기능을 포트폴리오에 연결하기
- [x] GitHub Pages 배포 후 공개 환경에서 정상 동작을 검증하기
- [x] 두 프로젝트의 Notion 페이지를 최신 웹 구성과 동기화하기

## 오늘의 한 줄 요약

루시드 다이버 포트폴리오에서 확립한 구성 기준을 mos.A.I.c와 DarkDock에도 적용하고, 실제 Git 코드·커밋 근거를 연결한 완성형 프로젝트 페이지로 리뉴얼한 뒤 웹 배포와 Notion 동기화까지 완료했습니다.

## 진행한 작업

### 1. 프로젝트 자료와 담당 범위 교차 검증

- mos.A.I.c와 DarkDock의 기존 포트폴리오, Notion 문서, 원본 Git 저장소를 함께 확인했습니다.
- 커밋 기록과 실제 스크립트를 기준으로 본인이 직접 구현한 범위와 팀 공동 작업 범위를 구분했습니다.
- <b>mos.A.I.c</b>에서는 Episode 3, SoundManager, SaveManager, 컷신 및 플레이 흐름을 대표 작업으로 정리했습니다.
- <b>DarkDock</b>에서는 Enemy AI, 아이템, 3개 스테이지 레벨 디자인, 오일 웅덩이와 경비견 관련 수정 사항을 대표 작업으로 정리했습니다.
- 확인한 직접 커밋은 mos.A.I.c 38개, DarkDock 34개이며 각 구현 자료에서 근거를 확인할 수 있도록 구성했습니다.

### 2. mos.A.I.c 포트폴리오 페이지 리뉴얼

- 프로젝트 소개, 담당 역할, 핵심 구현, 트러블슈팅 순서로 정보 구조를 재정리했습니다.
- Episode 3 진행 구조와 사운드·저장 시스템을 탭으로 나누어 빠르게 비교할 수 있도록 만들었습니다.
- 기획 의도와 실제 구현 결과가 함께 보이도록 설명과 코드 자료를 연결했습니다.

### 3. DarkDock 포트폴리오 페이지 리뉴얼

- Enemy AI, 아이템, 레벨 디자인과 대표 트러블슈팅을 중심으로 페이지를 재구성했습니다.
- 단순 기능 나열이 아니라 문제 상황, 판단 기준, 구현 결과가 이어지도록 사례형 설명으로 정리했습니다.
- 각 기능의 본인 담당 범위와 팀 작업 범위를 명확하게 표시했습니다.

### 4. 전체 스크립트 열람 기능 추가

- 두 프로젝트의 원본 Git 저장소에서 실제 스크립트를 가져와 읽기 전용 코드 자료로 연결했습니다.
- 구현 탭마다 대표 파일과 역할 설명, 담당 범위, 관련 커밋 링크를 함께 배치했습니다.
- 페이지 내부의 <b>전체 스크립트 보기</b> 버튼으로 원본 코드를 크게 열람할 수 있도록 공통 코드 뷰어를 구현했습니다.
- 공통 스타일과 뷰어 로직을 재사용할 수 있도록 별도 CSS와 JavaScript 모듈로 분리했습니다.

### 5. 검증·커밋·배포

- UTF-8 문자 인코딩, HTML 구조, JavaScript 문법, 파일 경로와 링크 존재 여부를 점검했습니다.
- <code>git diff --check</code>와 정적 검사를 통과한 뒤 변경 사항을 커밋하고 <code>main</code> 브랜치에 푸시했습니다.
- 커밋: [3cdc65f — Expand Mosaic and DarkDock portfolio pages](https://github.com/SongYeChan1024/Kasil-portfolio-pages/commit/3cdc65f)
- GitHub Pages 공개 주소에서 두 페이지 모두 HTTP 200 응답과 정상 표시를 확인했습니다.
- 작업 범위 밖의 미추적 파일은 커밋에 포함하지 않고 그대로 보존했습니다.

### 6. Notion 프로젝트 페이지 동기화

- mos.A.I.c와 DarkDock의 Notion 페이지에 핵심 작업, 트러블슈팅, 담당 범위와 근거를 최신 내용으로 반영했습니다.
- 웹 포트폴리오와 Notion에서 같은 흐름으로 내용을 확인할 수 있도록 제목과 설명 구조를 맞췄습니다.
- <b>전체 스크립트 보기</b>, <b>완성형 포트폴리오</b>, <b>담당 범위와 근거</b> 항목이 정상 반영되었는지 다시 확인했습니다.

## 오늘의 핵심 결정

- 프로젝트 페이지는 기능 목록이 아니라 <b>기획 의도 → 구현 → 문제 해결 → 검증 결과</b>의 흐름으로 구성합니다.
- 담당 범위는 설명만으로 주장하지 않고 실제 Git 코드와 커밋 링크를 근거로 제시합니다.
- 전체 코드는 페이지 안에서 확인할 수 있게 하되, 원본 저장소와 커밋으로 다시 추적할 수 있도록 연결합니다.
- 공통 UI와 코드 뷰어는 재사용 가능한 구조로 분리하여 이후 프로젝트 업데이트에도 활용합니다.
- 다른 작업의 미추적 파일은 임의로 정리하거나 커밋하지 않습니다.

## 트러블슈팅 및 검증

- 기존 페이지의 오래된 구성과 인코딩 문제 가능성을 줄이기 위해 UTF-8 기준으로 페이지 구조를 다시 정리했습니다.
- 코드 자료가 설명과 분리되어 보이지 않도록 각 구현 탭에 파일 역할·담당 범위·커밋 근거를 함께 배치했습니다.
- 로컬 정적 검사뿐 아니라 실제 GitHub Pages 공개 주소에서도 로딩 상태를 확인했습니다.

- 포트폴리오에서는 “무엇을 했다”보다 <b>왜 설계했고 어떤 코드로 구현했으며 어떤 근거가 남아 있는지</b>를 한 흐름으로 보여주는 것이 중요합니다.

- 웹과 Notion의 정보 구조를 맞추면 어느 쪽을 먼저 보더라도 프로젝트의 핵심을 동일하게 전달할 수 있습니다.
