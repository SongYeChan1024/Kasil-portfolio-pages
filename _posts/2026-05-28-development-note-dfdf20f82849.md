<b>Unity UI 설정 및 Canvas Scaler 수업</b> 2026-05-28


## 요약


### 오늘 수업 핵심 요약

- Unity에서 <b>CanvasScaler</b> 컴포넌트의 UI Scale Mode 옵션들을 배우고, 모바일 게임 개발에 적합한 <b>Scale With Screen Size</b> 모드를 실습했습니다. 
- <b>Firebase 연동 준비</b> 작업으로 Android 빌드 설정과 Package Name 설정 방법을 학습했습니다. 
- 메인 씬의 UI 레이아웃을 설계하고, <b>앵커(Anchor) 시스템</b>을 활용해 다양한 해상도에서도 UI 위치가 고정되도록 반응형 UI를 구현했습니다. 
- LittleWarS 에셋팩을 활용해 게임 스타트 버튼, 상점 버튼, 유저 버튼 등의 UI 요소를 배치하고 디자인했습니다. 
- 이번 수업은 Firebase 데이터베이스 연동을 위한 기초 작업으로, 향후 메인 씬, 상점 씬, 유저 씬, 게임 씬 총 4개의 씬을 제작할 예정입니다. 

### 주요 개념 정리

- <b>CanvasScaler - UI Scale Mode</b>
  - 설명: Canvas 내 UI 요소들이 화면 크기 변화에 따라 어떻게 스케일링될지 결정하는 설정 
  - 사용되는 상황: 다양한 해상도의 디바이스를 지원하는 모바일/PC 게임 개발 시
  - 헷갈릴 수 있는 점: 세 가지 모드(Constant Pixel Size, Scale With Screen Size, Constant Physical Size)의 차이를 명확히 이해해야 함

| 모드 | 의미 | 사용 상황 |
| --- | --- | --- |
| Constant Pixel Size | UI가 항상 지정된 픽셀 크기 유 |  |
| Scale With Screen Size | 기준 해상도 대비 |  |
| Constant Physical Size | 실제 물리적 크기(인치/cm) 유지 |  |

- <b>Screen Match Mode</b>
  <ul>
  <li>
  설명: Scale With Screen Size 모드에서 가로(Width)와 세로(Height) 중 어느 쪽을 기준으로 스케일을 맞출지 결정하는 옵션 
  </li>
  <li>
  예시: 

  - Match Width or Height: 슬라이더 0\~1로 조절 (가로형 게임은 1/Height, 세로형 게임은 0/Width) 
  - Expand: UI가 잘리지 않도록 캔버스를 확장 (여백 발생 가능) 
  - Shrink: UI를 화면 안에 강제로 축소 (UI가 작아지는 문제로 실무에서 거의 사용 안 함) 
  </li>
  </ul>
- <b>Anchor(앵커)</b>
  - 설명: UI 요소의 위치를 부모 요소의 특정 지점에 고정시키는 시스템
  - 사용되는 상황: 해상도가 변경되어도 UI 위치가 올바르게 유지되어야 할 때
  - 헷갈릴 수 있는 점: 앵커를 설정하지 않고 Middle Center만 사용하면 해상도 변경 시 UI 위치가 엉망이 됨 
- <b>Screen Space - Camera</b>
  - 설명: Canvas의 Render Mode 중 하나로, 카메라를 통해 UI를 렌더링하는 방식 
  - 사용되는 상황: UI에 카메라 효과를 적용하거나 3D 공간에서 UI를 표현할 때
  - 예시: Main Camera를 Render Camera로 지정
- <b>Firebase Package Name</b>
  - 설명: Firebase와 Unity 앱을 연결하기 위한 고유 식별자 
  - 예시: com.EliseCompany.FireBasePro\_01 
  - 사용되는 상황: Firebase 데이터베이스를 Unity 프로젝트에 연동할 때 필수
  - 헷갈릴 수 있는 점: Override Default Package Name을 체크 해제 후 재체크해야 변경사항이 적용됨 

### 수업 흐름별 정리

### 1. 프로젝트 설정 및 Firebase 준비

- 설명: 눈 피하기 게임 제작을 위한 기본 스펙 정리 및 Firebase 연동 준비 
- 게임 스펙:
  - 가로 이동 플레이어
  - 위에서 떨어지는 눈 피하기
  - 체력 100, 눈 맞을 때 데미지 20 (5번 맞으면 게임 오버) 
  - 게임 재화: 코인, 스코어, 플레이어 캐릭터 종류 (5\~6가지) 
- 중요: Firebase를 사용해 게임 점수, 코인, 선택한 캐릭터 정보를 데이터베이스에 저장 

### 2. Android 빌드 설정

- 설명: Firebase 연동을 위해 Android 플랫폼 설정 필수 
- 중요한 이유: Firebase 앱과 Unity를 연결하려면 Android Build Support가 설치되어 있어야 함
- 실습 순서:
  1. File > Build Settings 열기 
  2. Player Settings 클릭 
  3. Android 탭으로 이동 
  4. Other Settings에서 Override Default Package Name 체크 
  5. Company Name과 Product Name 설정 (예: EliseCompany, FireBasePro\_01) 
  6. Package Name 복사 후 메모장에 저장 (Firebase 설정 시 사용) 

### 3. Canvas 및 Camera 설정

- 설명: UI를 화면에 표시하기 위한 기본 Canvas 설정 
- 실습 내용:
  - Game View를 Full HD 1920x1080으로 설정 
  - Canvas의 Render Mode를 Screen Space - Camera로 변경 
  - Main Camera를 Render Camera에 할당 
  - Main Camera의 Background를 밝은 노란색(FFCO)으로 변경 
- 중요: 2D 프로젝트에서는 Main Camera의 Projection이 Orthographic으로 설정됨 

### 4. CanvasScaler 설정

- 설명: 반응형 UI를 만들기 위한 CanvasScaler 설정 
- 실습 내용:
  - UI Scale Mode: Scale With Screen Size 선택 
  - Reference Resolution: 1920 x 1080 (Full HD) 
  - Screen Match Mode: Expand 
- 중요: 대부분의 상용 게임(99%)은 Scale With Screen Size 모드를 사용 

### 5. 메인 씬 UI 제작

- 설명: 게임 시작, 상점, 유저 버튼 및 닉네임 표시 영역 제작 
- 제작한 UI 요소:
  - 게임 스타트 버튼 (Y: -300) 
  - 상점 버튼 (Top Right 앵커, X: -70, Y: -30) 
  - 유저 버튼 (상점 버튼 아래) 
  - 닉네임 패널 (Top Middle 앵커, Y: -80, Width: 300, Height: 100) 
  - 유닛 이미지 (Middle Center, Y: 100, 250x250) 
- 중요: LittleWarS Asset Pack의 Bar Front 스프라이트를 버튼 Source Image로 사용 

### 6. 앵커를 활용한 반응형 UI 배치

- 설명: 해상도가 변경되어도 UI 위치가 고정되도록 앵커 설정 
- 예시:
  - 상점 버튼: Top Right 앵커로 오른쪽 상단에 고정 
  - 닉네임 패널: Top Middle 앵커로 상단 중앙에 고정 
  - 게임 스타트 버튼: Middle Center 앵커 사용
- 중요: 앵커를 설정하지 않으면 해상도 변경 시 UI가 엉망이 됨 

### 실습 / 작업 순서

### Android Build Support 설치 (미설치자)

1. Unity Hub 열기
2. Unity 2022 버전 옆의 설정(⚙️) 클릭
3. 모듈 추가(Add Modules) 선택 
4. Android Build Support 체크 
5. 설치 완료

### Canvas 및 CanvasScaler 설정

1. Hierarchy에서 UI > Image 생성 (Canvas 자동 생성됨)
2. Game View를 Full HD 1920x1080으로 설정 
3. Canvas 선택 > Render Mode를 Screen Space - Camera로 변경 
4. Main Camera를 Render Camera 필드에 드래그 앤 드롭 
5. Canvas Scaler 컴포넌트에서 UI Scale Mode를 Scale With Screen Size로 설정 
6. Reference Resolution: 1920 x 1080 입력 
7. Screen Match Mode를 Expand로 설정 

### 메인 씬 UI 버튼 제작

1. Canvas 우클릭 > UI > Legacy > Button 생성 
2. 버튼 이름을 GameStart\_btn으로 변경 
3. 버튼 위치: Y값 -300 설정 
4. 버튼 크기: Width 200, Height 50 (나중에 230 x 90으로 조정) 
5. 자식 Text 오브젝트에서 텍스트를 "게임 시작"으로 변경 
6. Font Size 30, Bold 스타일 적용 
7. LittleWarS > Sprites에서 Bar Front 스프라이트를 버튼의 Source Image로 설정 
8. 같은 방식으로 Shop\_btn과 User\_btn 생성 

### 닉네임 및 캐릭터 이미지 배치

1. Canvas 우클릭 > UI > Panel 생성, 이름을 Nickname\_Panel로 변경 
2. 앵커를 Top Middle로 설정 
3. Y: -80, Width: 300, Height: 100 설정 
4. Bar Front 스프라이트를 Source Image로 설정, Alpha 200으로 조정 
5. Nickname\_Panel 우클릭 > UI > Text 생성, "닉네임"으로 텍스트 설정 
6. Canvas 우클릭 > UI > Image 생성, Unit\_Image로 이름 변경 
7. Middle Center 앵커, Y: 100, 크기 250 x 250 (나중에 Width 320으로 조정) 
8. LittleWarS > Sprites > Characters에서 BS\_Idle 스프라이트 할당 

### 씬 저장 및 이름 변경

1. Ctrl + S로 씬 저장 
2. Hierarchy에서 씬 이름 우클릭 > Select Scene Asset 
3. Project 창에서 씬 이름을 "Main\_Scene"으로 변경

### 헷갈릴 수 있는 부분

- 헷갈리는 개념: Override Default Package Name 체크박스 
- 헷갈리는 이유: 체크만 하면 되는 것이 아니라, 체크 해제 후 다시 체크해야 Package Name이 정상 반영됨
- 구분 방법: Company Name과 Product Name 변경 후 반드시 체크 해제 → 재체크 수행
- 헷갈리는 개념: Panel vs Image
- 헷갈리는 이유: 닉네임 영역을 만들 때 Panel을 사용했지만, 결과적으로 Image와 동일한 기능
- 구분 방법: Panel은 기본적으로 Background 이미지가 있는 컨테이너, Image는 단순 이미지 표시 용도
- 헷갈리는 개념: Anchor 설정 안 함 vs Middle Center만 사용
- 헷갈리는 이유: Middle Center도 앵커처럼 보이지만, 해상도 변경 시 UI가 엉망이 됨 
- 구분 방법: Top Right, Top Middle 등 명확한 앵커 포인트를 설정해야 반응형 UI 구현 가능

### 주요 개념 정리

- <b>ScriptableObject</b>
  - 설명: Unity에서 대량의 데이터를 저장하기 위한 데이터 컨테이너로, MonoBehaviour와 달리 GameObject에 붙지 않고 Project 창에 에셋 파일로 존재합니다.
  - 예시: 캐릭터 데이터, 아이템 정보, 스킬 데이터, 몬스터 능력치 등
  - 사용되는 상황: 같은 구조의 데이터를 여러 개 만들어야 할 때, 코드 수정 없이 Inspector에서 값을 관리하고 싶을 때
  - 헷갈릴 수 있는 점: 플레이어 진행 상황 같은 저장 데이터에는 부적합하며, 에디터에서는 값이 유지되지만 빌드된 게임에서는 초기화됩니다.
- <b>UnityMainThreadDispatcher</b>
  - 설명: Firebase의 백그라운드 스레드 콜백을 Unity의 메인 스레드로 전달해주는 중재자 역할을 하는 패키지
  - 사용되는 상황: Firebase 로그인, 데이터베이스 연동 등 백그라운드 작업의 결과를 Unity UI에 반영해야 할 때
  - 헷갈릴 수 있는 점: Unity UI와 GameObject 조작은 반드시 메인 스레드에서만 가능하므로, Firebase에서 직접 UI를 건드리면 크래시가 발생합니다.
- <b>Newtonsoft.Json (</b>`Json.NET`<b>)</b>
  - 설명: Firebase Realtime Database와 Firestore에서 데이터를 주고받을 때 JSON 직렬화를 수행하는 패키지

### 헷갈릴 수 있는 부분

- 헷갈리는 개념: ScriptableObject는 저장용인가?
- 헷갈리는 이유: 에디터에서는 값이 유지되지만, 빌드된 게임에서는 수정값이 초기화됨
- 구분 방법: ScriptableObject는 <b>기본 설정 데이터</b>용이고, 플레이어 진행 상황은 PlayerPrefs, JSON, Firebase 등 저장 시스템 사용
- 헷갈리는 개념: Mathf.Clamp vs Mathf.Clamp01
- 헷갈리는 이유: 이름이 비슷하지만 사용법이 다름
- 구분 방법: Clamp는 (값, 최소, 최대) 3개 인자 필요, Clamp01은 무조건 0\~1 사이로 제한
- 헷갈리는 개념: Firebase 연동 시 두 패키지가 모두 필요한 이유
- 헷갈리는 이유: UnityMainThreadDispatcher와 Newtonsoft.Json의 역할이 명확히 구분되지 않음
- 구분 방법: UnityMainThreadDispatcher는 <b>스레드 전환</b>(백그라운드→메인), Newtonsoft.Json은 <b>데이터 형식 변환</b>(객체↔JSON)

### 주요 개념 정리

<b>ScriptableObject</b>

- 설명: Unity에서 대량의 데이터를 저장하기 위한 데이터 컨테이너로, MonoBehaviour와 달리 GameObject에 붙지 않고 Project 창에 에셋 파일로 존재합니다.
- 예시: 캐릭터 데이터, 아이템 정보, 스킬 데이터, 몬스터 능력치 등
- 사용되는 상황: 같은 구조의 데이터를 여러 개 만들어야 할 때, 코드 수정 없이 Inspector에서 값을 관리하고 싶을 때
- 헷갈릴 수 있는 점: 플레이어 진행 상황 같은 저장 데이터에는 부적합하며, 에디터에서는 값이 유지되지만 빌드된 게임에서는 초기화됩니다.

<b>UnityMainThreadDispatcher</b>

- 설명: Firebase의 백그라운드 스레드 콜백을 Unity의 메인 스레드로 전달해주는 중재자 역할을 하는 패키지
- 사용되는 상황: Firebase 로그인, 데이터베이스 연동 등 백그라운드 작업의 결과를 Unity UI에 반영해야 할 때
- 헷갈릴 수 있는 점: Unity UI와 GameObject 조작은 반드시 메인 스레드에서만 가능하므로, Firebase에서 직접 UI를 건드리면 크래시가 발생합니다.

<b>Newtonsoft.Json (</b>`Json.NET`<b>)</b>

- 설명: Firebase Realtime Database와 Firestore에서 데이터를 주고받을 때 JSON 직렬화를 수행하는 패키지
- 사용되는 상황: 게임 데이터(int, float, string)를 바이트 단위로 변환하여 서버와 통신할 때

<b>Kinematic Rigidbody2D</b>

- 설명: 물리 효과는 받지 않지만 스크립트를 통해 제어 가능한 Rigidbody 타입
- 예시: 일정한 속도로 떨어지는 눈, 아이템

<b>카메라 영역 제한 (Camera Limited)</b>

- 설명: 플레이어가 카메라 뷰포트(Viewport) 밖으로 벗어나지 못하도록 제한하는 기능
- 구현 방식: 월드 좌표를 뷰포트 좌표(0\~1)로 변환 → Mathf.Clamp01로 제한 → 다시 월드 좌표로 변환

### 1. ScriptableObject 이론 학습

- 설명: MonoBehaviour와의 차이점, 사용 이유, 장단점을 배웠습니다.

### 헷갈릴 수 있는 부분

- 헷갈리는 개념: ScriptableObject는 저장용인가?
- 헷갈리는 이유: 에디터에서는 값이 유지되지만, 빌드된 게임에서는 수정값이 초기화됨
- 구분 방법: ScriptableObject는 <b>기본 설정 데이터</b>용이고, 플레이어 진행 상황은 PlayerPrefs, JSON, Firebase 등 저장 시스템 사용
- 헷갈리는 개념: Mathf.Clamp vs Mathf.Clamp01
- 헷갈리는 이유: 이름이 비슷하지만 사용법이 다름
- 구분 방법: Clamp는 (값, 최소, 최대) 3개 인자 필요, Clamp01은 무조건 0\~1 사이로 제한
- 헷갈리는 개념: Firebase 연동 시 두 패키지가 모두 필요한 이유
- 헷갈리는 이유: UnityMainThreadDispatcher와 Newtonsoft.Json의 역할이 명확히 구분되지 않음
- 구분 방법: UnityMainThreadDispatcher는 <b>스레드 전환</b>(백그라운드→메인), Newtonsoft.Json은 <b>데이터 형식 변환</b>(객체↔JSON)

# ScriptableObject

## ScriptableObject란?

<b>ScriptableObject</b>는 Unity에서 사용하는 <b>데이터 저장용 에셋</b>이야.

일반적인 스크립트인 <code>MonoBehaviour</code>는 GameObject에 붙어서 동작하지만, <code>ScriptableObject</code>는 GameObject에 붙지 않고 <b>Project 창에 에셋 파일로 만들어서 사용하는 데이터 보관함</b>이라고 보면 돼.

쉽게 말하면,

```txt
MonoBehaviour
→ 게임 오브젝트에 붙어서 움직임, 충돌, 입력 같은 동작을 처리함

ScriptableObject
→ 캐릭터, 아이템, 스킬, 스테이지 같은 데이터를 저장함
```

## MonoBehaviour와 ScriptableObject 차이

| 구분 | MonoBehaviour | ScriptableObject |
| --- | --- | --- |
| 역할 | 동작 처리 | 데이터 저장 |
| 위치 | GameObject에 컴포넌트로 붙음 | Project 창에 Asset으로 존재 |
| 사용 예시 | 이동, 공격, 충돌, UI 제어 | 아이템 정보, 캐릭터 정보, 스킬 정보 |
| 씬 필요 여부 | 씬 안에 GameObject가 필요함 | 씬에 없어도 사용 가능 |
| 재사용성 | 오브젝트마다 따로 가질 수 있음 | 여러 오브젝트가 같은 데이터 공유 가능 |

# 왜 사용하는가?

ScriptableObject를 사용하면 <b>데이터와 기능을 분리</b>할 수 있어.

예를 들어 아이템 데이터가 있다고 해보자.

```txt
아이템 이름
아이템 설명
아이템 아이콘
가격
공격력
방어력
```

이런 값을 코드 안에 직접 적으면 수정하기 불편해져.

```txt
itemName="철검";
price=100;
attackPower=10;
```

아이템이 많아질수록 코드가 복잡해지고, 값을 바꿀 때마다 스크립트를 수정해야 해.

하지만 ScriptableObject를 쓰면 아이템마다 별도의 에셋을 만들어서 Inspector에서 값을 관리할 수 있어.

```txt
IronSword.asset
WoodShield.asset
FirePotion.asset
IceSkill.asset
```

이렇게 하면 코드 수정 없이 Unity 에디터에서 데이터를 바꿀 수 있어.

# ScriptableObject를 쓰기 좋은 경우

| 사용 대상 | 이유 |
| --- | --- |
| 캐릭터 데이터 | 이름, 체력, 속도, 공격력 관리 |
| 아이템 데이터 | 이름, 설명, 가격, 아이콘 관리 |
| 스킬 데이터 | 데미지, 쿨타임, 이펙트 관리 |
| 몬스터 데이터 | 체력, 공격력, 이동속도 관리 |
| 스테이지 데이터 | 난이도, 제한 시간, 등장 오브젝트 관리 |
| 대사 데이터 | NPC 이름, 대사 내용, 조건 관리 |

즉, <b>같은 구조의 데이터를 여러 개 만들어야 할 때</b> ScriptableObject가 잘 맞아.

# 기본 코드 예시

아이템 데이터를 ScriptableObject로 만든다면 이렇게 작성할 수 있어.

```txt
usingUnityEngine;

[CreateAssetMenu(fileName="ItemData",menuName="Game Data/Item Data")]
publicclassItemData :ScriptableObject
{
publicstringitemName;
publicstringdescription;
publicSpriteicon;

publicintprice;
publicintattackPower;
publicintdefensePower;
}
```

여기서 중요한 부분은 이거야.

```txt
[CreateAssetMenu(fileName="ItemData",menuName="Game Data/Item Data")]
```

이 코드를 넣으면 Unity에서 다음 경로로 에셋을 만들 수 있어.

```txt
Project 창 우클릭
→ Create
→ Game Data
→ Item Data
```

그러면 <code>ItemData</code>라는 데이터 에셋을 여러 개 만들 수 있어.

# 사용하는 쪽 코드 예시

ScriptableObject를 만든 뒤에는 다른 스크립트에서 참조해서 사용할 수 있어.

```txt
usingUnityEngine;

publicclassItemViewer :MonoBehaviour
{
    [SerializeField]privateItemDataitemData;

privatevoidStart()
    {
Debug.Log("아이템 이름: "+itemData.itemName);
Debug.Log("아이템 설명: "+itemData.description);
Debug.Log("아이템 가격: "+itemData.price);
    }
}
```

이렇게 하면 <code>ItemViewer</code>는 직접 데이터를 가지고 있는 게 아니라, <code>ItemData</code> 에셋을 읽어서 사용하는 구조가 돼.

```txt
ItemData
→ 실제 아이템 정보 저장

ItemViewer
→ ItemData를 읽어서 화면에 표시하거나 사용
```

# 장점

## 1. 데이터 관리가 편해짐

코드 안에 값을 직접 적지 않고, 에셋으로 관리할 수 있어.

```txt
코드 수정 없이 Inspector에서 값 변경 가능
```

## 2. 재사용이 쉬움

여러 오브젝트가 같은 ScriptableObject를 참조할 수 있어.

예를 들어 여러 몬스터가 같은 <code>MonsterData</code>를 사용하면, 하나의 데이터만 수정해도 그 데이터를 참조하는 몬스터들이 같은 값을 사용하게 돼.

## 3. 코드가 깔끔해짐

데이터는 ScriptableObject에 두고, 동작은 MonoBehaviour에서 처리하면 구조가 깔끔해져.

```txt
데이터 담당: ScriptableObject
동작 담당: MonoBehaviour
```

## 4. 밸런스 조정이 쉬움

캐릭터 체력, 아이템 가격, 스킬 데미지 같은 값을 코드 수정 없이 Inspector에서 바꿀 수 있어.

게임 밸런스를 조정할 때 특히 편해.

# 주의할 점

ScriptableObject는 보통 <b>기본 데이터</b>를 저장하는 데 사용해.

하지만 플레이어의 진행 상황처럼 계속 바뀌는 저장 데이터에는 조심해서 써야 해.

예를 들어 이런 데이터는 ScriptableObject보다 저장 시스템을 따로 쓰는 게 좋아.

| 데이터 | 추천 방식 |
| --- | --- |
| 플레이어 현재 돈 | 저장 시스템 |
| 최고 점수 | 저장 시스템 |
| 클리어 여부 | 저장 시스템 |
| 구매한 아이템 목록 | 저장 시스템 |
| 캐릭터 기본 능력치 | ScriptableObject |
| 아이템 기본 정보 | ScriptableObject |
| 스킬 기본 정보 | ScriptableObject |

즉, ScriptableObject는 <b>설계된 기본값을 담는 데이터 파일</b>에 가깝고, 플레이어별 저장 정보는 <code>PlayerPrefs</code>, <code>JSON 저장</code>, <code>Firebase</code>, 서버 DB 같은 방식을 쓰는 게 더 적절해.

# 정리

ScriptableObject는 Unity에서 <b>데이터를 에셋으로 만들어 관리하는 기능</b>이야.

한 문장으로 정리하면:

> <b>ScriptableObject는 캐릭터, 아이템, 스킬, 몬스터, 스테이지 같은 기본 데이터를 코드와 분리해서 관리하는 Unity의 데이터 에셋이다.</b>

가장 중요한 구분은 이거야.

```txt
움직이고 행동하는 기능
→ MonoBehaviour

변하지 않는 기본 데이터
→ ScriptableObject

플레이어별로 저장해야 하는 데이터
→ 저장 시스템
```

이렇게 나누면 프로젝트 구조가 훨씬 깔끔해져.

데이터가 서랍별로 정리되는 느낌이라, 나중에 기능이 늘어나도 코드가 덜 엉켜.
