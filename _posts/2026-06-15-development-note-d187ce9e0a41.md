## 1. 프로젝트 목표 정리

본 문서는 《침몽도시: 루시드 다이버》의 컨셉 기획을 실제 제작 가능한 일정과 작업 단위로 전환하기 위한 PM 관리 문서이다.

PM의 역할은 프로젝트의 방향을 새로 정하는 것이 아니라, 팀이 합의한 방향이 실제 결과물로 완성될 수 있도록 목표, 역할, 일정, 업무, 리스크, 완료 기준을 정리하고 관리하는 것이다.

| 항목 | 내용 |
| --- | --- |
| 프로젝트 이름 | 《침몽도시: 루시드 다이버》 |
| 장르 | 모바일 2.5D 실시간 협동 익스트랙션 슈팅 RPG |
| 핵심 한 줄 설명 | 더 깊이 들어가 보상을 노릴 것인가, 지금 가진 것을 지키기 위해 탈출할 것인가 |
| 개발 기간 | 2026.06.11 \~ 2026.07.28 |
| 최종 목표 | 모바일 환경에서 2명의 플레이어가 같은 침몽도시 전장에 진입해 침식체와 협동 전투를 벌이고, 심상기물을 회수한 뒤 탈출하는 핵심 경험 구현 |
| 핵심 플레이 루프 | 진입 → 이동 → 전투 → 회수 → 탈출 → 결과 확인 |
| PM 관리 방향 | 리소스와 로드맵을 기준으로 제작 범위, 일정, 담당자, 완료 기준, 리스크를 관리한다 |

### 프로젝트 목표 문장

이번 프로젝트의 목표는 《침몽도시: 루시드 다이버》의 전체 기획을 한 번에 완성하는 것이 아니라, 실제로 플레이 가능한 핵심 루프를 구현하는 것이다.

화려한 확장 기능보다 <b>진입 → 이동 → 전투 → 회수 → 탈출 → 결과 확인</b> 흐름이 끊기지 않는 것을 우선하며, 이후 제한시간, 안전 금고, 2인 협동 전투를 단계적으로 붙여 MVP 완성도를 높인다.

## 3. 핵심 기능과 제외 기능

PM은 하고 싶은 기능과 반드시 구현해야 하는 기능을 구분한다.

이번 프로젝트에서는 MVP 완성을 위해 기능을 Must / Should / Could / Won’t로 분리한다.

### Must: 반드시 구현해야 하는 기능

| 기능 | 이유 |
| --- | --- |
| 플레이어 이동 | 모든 플레이의 기본 |
| 조준 및 기본 공격 | 슈팅 전투 검증 필수 |
| 적 추적 AI | 침식체 위협 구조 검증 |
| 아이템 획득 | 익스트랙션 회수 구조의 핵심 |
| 탈출 지점 | 보상을 지키고 나가는 판단의 핵심 |
| 결과창 | 플레이 결과 확인 필수 |
| 테스트 맵 1개 | 핵심 루프 검증 공간 필요 |
| 기본 UI | 체력, 마나, 제한시간, 회수품 상태 확인 필요 |

### Should: 가능하면 구현해야 하는 기능

| 기능 | 이유 |
| --- | --- |
| 제한시간 시스템 | 욕심과 탈출 판단 강화 |
| 마나 시스템 | 사격과 스킬 자원 관리 구조 확인 |
| 각성 보존 슬롯 | 실패 시 손실 부담 완화 |
| 중형 침식체 | 피할지 싸울지 선택하는 전투 구조 검증 |
| 1\~2인 멀티플레이 | 협동 익스트랙션 장르 정체성 검증 |
| 탈출 지점 2개 | 탈출 루트 선택 가능성 제공 |

### Could: 시간이 남으면 추가할 기능

| 기능 | 이유 |
| --- | --- |
| 보스 고유 패턴 추가 | 전투 완성도 상승 |
| 지원 캐릭터 호출 | 캐릭터 편성 재미 강화 |
| 간단한 연출 컷인 | 서브컬처 RPG 분위기 강화 |
| 추가 아이템 / 회수품 | 반복 플레이 동기 강화 |
| 사운드 / 이펙트 폴리싱 | 발표 완성도 상승 |

### Won’t: 이번 버전에서 제외할 기능

| 기능 | 제외 이유 |
| --- | --- |
| 4인 멀티플레이 | 1\~2인 안정화가 우선 |
| 루시드 공명 시스템 | 협동 확장 기능이므로 MVP 이후 검토 |
| 복잡한 제작 / 강화 / 경제 시스템 | 핵심 루프 검증 이후 확장 |
| 다수 맵 | 맵 1개의 완성도 우선 |
| 캐릭터 간 상호 대사 | MVP 핵심 기능 아님 |
| 대규모 보스 레이드 | 현재 기간과 리소스 대비 부담 큼 |
| 가챠 BM | 현재 방향에서 제외된 요소 |

## 5. 업무 보드 관리 방식

업무는 기능 단위로 쪼개고, 각 작업마다 담당자, 마감일, 우선순위, 완료 기준을 기록한다.

| 상태 | 의미 |
| --- | --- |
| Backlog | 언젠가 해야 할 일 |
| To Do | 이번 단계에서 해야 할 일 |
| In Progress | 작업 중 |
| Review | 확인 필요 |
| Done | 완료 |
| Blocked | 막힌 일 |

### 업무 카드 양식

```txt
작업명:
담당자:
마감일:
우선순위:
상태:

작업 내용:
-

완료 기준:
-
-
-

필요 리소스:
-

메모 / 이슈:
-
```

### 예시 업무 카드

```txt
작업명: 최소 플레이 루프 구현
담당자: 개발 담당 / PM 확인
마감일: 2026.06.24
우선순위: Must
상태: To Do

작업 내용:
- 테스트 맵에서 플레이어 이동 구현
- 기본 공격 구현
- 적 1종 추적 AI 구현
- 아이템 1종 획득 구현
- 탈출 지점 구현
- 결과창 출력 구현

완료 기준:
- 플레이어가 맵에 진입한다.
- 플레이어가 이동하고 적을 공격할 수 있다.
- 적이 플레이어를 추적한다.
- 플레이어가 아이템을 획득한다.
- 탈출 지점에 도착하면 결과창이 출력된다.
- 위 흐름이 1회 이상 끊기지 않고 반복 가능하다.

필요 리소스:
- 테스트 맵
- 플레이어 임시 모델 또는 프리팹
- 적 임시 프리팹
- 아이템 임시 프리팹
- 결과창 UI
```

## 6. 매일 확인해야 할 것

PM은 매일 팀원들의 진행 상황을 짧게 확인하고, 막힌 문제를 따로 기록한다.

회의는 길게 하기보다 진행 상황, 오늘 할 일, 블로커를 확인하는 방식으로 운영한다.

### 일일 체크 질문

1. 어제 무엇을 완료했는가?
2. 오늘 무엇을 진행할 것인가?
3. 현재 막힌 문제가 있는가?
4. 일정에 영향을 줄 변경 사항이 있는가?

## 7. 리스크 관리

PM은 일정이 터진 뒤에 수습하는 사람이 아니라, 터지기 전에 위험 신호를 발견하는 사람이다.

아래 항목은 프로젝트 진행 중 우선적으로 관리해야 할 리스크이다.

| 리스크 | 영향 | 대응 방안 | 상태 |
| --- | --- | --- | --- |
| 기획 범위 과다 | 일정 지연 및 미완성 위험 | Must / Should / Could / Won’t 구분 | 확인 필요 |
| 멀티플레이 구현 난이도 | 협동 기능 미완성 위험 | 1\~2인 우선, 4인은 제외 | 확인 필요 |
| 모바일 조작 피로도 | 전투 조작 불편 | 버튼 수 최소화, 자동/반자동 사격 검토 | 확인 필요 |
| 문서 버전 불일치 | 팀원 간 이해 차이 발생 | 최신 기준 문서와 로드맵 동기화 | 진행 |
| 통합 일정 부족 | 발표 직전 빌드 오류 위험 | 통합일과 QA일 별도 확보 | 확인 필요 |
| 아트 / UI 리소스 부족 | 발표 완성도 저하 | 임시 리소스 우선 사용 후 교체 | 확인 필요 |
| 보스 / 특수 시스템 과다 | 구현량 증가 | 기본 침식체와 중형 침식체 우선 구현 | 확인 필요 |

## 9. 통합 및 QA 일정 관리

개발 마감일과 발표일을 같은 날로 잡으면 위험하다.

따라서 PM은 기능 개발과 별도로 통합, QA, 리허설 일정을 반드시 확보한다.

| 단계 | 내용 |
| --- | --- |
| 기능 개발 | 각자 맡은 기능 구현 |
| 1차 통합 | 기능을 한 프로젝트에 합치기 |
| 버그 수정 | 충돌, 오류, 누락 확인 |
| 2차 통합 | 발표용 빌드 기준으로 정리 |
| QA | 핵심 루프 반복 테스트 |
| 리허설 | 실제 발표처럼 시연 |
| 최종 제출 | 빌드, 문서, PPT 정리 |

### 시연 성공 기준

발표용 빌드는 아래 흐름이 최소 1회 이상 안정적으로 진행되어야 한다.

```txt
게임 시작
→ 플레이어 전장 진입
→ 이동
→ 적 조우
→ 기본 공격
→ 아이템 획득
→ 제한시간 확인
→ 탈출 지점 이동
→ 결과창 출력
```

## 11. PM이 하지 말아야 할 것

| 하지 말아야 할 행동 | 이유 |
| --- | --- |

## 12. PM 핵심 관리 문장

PM은 아래 네 가지를 계속 확인한다.

```txt
누가 담당하는가?
무엇을 구현하는가?
언제까지 완료하는가?
어떤 상태를 완료로 볼 것인가?
```

본 프로젝트에서 PM의 최우선 목표는 기획을 더 크게 만드는 것이 아니라, 정해진 핵심 플레이 루프가 실제 발표 가능한 빌드로 완성되도록 관리하는 것이다.
