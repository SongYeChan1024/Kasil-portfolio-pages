### 주요 개념 정리

- <b>RPC Target</b>
  <ul>
  <li>
  설명: Photon2에서 네트워크 메시지를 누구에게 전송할지 지정하는 옵션
  </li>
  <li>
  예시: 

  - <code>RPC Target All</code>: 총알 이펙트와 소리처럼 모두에게 보여야 하는 것
  - <code>RPC Target Owner</code>: 탱크 체력처럼 소유주에게만 전송
  - <code>RPC Target MasterClient</code>: 마스터 클라이언트를 거쳐 검증하는 방식
  </li>
  <li>
  사용되는 상황: 멀티플레이 동기화에서 시각 효과와 데이터 처리를 구분할 때
  </li>
  </ul>
- <b>Frustum Culling vs Occlusion Culling</b>
  - Frustum Culling: 카메라 시야 밖의 오브젝트를 자동으로 렌더링에서 제외. Unity가 기본적으로 자동 수행
  - Occlusion Culling: 큰 객체에 가려진 정적 오브젝트를 베이킹해서 렌더링에서 제외
  - 헷갈릴 수 있는 점: Occlusion Culling만 답으로 적으면 부족함. 두 가지를 함께 활용한다고 명시해야 정답

- <b>VRM (VR Model)</b>
  - 설명: 메타버스 아바타의 사실상 표준 3D 파일 포맷. 휴머노이드 리깅 규격, 툰 셰이더, 시선 처리, 립싱크 데이터가 파일 자체에 표준화되어 있음
  - 예시: VRChat, HelloVR 등 메타버스 플랫폼에서 사용
  - 사용되는 상황: 외부 도구(Ready Player Me 등)에서 만든 아바타를 Unity 메타버스 프로젝트에 불러올 때
  - 헷갈릴 수 있는 점: FBX는 일반적인 3D 포맷이지만, 엔진마다 본 매핑이나 셰이더 규격이 달라 런타임에서 깨질 수 있음. VRM 또는 glTF 2.0이 메타버스 표준
- <b>Lerp (Linear Interpolation)</b>
  - 설명: A 지점에서 B 지점으로 시간에 따라 선형적으로 부드럽게 이동하는 보간 함수
  - 예시: <code>Vector3.Lerp(A, B, Time.deltaTime * dampingValue)</code>
  - 사용되는 상황: 오브젝트의 위치를 부드럽게 이동시킬 때
  - 회전 버전: <code>Quaternion.Slerp()</code> - 구면 보간으로 회전을 부드럽게 처리
  - 더 부드러운 회전: <code>Quaternion.RotateTowards()</code> - 일정한 속도로 회전. Slerp는 가까워질수록 느려지는 경향이 있어 일정한 속도가 필요하면 RotateTowards 사용
- <b>LTS 버전 명시의 중요성</b>
  - 설명: Unity LTS 버전(예: 6.3.4.2 LTS)을 명시하면 관련 패키지 버전(XRI 3.0, Cinemachine 3.0 등)이 자동으로 제약 조건 설정됨
  - 사용되는 상황: AI에게 코드 생성을 요청할 때 구버전 API 호출을 막기 위해
  - 예시: "Unity 6.3, XRI 3.0에서 쓰는 코드를 알려줘"

### 수업 흐름별 정리

### 1. 복습 문제 풀이 (Quiz Review)

- <b>RPC 타겟 구분</b>: 총알 이펙트/소리는 All, 탱크 체력은 Owner 또는 MasterClient 경유
- <b>컬링 기법</b>: Frustum Culling(자동) + Occlusion Culling(베이킹) 함께 사용
- <b>AI 버전 명시</b>: Unity 버전과 패키지 버전을 정확히 명시해야 구버전 코드 생성 방지
- <b>VR UI 모드</b>: 3D 공간에서 UI Canvas를 World Space 모드로 설정하고, Ray를 Canvas의 Raycaster에 충돌시켜 상호작용
- <b>메타버스 아바타 포맷</b>: FBX가 아닌 VRM 또는 glTF 2.0이 표준
- <b>프롬프트 작성</b>: 행동지침, 금지사항, 보조역할, 역할 명시
- <b>백엔드 플랫폼</b>: Firebase, Photon, Pocketbase 등 BaaS 활용으로 프론트엔드 개발에 집중
- <b>AI 리소스 툴</b>: Adobe Firefly(텍스처), Polly, Midjourney(이미지), CSM, Spline AI(3D), Ready Player Me(아바타), `Move.ai`(모션캡처), 11Labs(보이스) 등

중요: 많은 학생들이 Occlusion Culling만 답으로 적었지만, Frustum Culling과 함께 명시해야 정답

### 2. 룸 리스트 UI 제작

- 설명: 멀티플레이 로비에서 생성된 방 목록을 스크롤뷰로 표시하는 UI 구성
- Canvas 구조:
  - Panel Room List (마스크 적용)
  - Scroll Content (Grid Layout Group)
  - Room Item (프리팹)
- 중요: Panel Room List에 <b>Mask 컴포넌트</b>를 추가해야 스크롤 영역 밖의 아이템이 보이지 않음
- Grid Layout Group의 Top 값을 조정(-90)하여 아이템 생성 위치 조절

### 3. RoomItem 스크립트 작성

- 설명: 방 정보를 표시하는 프리팹에 붙일 스크립트 작성
- 역할: Photon Manager에서 방 정보를 받아 UI에 표시
- 외부에서 호출되므로 모든 변수와 함수를 <code>public</code>으로 선언

### 4. 버그 수정

- <b>문제 1</b>: 아파치 헬기가 파괴된 후에도 계속 공격함
- <b>문제 2</b>: 탱크가 파괴된 후에도 움직이고 공격 가능
- <b>문제 3</b>: 탱크 UI Canvas가 카메라를 바라보지 않음

### 실습 / 작업 순서

#### 룸 리스트 UI 생성

1. Canvas에서 Panel Room List 생성 후 위치 조정 (Width: 490, Height: 450)
2. Panel Room List 아래에 Scroll Content와 Scroll Bar 배치
3. Scroll Content에 Grid Layout Group 컴포넌트 추가
4. Grid Layout Group의 Top 값을 -90으로 설정하여 첫 아이템 위치 조정
5. Panel Room List에 Mask 컴포넌트 추가
6. Room Item 프리팹을 Prefabs 폴더로 이동
7. Scroll Content 아래의 테스트 Room Item들 삭제 (하나만 남기고 프리팹화)

#### RoomItem 스크립트 작성

1. Scripts > Network 폴더에서 우클릭 > Create > C# Script > "RoomItem" 생성
2. RoomItem 스크립트 열기
3. 필드 선언:
   - <code>[SerializeField] private TMP_Text roomNameText;</code>
   - <code>[SerializeField] private TMP_Text currentPlayerText;</code>
   - <code>[HideInInspector] public string roomName;</code>
   - <code>[HideInInspector] public int currentPlayer;</code>
   - <code>[HideInInspector] public int maxPlayer;</code>
4. <code>public void DisplayRoomData()</code> 함수 작성:
   - <code>roomNameText.text = roomName;</code>
   - <code>currentPlayerText.text = $"{currentPlayer} / {maxPlayer}";</code>
5. Room Item 프리팹 더블클릭하여 열기
6. Room Item GameObject에 RoomItem 스크립트 추가
7. Inspector에서 roomNameText와 currentPlayerText 연결

#### 버그 수정 - 파괴된 오브젝트 스크립트 비활성화

1. Tank > TankDamage 스크립트 열기
2. 필드 추가: <code>MonoBehaviour[] monoScripts;</code>
3. Awake()에서: <code>monoScripts = GetComponentsInChildren&lt;MonoBehaviour&gt;();</code>
4. RPC\_ChangeState()에서:
   ```javascript
   foreach(var script in monoScripts)
   {
       script.enabled = state;
   }
   ```
5. 시작 시 false로 스크립트 비활성화, RPC로 상태 동기화
6. 리스폰 시 다시 true로 활성화

#### 버그 수정 - UI Canvas 카메라 바라보기

1. Scripts > Camera 폴더에 "CameraLookAt" 스크립트 생성
2. 탱크의 UI Canvas에 CameraLookAt 스크립트 추가
3. Update()에서 카메라 방향으로 회전 처리 구현 \[확인 필요\]

### 예시와 활용 사례

- <b>예시 1: RPC 타겟 구분</b>
  - 상황: 탱크가 총알을 발사할 때
  - 설명: 총알 이펙트/소리는 모든 플레이어가 봐야 하므로 <code>RPC Target All</code>, 탱크 체력 감소는 소유주만 알면 되므로 <code>RPC Target Owner</code>
  - 왜 이 예시를 사용했는지: 시각 효과와 데이터 처리의 차이를 명확히 구분하기 위해
- <b>예시 2: 컬링 기법 조합</b>
  - 상황: 메타버스 맵에 건물을 많이 배치했더니 프레임 드랍
  - 설명: Frustum Culling(카메라 시야 밖 자동 제외) + Occlusion Culling(건물에 가려진 정적 오브젝트 베이킹 제외)
  - 왜 이 예시를 사용했는지: 두 가지 기법을 함께 사용해야 최적화 효과가 있음을 강조
- <b>예시 3: VRM vs FBX</b>
  - 상황: 외부 아바타 제작 툴에서 만든 아바타를 Unity에 불러올 때
  - 설명: FBX는 엔진마다 규격이 달라 깨지지만, VRM은 표준화된 규격으로 VRChat, HelloVR 등에서 바로 사용 가능
  - 왜 이 예시를 사용했는지: 메타버스 개발 시 실제 사용되는 표준 포맷 숙지

### 헷갈릴 수 있는 부분

- <b>헷갈리는 개념</b>: Frustum Culling과 Occlusion Culling
- <b>헷갈리는 이유</b>: 둘 다 렌더링 최적화 기법이고 "안 보이는 것을 제외"한다는 점에서 비슷함
- <b>구분 방법</b>: Frustum Culling은 카메라 시야 밖(자동), Occlusion Culling은 가려진 것(베이킹 필요)

---

- <b>헷갈리는 개념</b>: Lerp vs Slerp vs RotateTowards
- <b>헷갈리는 이유</b>: 모두 부드러운 이동/회전에 사용되는 보간 함수
- <b>구분 방법</b>: Lerp는 위치 선형 보간, Slerp는 회전 구면 보간(가까워지면 느려짐), RotateTowards는 일정한 속도 회전

---

- <b>헷갈리는 개념</b>: SetActive(false) vs script.enabled = false
- <b>헷갈리는 이유</b>: 둘 다 오브젝트를 "끈다"
- <b>구분 방법</b>: SetActive는 GameObject 전체를 끄고, enabled는 스크립트만 끔. 파괴된 탱크가 움직이는 문제는 enabled로 해결

- <b>OnRoomListUpdate 콜백</b>을 활용한 딕셔너리 기반 방 관리 시스템을 구현하여 효율적인 UI 업데이트를 구현했습니다.
- <b>방 생성 함수(OnClickCreateRoom)</b>를 작성하고 동적 리스너를 통한 버튼 이벤트 처리 방법을 학습했습니다.

### 주요 개념 정리

- <b>Update 사이클 타이밍</b>
  - 설명: FixedUpdate는 Update보다 빠르게 호출되며, LateUpdate는 Update 이후에 호출됨
  - 예시: 탱크가 FixedUpdate로 움직이는데 카메라가 LateUpdate로 따라가면 따라가지 못하는 문제 발생
  - 사용되는 상황: 물리 기반 이동은 FixedUpdate, UI 추적은 Update로 해결
  - 헷갈릴 수 있는 점: LateUpdate가 항상 좋은 것은 아니며, 추적 대상의 업데이트 타이밍을 고려해야 함
- <b>OnRoomListUpdate 콜백</b>
  - 설명: Photon에서 제공하는 콜백으로, 로비에서 방 목록 변경사항이 생기면 자동으로 호출됨
  - 예시: 방 생성, 방 삭제, 인원 변경, 방이 가득 참 등의 상황에서 자동 호출
  - 사용되는 상황: 로비 UI에서 실시간으로 방 목록을 업데이트할 때
  - 헷갈릴 수 있는 점: 방이 제거되거나 가득 찬 경우도 이 콜백을 통해 처리해야 함
- <b>Dictionary 기반 방 관리</b>
  - 설명: 방 이름(key)과 RoomInfo(value), 방 이름(key)과 GameObject(value) 두 개의 딕셔너리로 방 데이터와 UI를 관리
  - 예시: <code>cachedRoomList</code>에는 방 정보 데이터, <code>roomUIItems</code>에는 생성된 UI 오브젝트 저장
  - 사용되는 상황: 방 목록을 효율적으로 업데이트하고 삭제할 때
  - 헷갈릴 수 있는 점: 예전에는 전체 삭제 후 재생성 방식을 사용했으나, 부하가 크므로 딕셔너리로 개별 관리하는 방식으로 변경
- <b>TryGetValue</b>
  - 설명: 딕셔너리에서 키 존재 여부를 확인하고 값을 가져오는 안전한 방법
  - 예시: <code>roomUIItems.TryGetValue(roomName, out GameObject item)</code>
  - 사용되는 상황: 방이 이미 존재하는지 확인하고 UI를 업데이트할 때
  - 헷갈릴 수 있는 점: Null Reference Exception을 방지하면서 bool 값만 반환
- <b>동적 리스너 (AddListener)</b>
  - 설명: 런타임에 버튼 이벤트를 코드로 추가하는 방법
  - 예시: <code>btn.onClick.AddListener(() =&gt; OnClickRoomItem(roomName));</code>
  - 사용되는 상황: 동적으로 생성되는 UI 요소에 이벤트를 연결할 때
  - 헷갈릴 수 있는 점: Inspector에서 직접 연결하는 방식 대신 스크립트로 연결

### 수업 흐름별 정리

### 1. CameraLookAt 스크립트 작성 및 버그 수정

- 설명: UI Canvas가 카메라를 바라보도록 하는 스크립트 작성
- LateUpdate에서 카메라를 바라보도록 구현했으나 너무 느린 문제 발생
- 원인: 탱크가 FixedUpdate로 움직이는데 LateUpdate로 추적하니 못 따라감
- 해결: Update로 변경하여 정상 작동 확인
- 중요: Update 사이클 타이밍을 이해하고 적절한 함수를 선택해야 함

### 2. Photon 매니저 설정 및 변수 선언

- 설명: 방 생성 및 관리를 위한 변수들을 선언
- userIF: 유저 닉네임 입력창
- roomIF: 방 이름 입력창
- scrollContent: 방 목록의 부모 Transform
- roomItem: 방 목록 UI 아이템 프리팹
- Inspector에서 연결: 스크립트로 찾는 것보다 Inspector에서 끌어서 넣는 것을 권장

### 3. 딕셔너리 변수 선언

- 설명: 방 정보와 UI를 관리할 두 개의 딕셔너리 선언
- <code>cachedRoomList</code>: 방 이름(key)과 RoomInfo(value) 저장
- <code>roomUIItems</code>: 방 이름(key)과 생성된 GameObject(value) 저장
- 중요: 데이터와 UI를 분리하여 관리하는 구조

### 4. 버전 및 서버 설정

- Photon Unity Networking: Unity 전용 패키지
- Photon Realtime: 룸, 플레이어 등 실시간 통신 관련 클래스 포함
- 게임 버전 설정: 버전이 다른 유저끼리는 접속 차단
- KR 서버 접속: 핑(Ping)을 고려한 서버 선택
- 자동 로드 레벨: 방장이 씬 전환하면 자동으로 다른 클라이언트도 동기화

### 5. OnClickCreateRoom 함수 작성

- 설명: 방 생성 버튼 클릭 시 호출되는 함수 작성
- 로비 접속 확인: 로비에 접속하지 않았으면 return
- 닉네임 확인: 입력하지 않았으면 "닉네임을 입력해주세요" 표시 후 return
- 방 이름 확인: 입력하지 않았으면 "Thunderbolt" + 랜덤 3자리 숫자로 자동 생성
- PhotonNetwork.NickName 설정 및 PlayerPrefs 저장
- PhotonNetwork.CreateRoom 호출하여 방 생성

### 6. OnRoomListUpdate 콜백 구현

- 설명: 방 목록 변경사항을 실시간으로 처리하는 핵심 콜백 함수
- 로비에 머무는 동안 방 생성, 제거, 인원 변경 등이 생기면 자동 호출
- 중요: 가장 핵심적인 콜백 함수로, 방 목록의 모든 변동사항 처리

### 7. 방 제거 로직 구현

- 설명: 방이 제거되거나 가득 찬 경우 UI에서 제거
- 조건: 방이 완전히 닫혔거나(RemovedFromList) 또는 가득 참
- TryGetValue로 존재 여부 확인 후 UI 제거 및 딕셔너리에서 삭제
- 예시: 혼자 있던 방에서 나가면 방이 사라져야 함

### 8. 방 생성 및 업데이트 로직 구현

- 설명: 신규 방 생성 또는 기존 방 정보 업데이트
- cachedRoomList에 방 정보 등록
- 기존 UI가 없는 경우: 새로운 GameObject 생성 후 RoomItem 컴포넌트 추가
- ScrollContent 하위에 생성 및 데이터 설정
- 동적 리스너로 버튼 클릭 이벤트 추가
- 기존 UI가 있는 경우: 인원수 정보만 업데이트

### 9. OnClickRoomItem 함수 작성

- 설명: 방 목록 UI 클릭 시 해당 방에 접속하는 함수
- 닉네임 확인 후 PlayerPrefs 저장
- PhotonNetwork.JoinRoom 호출하여 방 접속

### 10. Roblox Studio 기초 실습

- 설명: 간단한 맵 제작 실습
- BaseCreate 템플릿 선택 후 플레이 테스트
- BaseFloor 생성 및 색상, 크기 조정
- Part로 벽 생성 및 복제(Ctrl+D)
- Anchored 체크하여 중력 무시
- Transparency를 1로 설정하여 투명하게 만들기

  - 왜 이 예시를 사용했는지: Update 사이클의 순서와 속도를 이해하는 것이 중요함을 강조
- <b>예시 2: 딕셔너리 기반 방 관리의 효율성</b>
  - 상황: 방 목록이 자주 변경되는 멀티플레이 로비
  - 설명: 예전에는 전체 삭제 후 재생성했으나, 부하가 커서 딕셔너리로 개별 관리하는 방식으로 변경
  - 왜 이 예시를 사용했는지: 자료구조 선택이 성능에 미치는 영향을 이해
- <b>예시 3: 동적 리스너 활용</b>
  - 상황: 런타임에 생성되는 방 목록 UI 버튼에 이벤트 연결
  - 설명: Inspector에서 미리 연결할 수 없으므로 AddListener로 동적으로 연결
  - 왜 이 예시를 사용했는지: 동적으로 생성되는 UI 요소의 이벤트 처리 방법 학습

---

### 헷갈릴 수 있는 부분

- <b>헷갈리는 개념</b>: FixedUpdate vs Update vs LateUpdate
- <b>헷갈리는 이유</b>: 모두 매 프레임 호출되는 것처럼 보임
- <b>구분 방법</b>: FixedUpdate가 가장 빠르고 주로 물리 연산용, Update는 일반 로직, LateUpdate는 Update 이후 실행되어 카메라 추적 등에 사용. 하지만 추적 대상이 FixedUpdate로 움직이면 LateUpdate는 느림

---

- <b>헷갈리는 개념</b>: cachedRoomList vs roomUIItems
- <b>헷갈리는 이유</b>: 둘 다 방 정보를 저장하는 딕셔너리
- <b>구분 방법</b>: cachedRoomList는 Photon의 RoomInfo 데이터만 저장, roomUIItems는 실제 생성된 UI GameObject를 저장. 데이터와 UI를 분리하여 관리

---

- <b>헷갈리는 개념</b>: ContainsKey vs TryGetValue
- <b>헷갈리는 이유</b>: 둘 다 딕셔너리에서 키 존재 여부를 확인
- <b>구분 방법</b>: ContainsKey는 존재 여부만 bool로 반환, TryGetValue는 존재 여부와 함께 값도 out 파라미터로 반환하여 Null Reference 방지

## 문제 1. 오브젝트 생성 및 소유권

마스터 클라이언트가 나가도 방에 남아 있어야 하는 공통 오브젝트는 <code>PhotonNetwork.Instantiate()</code>가 아니라 \*\*<code>PhotonNetwork.InstantiateRoomObject()</code>\*\*로 생성해야 합니다.

```txt
if (PhotonNetwork.IsMasterClient)
{
PhotonNetwork.InstantiateRoomObject(
"WorldDropItem",
spawnPosition,
Quaternion.identity
    );
}
```

<code>PhotonNetwork.Instantiate()</code>로 생성한 오브젝트는 기본적으로 <b>생성한 클라이언트의 생명주기</b>에 묶입니다. 그래서 생성자가 방을 나가면 해당 오브젝트도 다른 클라이언트에서 제거될 수 있습니다. 반면 <code>PhotonNetwork.InstantiateRoomObject()</code>는 오브젝트가 특정 플레이어가 아니라 <b>Room에 종속</b>되므로, 생성한 마스터 클라이언트가 나가도 방이 유지되는 동안 남아 있을 수 있습니다. Photon 공식 문서에서도 일반 Instantiate 오브젝트는 생성자가 방에 있는 동안 존재하고, <code>InstantiateRoomObject()</code>는 방의 생명주기를 따르며 마스터 클라이언트와 직접 연결되지 않는다고 설명합니다.

소유권 관점에서는 이 오브젝트를 <b>플레이어 개인 소유가 아닌 Room Object</b>로 보고, 기본 제어자는 현재 <b>MasterClient</b>가 됩니다. 기존 마스터가 나가면 새 마스터가 이어서 제어할 수 있습니다. 필요하다면 <code>photonView.TransferOwnership()</code>으로 제어권을 다른 클라이언트에게 넘길 수도 있습니다. 단, <code>InstantiateRoomObject()</code>로 만든 오브젝트를 네트워크 상에서 파괴할 때는 기본적으로 MasterClient가 처리해야 합니다.

<b>답안 예시:</b>

마스터 클라이언트가 나가도 유지되어야 하는 중립 몬스터나 월드 드롭 아이템은 <code>PhotonNetwork.InstantiateRoomObject()</code>로 생성해야 한다. 이 오브젝트는 특정 플레이어가 아니라 Room에 종속되며, 기본적으로 현재 MasterClient가 제어한다. 따라서 기존 마스터 클라이언트가 나가도 새 MasterClient가 제어를 이어받을 수 있다. 필요하면 <code>TransferOwnership()</code>으로 소유권 또는 제어권을 넘길 수 있다.

## 문제 2. 동기화 최적화, Serialization

<code>OnPhotonSerializeView</code>에서 매번 위치와 회전을 무조건 보내면 트래픽이 낭비됩니다. 그래서 <code>stream.IsWriting</code>일 때 <b>이전 전송 값과 현재 값을 비교</b>해서, 일정 기준 이상 변했을 때만 데이터를 보내는 방식으로 최적화합니다.

예를 들어 이런 개념입니다.

```txt
privateVector3lastSentPosition;
privateQuaternionlastSentRotation;

privatefloatpositionThreshold=0.05f;
privatefloatrotationThreshold=2f;

publicvoidOnPhotonSerializeView(PhotonStreamstream,PhotonMessageInfoinfo)
{
if (stream.IsWriting)
    {
boolpositionChanged=
Vector3.Distance(transform.position,lastSentPosition)>positionThreshold;

boolrotationChanged=
Quaternion.Angle(transform.rotation,lastSentRotation)>rotationThreshold;

if (!positionChanged&&!rotationChanged)
        {
return;
        }

stream.SendNext(positionChanged);
if (positionChanged)
        {
stream.SendNext(transform.position);
lastSentPosition=transform.position;
        }

stream.SendNext(rotationChanged);
if (rotationChanged)
        {
stream.SendNext(transform.rotation);
lastSentRotation=transform.rotation;
        }
    }
else
    {
boolpositionChanged= (bool)stream.ReceiveNext();
if (positionChanged)
        {
Vector3receivedPosition= (Vector3)stream.ReceiveNext();
// 바로 대입하지 말고 보간 목표값으로 저장
        }

boolrotationChanged= (bool)stream.ReceiveNext();
if (rotationChanged)
        {
QuaternionreceivedRotation= (Quaternion)stream.ReceiveNext();
// 바로 대입하지 말고 보간 목표값으로 저장
        }
    }
}
```

핵심은 <b>변화량 기준값 Threshold</b>를 두는 것입니다.

- 위치 변화가 너무 작으면 보내지 않음
- 회전 변화가 너무 작으면 보내지 않음
- 변화가 있을 때만 <code>SendNext()</code>
- 어떤 데이터가 보내졌는지 알기 위해 <code>bool</code> 플래그 또는 bitmask를 먼저 보냄
- 수신 측은 받은 위치와 회전을 바로 순간이동시키지 않고 <code>Lerp</code>, <code>Slerp</code>로 보간

Photon 문서에서도 <code>OnPhotonSerializeView</code>는 <code>PhotonView</code>의 Observed Component로 등록된 스크립트에서 호출되며, <code>stream.IsWriting</code>인 클라이언트가 데이터를 쓰고 원격 클라이언트는 읽는 구조라고 설명합니다. 또한 아무 값도 stream에 쓰지 않으면 PUN이 해당 업데이트를 건너뛰어 대역폭을 아낄 수 있습니다.

<b>답안 예시:</b>

<code>stream.IsWriting</code> 내부에서 현재 위치와 마지막으로 전송한 위치를 비교하고, <code>Vector3.Distance</code> 값이 일정 기준보다 클 때만 위치를 전송한다. 회전도 <code>Quaternion.Angle</code>로 비교하여 일정 각도 이상 변했을 때만 전송한다. 변화가 없다면 <code>SendNext()</code>를 호출하지 않아 업데이트를 생략한다. 변화가 있는 데이터만 보내되, 수신 측에서 데이터 순서가 꼬이지 않도록 위치 변화 여부와 회전 변화 여부를 bool 값으로 먼저 전송한다.

## 문제 3. 마스터 클라이언트 전환 대응

구현해야 하는 콜백 메서드는 다음입니다.

```txt
publicoverridevoidOnMasterClientSwitched(PlayernewMasterClient)
{
}
```

이 메서드는 <code>MonoBehaviourPunCallbacks</code>를 상속받은 스크립트에서 <code>override</code>해서 사용할 수 있습니다. Photon 공식 API 문서에서도 <code>OnMasterClientSwitched(Player newMasterClient)</code>는 기존 MasterClient가 나간 뒤 새 MasterClient로 전환된 후 호출되는 콜백이라고 설명합니다.

예시 구조는 이렇습니다.

```txt
usingPhoton.Pun;
usingPhoton.Realtime;
usingUnityEngine;

publicclassHostLogicManager :MonoBehaviourPunCallbacks
{
privateboolisHostLogicRunning;

publicoverridevoidOnMasterClientSwitched(PlayernewMasterClient)
    {
if (!PhotonNetwork.InRoom)
return;

if (newMasterClient==null)
return;

if (PhotonNetwork.LocalPlayer.ActorNumber!=newMasterClient.ActorNumber)
return;

TakeOverHostLogic();
    }

privatevoidTakeOverHostLogic()
    {
if (isHostLogicRunning)
return;

isHostLogicRunning=true;

// 1. Room Custom Properties에서 게임 타이머 복구
// 2. 몬스터 상태, 웨이브 상태, 스폰 정보 복구
// 3. AI 행동 루프 다시 시작
    }
}
```

여기서 중요한 예외 처리는 다음입니다.

첫째, <b>새 마스터인지 확인</b>해야 합니다.

```txt
if (!PhotonNetwork.IsMasterClient)
return;
```

콜백은 여러 클라이언트에서 받을 수 있으므로, 실제 호스트 로직은 새 MasterClient가 된 클라이언트만 실행해야 합니다.

둘째, <b>중복 실행 방지</b>가 필요합니다.

이미 타이머 코루틴이나 AI 루프가 돌고 있는데 또 실행하면 몬스터가 두 번 움직이거나 시간이 두 배로 흐를 수 있습니다.

셋째, <b>이전 마스터의 로컬 변수에 의존하면 안 됩니다.</b>

기존 마스터가 가지고 있던 <code>monsterTarget</code>, <code>waveIndex</code>, <code>remainingTime</code> 같은 값은 새 마스터에게 자동으로 넘어오지 않습니다. 그래서 중요한 상태는 <code>Room Custom Properties</code>, <code>Player Custom Properties</code>, 네트워크 동기화된 오브젝트 상태, 또는 <code>PhotonNetwork.Time</code> 기반 타이머로 복구할 수 있게 해야 합니다. Photon 문서에서도 Room과 Player의 Custom Properties는 서버를 통해 동기화되고, 변경 시 <code>OnRoomPropertiesUpdate</code> 또는 <code>OnPlayerPropertiesUpdate</code> 콜백으로 받을 수 있다고 설명합니다.

<b>답안 예시:</b>

마스터 클라이언트가 변경될 때는 <code>OnMasterClientSwitched(Player newMasterClient)</code> 콜백을 구현해야 한다. 이 콜백 안에서 현재 클라이언트가 새 MasterClient인지 확인한 뒤, AI 몬스터 로직이나 게임 타이머 같은 호스트 기반 로직을 이어받아 실행한다. 이때 기존 마스터의 로컬 변수는 사라질 수 있으므로, 타이머 시작 시간, 몬스터 상태, 웨이브 진행도 같은 값은 Room Custom Properties나 네트워크 동기화 데이터로 저장해 두어야 한다. 또한 코루틴이나 AI 루프가 중복 실행되지 않도록 예외 처리가 필요하다.

## 문제 4. 오브젝트 풀링과 Photon 연동

정답은 \*\*<code>IPunPrefabPool</code>\*\*입니다.

Photon에서 <code>PhotonNetwork.Instantiate</code>와 <code>PhotonNetwork.Destroy</code>가 호출될 때, 기본 생성/파괴 대신 개발자가 만든 풀을 사용하게 하려면 <code>IPunPrefabPool</code> 인터페이스를 구현하고 <code>PhotonNetwork.PrefabPool</code>에 등록해야 합니다.

```txt
PhotonNetwork.PrefabPool=newMyPunPrefabPool();
```

<code>IPunPrefabPool</code>에는 대표적으로 다음 두 메서드가 있습니다.

```txt
GameObjectInstantiate(stringprefabId,Vector3position,Quaternionrotation);
voidDestroy(GameObjectgameObject);
```

<code>Instantiate()</code>는 풀에서 꺼낸 비활성화된 오브젝트를 반환하고, <code>Destroy()</code>는 실제로 삭제하는 대신 다시 풀에 넣는 역할을 합니다. Photon 공식 문서에서도 <code>IPunPrefabPool</code>은 <code>PhotonNetwork.Instantiate</code>와 <code>PhotonNetwork.Destroy</code>에 사용되는 오브젝트 풀링 인터페이스이며, 커스텀 풀을 쓰려면 <code>PhotonNetwork.PrefabPool</code>에 설정한다고 설명합니다.

주의할 점은 풀링으로 재사용되는 오브젝트는 매번 새로 생성되는 것이 아니기 때문에 <code>Start()</code>가 다시 호출되지 않을 수 있습니다. 따라서 초기화 코드는 <code>OnEnable()</code>과 <code>OnDisable()</code>에 두는 것이 안전합니다. Photon 문서도 커스텀 <code>IPunPrefabPool</code>을 사용할 때 재사용 오브젝트에서는 <code>Awake</code>와 <code>Start</code>가 한 번만 호출되므로 <code>OnEnable</code>, <code>OnDisable</code>을 활용하라고 안내합니다.

<b>답안 예시:</b>

Photon의 네트워크 오브젝트 생성과 파괴를 오브젝트 풀과 연동하기 위해 사용하는 인터페이스는 <code>IPunPrefabPool</code>이다. 이 인터페이스를 구현한 뒤 <code>PhotonNetwork.PrefabPool</code>에 등록하면, <code>PhotonNetwork.Instantiate</code>는 새 오브젝트를 생성하는 대신 풀에서 오브젝트를 가져오고, <code>PhotonNetwork.Destroy</code>는 오브젝트를 실제 삭제하지 않고 풀로 반환하게 만들 수 있다.

<b>문제 1 (오브젝트 생성 및 소유권)</b>

<b>PhotonNetwork.Instantiate를 통해 생성된 네트워크 오브젝트는</b>

<b>기본적으로 방(Room)에 종속되므로 생성한 클라이언트가 방을 나가면 함께 파괴됩니다.</b>

<b>만약 1인 개발자가 마스터 클라이언트가 나가더라도 방에 유지되어야</b>

<b>하는 공통 오브젝트(예: 월드 드롭 아이템, 중립 몬스터 등)를 생성하고자 할 때,</b>

<b>어떤 방식으로 오브젝트를 생성해야 하며 이때 소유권(Ownership)은 어떻게 처리해야 하는지 기술하시오.</b>

<br />마스터 클라이언트가 나가도 유지되어야 하는 중립 몬스터나 월드 드롭 아이템은 <code>PhotonNetwork.InstantiateRoomObject()</code>로 생성해야 한다. 이 오브젝트는 특정 플레이어가 아니라 Room에 종속되며, 기본적으로 현재 MasterClient가 제어한다. 따라서 기존 마스터 클라이언트가 나가도 새 MasterClient가 제어를 이어받을 수 있다. 필요하면 <code>TransferOwnership()</code>으로 소유권 또는 제어권을 넘길 수 있다.<br /><br />

<b>문제 2 (동기화 최적화 - Serialization)</b>

<b>IPunObservable 인터페이스의 OnPhotonSerializeView 메서드를</b>

<b>사용하여 캐릭터의 위치와 회전 값을 동기화하려고 합니다.</b>

<b>매 프레임 모든 데이터를 무조건 보내는 방식은 대역폭을 낭비하게 됩니다.</b>

<b>소규모 팀에서 네트워크 트래픽을 최적화하기 위해, stream.isWriting 조건문 내부에서</b>

<b>데이터의 변화 여부를 감지하여 전송을 제어하는 구체적인 로직(개념)을 설명하시오.</b>

<code>stream.IsWriting</code> 내부에서 현재 위치와 마지막으로 전송한 위치를 비교하고, <code>Vector3.Distance</code> 값이 일정 기준보다 클 때만 위치를 전송한다. 회전도 <code>Quaternion.Angle</code>로 비교하여 일정 각도 이상 변했을 때만 전송한다. 변화가 없다면 <code>SendNext()</code>를 호출하지 않아 업데이트를 생략한다. 변화가 있는 데이터만 보내되, 수신 측에서 데이터 순서가 꼬이지 않도록 위치 변화 여부와 회전 변화 여부를 bool 값으로 먼저 전송한다.<br /><br />

<b>문제 3 (마스터 클라이언트 전환 대응)</b>

<b>Photon은 방장을 맡고 있는 클라이언트가 연결을 끊으면 다른 플레이어를</b>

<b>자동으로 MasterClient로 위임합니다.</b>

<b>이때 기존 마스터 클라이언트가 통제하던 호스트 기반의 로직(예: AI 몬스터의 행동 트리, 게임 타이머)이</b>

<b>끊기지 않고 부드럽게 이어지도록 하기 위해, 스크립트에서 구현해야 하는</b>

<b>Photon 콜백 메서드는 무엇이며 어떤 예외 처리가 필요한지 기술하시오.</b>

<br />마스터 클라이언트가 변경될 때는 <code>OnMasterClientSwitched(Player newMasterClient)</code> 콜백을 구현해야 한다. 이 콜백 안에서 현재 클라이언트가 새 MasterClient인지 확인한 뒤, AI 몬스터 로직이나 게임 타이머 같은 호스트 기반 로직을 이어받아 실행한다. 이때 기존 마스터의 로컬 변수는 사라질 수 있으므로, 타이머 시작 시간, 몬스터 상태, 웨이브 진행도 같은 값은 Room Custom Properties나 네트워크 동기화 데이터로 저장해 두어야 한다. 또한 코루틴이나 AI 루프가 중복 실행되지 않도록 예외 처리가 필요하다.<br /><br />

<b>문제 4 (오브젝트 풀링과의 연동)</b>

<b>소규모 팀에서 모바일 또는 저사양 PC를 타깃으로 멀티플레이어</b>

<b>게임을 개발할 때,</b>

<b>PhotonNetwork.Instantiate와 Destroy를 반복하면</b>

<b>가비지 컬렉션(GC)으로 인해 프레임 드랍이 발생합니다.</b>

<b>Photon에서 제공하는 특정 인터페이스를 구현하면</b>

<b>네트워크 오브젝트 생성/파괴 시 개발자가 만든 ‘오브젝트 풀(Object Pool)’을 거치도록 커스텀할 수 있습니다.</b>

<b>이 역할을 수행하는 인터페이스의 이름을 명시하시오.</b>

<br />Photon의 네트워크 오브젝트 생성과 파괴를 오브젝트 풀과 연동하기 위해 사용하는 인터페이스는 <code>IPunPrefabPool</code>이다. 이 인터페이스를 구현한 뒤 <code>PhotonNetwork.PrefabPool</code>에 등록하면, <code>PhotonNetwork.Instantiate</code>는 새 오브젝트를 생성하는 대신 풀에서 오브젝트를 가져오고, <code>PhotonNetwork.Destroy</code>는 오브젝트를 실제 삭제하지 않고 풀로 반환하게 만들 수 있다.<br /><br />
