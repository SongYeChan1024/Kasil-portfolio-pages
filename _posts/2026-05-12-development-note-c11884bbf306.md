### 인터넷과 네트워크의 역사

- 네트워크는 정보와 자원 공유를 위해 통신 가능한 장비들이 서로 연결되어 데이터를 주고받는 것  
- 인터넷은 "International Network"의 합성어로, 여러 개의 네트워크를 묶은 개념   
- 1969년 미국 국방부 펜타곤이 UCLA와 스탠포드 대학에 포 발사 각도 계산을 의뢰하며 시작  
- 두 대학 연구진이 데이터 공유를 위해 모니터에 간단한 대화창(채팅창)을 만들면서 네트워크 통신 시작  
- 1982년 TCP/IP가 인터넷 표준 프로토콜로 채택됨   
- 1988년 팀 버너스 리가 World Wide Web(WWW) 개발 제안  
- 1992년 인터넷 서비스로 월드와이드 웹 시작  
- 1994년 최초의 웹 브라우저 Netscape 등장  
- 1995년 Windows 95 출시 및 Internet Explorer 제공 시작  

### TCP (Transmission Control Protocol)

- <b>비유:</b> 전화  
- <b>특징:</b> 연결 지향적 프로토콜로 신뢰성이 있음  
- <b>신뢰성:</b> 패킷이 순서대로 도착했는지, 중간에 유실되지 않았는지 확인  
- <b>재전송:</b> 데이터가 유실되었거나 순서가 꼬였을 경우 다시 보내달라고 요청  
- <b>패킷:</b> 1024 바이트 단위로 묶어서 전송  
- <b>속도:</b> UDP에 비해 느리지만 절망적으로 느린 것은 아님  
- <b>장점:</b> 데이터의 정확성을 보장함 
- <b>사용 예시:</b>
  - 보드게임 (데이터 정확성이 중요)  
  - 웹 브라우징 (HTTP)  
  - 이메일 
  - 파일 전송 (FTP) 
  - 데이터가 하나라도 틀리면 안 되는 서비스  

### UDP (User Datagram Protocol)

- <b>비유:</b> 편지  
- <b>특징:</b> 비연결형 프로토콜  
- <b>연결 방식:</b> 상대방이 데이터를 받을 준비가 되었는지 확인하지 않고 일방적으로 전송   
- <b>신뢰성:</b> 신뢰성이 거의 없음 - 데이터가 순서대로 도착하는지, 중간에 유실되는지 확인하지 않음 
- <b>속도:</b> 확인 절차가 필요 없어 TCP보다 빠르고 오버헤드가 적음  
- <b>편지 비유 설명:</b> 같은 날 동시에 여러 편지를 보내도 어느 것이 먼저 도착할지 알 수 없음 - 순서가 보장되지 않음  
- <b>사용 예시:</b>
  - 실시간 스트리밍 
  - 온라인 게임 
  - 화상 통화 
  - FPS 게임, TPS 게임 등 속도가 중요한 게임  
  - 데이터가 조금 유실되어도 실시간성이 중요한 서비스 

### PhotonView Synchronization 옵션

- <b>Off:</b> 동기화 없음, <code>OnPhotonSerializeView</code>가 호출되지 않음, RPC만 사용 
  - 사용 사례: 점수 업데이트, 채팅 등 특정 시점에만 데이터 전송이 필요한 경우 
- <b>Unreliable (UDP 방식):</b> 데이터 변경 여부와 상관없이 매 틱(프레임)마다 패킷 전송, 손실 가능성 있음   
  - 사용 사례: 초당 전송 횟수가 많고 데이터가 누락되어도 다음 패킷이 금방 덮어쓰는 자유 이동  
- <b>Unreliable On Change (변경 시 전송, UDP):</b> 데이터에 변경 사항이 발생했을 때만 패킷 전송, 가장 많이 쓰이는 합리적인 옵션   
  - 사용 사례: 움직임이 멈춰있을 때 불필요한 패킷 발생을 막고 싶을 때, 대부분의 캐릭터 이동  
- <b>Reliable Delta Compressed (TCP 방식):</b> 마지막으로 보낸 데이터와 비교해 변경된 값만 전송하며 도착을 보장, 부하가 가장 큼   
  - 사용 사례: 매우 중요한 상태 값(체력, 장착 장비 등)이 반드시 전달되어야 할 때 

### Photon Unity Networking 실무 팁

- <b>권장 옵션:</b> 가급적 'Unreliable On Change'를 기본으로 사용 - 트래픽 비용을 아끼고 네트워크 부하를 줄이는 효율적인 선택 
- <b>Photon Transform View:</b> 위치, 회전, 크기 동기화 시 사용, Lerp/Smooth 설정으로 끊김 보정 가능   
- <b>Photon Animator View:</b> 애니메이션 파라미터 동기화 시 사용 
- <b>IPunObservable 직접 제어:</b> 복잡한 데이터(인벤토리 정보 등) 실시간 동기화 시 <code>OnPhotonSerializeView</code> 메서드에서 <code>stream.SendNext()</code>와 <code>stream.ReceiveNext()</code> 직접 구현 
- <b>주의사항:</b> 하나의 GameObject에 너무 많은 PhotonView를 넣지 말 것 - 루트 객체에 하나만 두고 하위 데이터를 한 번에 직렬화하는 것이 성능상 유리

## 1. 동기 vs 비동기 (작업 완료의 '순서'와 '통지')

두 개념의 핵심은 "작업의 순서가 지켜지는가?"와 "끝난 것을 누가 확인하는가?"에 있습니다.

- <b>동기 (Synchronous):</b> 설계가 매우 직관적입니다. A라는 작업이 끝나야 B라는 작업을 시작합니다. 호출한 함수가 결과를 반환할 때까지 기다리거나, 반환 시점에 맞춰 다음 작업을 수행합니다.
- <b>비동기 (Asynchronous):</b> A라는 작업을 던져두고 바로 B를 실행합니다. A가 언제 끝날지는 관심사가 아니며, A는 작업이 완료되면 콜백(Callback)이나 <b>이벤트</b>를 통해 결과를 알려줍니다.

## 2. 블록킹 vs 논 블록킹 (제어권의 '반환' 여부)

두 개념의 핵심은 "내 스레드가 멈춰 있는가, 일하고 있는가?"에 있습니다.

- <b>블록킹 (Blocking):</b> 요청한 작업이 끝날 때까지 내 스레드의 제어권을 넘겨줍니다. 즉, 함수를 호출하면 그 함수가 끝날 때까지 내 코드는 멈춥니다(Hang).
- <b>논 블록킹 (Non-blocking):</b> 요청한 작업의 완료 여부와 상관없이 제어권을 즉시 돌려받습니다. 내 스레드는 멈추지 않고 다음 코드를 계속 실행합니다.

---

## 3. 게임 개발 관점에서의 4가지 조합

이 개념들은 섞여서 나타날 때 그 진가가 드러납니다. 게임 루프를 예로 들어 보겠습니다.

### ① 동기 + 블록킹 (Sync-Blocking)

- <b>상황:</b> 게임 로딩 중 대용량 텍스처 파일을 읽어올 때.
- <b>현상:</b> 파일을 다 읽을 때까지 화면이 멈춥니다.
- <b>특징:</b> 구현은 가장 간단하지만, 메인 루프에서 실행하면 유저가 "게임이 튕겼나?"라고 느낄 수 있습니다.

### ② 동기 + 논 블록킹 (Sync-Non-blocking)

- <b>상황:</b> 네트워크 패킷이 왔는지 매 프레임마다 확인(<code>Poll</code>)할 때.
- <b>현상:</b> "데이터 왔어?" -> "아니" -> (다른 작업 수행) -> 다음 프레임에 다시 "데이터 왔어?"
- <b>특징:</b> 제어권을 바로 돌려받아 다른 일을 할 수 있지만, 결과가 나올 때까지 계속 물어봐야 하므로 자원 낭비가 발생할 수 있습니다.

### ③ 비동기 + 논 블록킹 (Async-Non-blocking)

- <b>상황:</b> 백그라운드 리소스 로딩 (예: Unity의 <code>Addressables</code>나 <code>LoadSceneAsync</code>).
- <b>현상:</b> 로딩을 명령하고 메인 루프는 계속 돌아가며 로딩 UI를 업데이트합니다. 로딩이 끝나면 시스템이 "다 됐어!"라고 알려줍니다.
- <b>특징:</b> 성능과 사용자 경험 측면에서 가장 이상적입니다.

### ④ 비동기 + 블록킹 (Async-Blocking)

- <b>상황:</b> 비동기로 DB 쿼리를 던졌는데, 정작 코드 아래에서 그 결과값이 없으면 안 되어 억지로 기다리는(<code>Wait</code>, <code>Join</code>) 경우.
- <b>현상:</b> 비동기처럼 보이지만 결국 스레드가 멈춰버립니다.
- <b>특징:</b> 의도치 않은 실수로 발생하는 경우가 많으며, 성능 이점을 갉아먹는 안 좋은 패턴입니다.
