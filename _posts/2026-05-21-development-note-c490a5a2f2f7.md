<b>제페토(Zepeto) 플랫폼 개요 및 실습 준비</b> 2026-05-21


## 요약


### 오늘 수업 핵심 요약

- <b>제페토(Zepeto)</b> 메타버스 플랫폼의 비즈니스 모델과 수익 구조를 학습했습니다. 
- 제페토에서 <b>아이템 제작 및 월드 제작</b>을 통해 실제 수익을 창출할 수 있는 방법을 배웠습니다. 
- Unity 2022.3.9f 버전과 제페토 Build it 툴 설치를 포함한 <b>개발 환경 구축</b> 실습을 준비했습니다. 
- 직접 제페토 계정을 만들고 게임을 플레이하며 플랫폼을 체험하는 것이 개발자로서 중요하다는 점을 강조했습니다. 
- 대중성과 컨텐츠가 기술적 완성도보다 중요할 수 있다는 관점을 배웠습니다. 

---

### 주요 개념 정리

- <b>ARPU (Average Revenue Per User, 객단가)</b> 
  - 설명: 사용자 1인당 평균 매출을 의미하는 게임 업계 핵심 지표
  - 예시: 믹스마스터 약 2만원, 천상계/징기스칸 등 무역게임 약 10\~13만원 
  - 사용되는 상황: 게임의 수익성을 평가할 때. 이용자 수가 많아도 ARPU가 낮으면 실제 매출은 낮을 수 있음
  - 헷갈릴 수 있는 점: 이용자 수와 매출이 반드시 비례하지 않음. 제페토는 5억 명 이용자에 매출 약 1,500억원, 던전앤파이터는 2.5억 명 이용자에 연매출 약 2조원 
- <b>제페토(Zepeto)</b> 
  - 설명: 전세계 5억 명이 이용하는 메타버스 플랫폼
  - 예시: 아이템 제작/판매, 월드 제작, 라이브 방송 등이 가능
  - 사용되는 상황: 개인 크리에이터가 컨텐츠를 제작하여 수익화하거나, 기업이 브랜드 마케팅 목적으로 활용
  - 헷갈릴 수 있는 점: 그래픽이 단순해 보여도 수억 명이 이용하고 실제 수익이 발생하는 플랫폼 
- <b>Build it</b> 
  - 설명: 제페토에서 제공하는 자체 월드 제작 툴
  - 예시: Unity 없이도 드래그 앤 드롭 방식으로 월드 제작 가능 
  - 사용되는 상황: 간단한 월드를 빠르게 제작하고 싶을 때
  - 헷갈릴 수 있는 점: Unity를 사용하면 더 복잡한 기능 구현 가능

---

### 수업 흐름별 정리

### 1. 제페토 비즈니스 모델 이해 

- 설명: 제페토와 다른 게임들의 이용자 수 대비 매출 비교를 통해 ARPU의 중요성 학습
- 예시: 제페토(5억 명, 약 1,500억원) vs 던전앤파이터(2.5억 명, 약 2조원)
- 중요한 이유: 단순히 이용자 수가 많다고 성공하는 것이 아니라, 수익 구조를 이해해야 함 

### 2. 개발자 마인드셋: 게임을 직접 해봐야 하는 이유 

- 설명: 게임을 만들려면 반드시 해당 게임을 직접 플레이해봐야 한다는 강조
- 예시: 카지노 게임 개발 시 프로그래머들이 게임을 몰라서 실제 카지노에 보낸 경험 
- <code>중요:</code> 로블록스, 마인크래프트, 제페토 등 메타버스를 만들려면 반드시 게임을 먼저 체험해야 함 

### 3. 제페토 수익 창출 사례 

- 설명: 실제로 제페토에서 아이템을 제작해 수익을 올린 사례 소개
- 예시: 한 수강생이 5일만에 아이템 4,000개 이상 판매. 현재는 월 300\~500만원 수익, 연 5,000만원 수준
- 중요한 이유: 그래픽이 단순해 보여도 실제 수익 창출이 가능하다는 증거

### 4. 기업/기관의 제페토 활용 

- 설명: 한전, 대학교, YG 등 다양한 기관에서 제페토 월드 제작을 외주로 발주
- 예시: 한전 제페토 월드 제작 비용 약 1,350만원 
- 중요한 이유: 개인 크리에이터뿐 아니라 B2B 외주로도 수익 창출 가능

### 5. 대중성의 중요성 

- 설명: 기술적으로 완성도가 높지 않아도 대중성과 컨텐츠가 있으면 성공할 수 있음
- 예시: 제페토, 로블록스 같은 플랫폼의 성공
- <code>중요:</code> 고급 그래픽이 전부가 아니며, 타겟 대중을 이해하는 것이 핵심 

---

### 실습 / 작업 순서

1. 제페토 PC 버전 및 모바일 버전 설치 
2. 제페토 계정 가입 및 캐릭터 생성 
3. 캐릭터 커스터마이징 (옷 입히기 등) 
4. 제페토 월드에 접속하여 다양한 컨텐츠 체험 
5. Unity 2022.3.9f 버전 설치 
6. Build it 툴 설치 
7. Build it으로 간단한 월드 제작 실습 
8. Test 버튼을 눌러 자신의 캐릭터로 월드 테스트 
9. ESC 키를 눌러 테스트 종료 
10. 완성된 월드는 '공개' 버튼을 눌러 전세계에 배포 가능

### 예시와 활용 사례

- 예시 1: 한전 제페토 월드 
  - 상황: 한전에서 제페토 월드 제작을 외주로 발주
  - 설명: 자동으로 문이 열리고, 모니터 앞에 가면 한전 역사 영상이 자동 재생되며, 버튼을 누르면 태양광 등 에너지 관련 정보 표시
  - 왜 이 예시를 사용했는지: 기업이 제페토를 마케팅/홍보 목적으로 활용하는 실제 사례
- 예시 2: YG 엔터테인먼트 
  - 상황: YG가 제페토에 130\~170억원 투자
  - 설명: 제페토 내 YG존에서 블랙핑크 등 가수들의 캐릭터가 춤추고 뮤직비디오가 재생됨
  - 왜 이 예시를 사용했는지: 대형 엔터테인먼트 회사의 메타버스 투자 사례
- 예시 3: 개인 크리에이터 수익 사례 
  - 상황: 패션 디자인 경력이 있는 수강생이 제페토 아이템 제작
  - 설명: 5일만에 4,000개 이상 판매, 현재 월 300\~500만원 수익
  - 왜 이 예시를 사용했는지: 개인도 충분히 수익을 창출할 수 있다는 동기 부여

### 오늘 수업 핵심 요약

- <b>Photon Networking</b>에서 발생하는 <b>레이트 조인(Late-joiner) 상태 동기화 문제</b>를 Buffered RPC와 Custom Properties로 해결하는 방법을 학습했습니다. 
- <b>소유권(Ownership) 이전</b>과 <b>경쟁 조건(Race Condition)</b>을 방지하기 위한 마스터 클라이언트 경유 방식의 아이템 획득 처리 워크플로우를 배웠습니다. 
- <b>모바일 환경의 일시적 단선</b> 상황에서 <code>PlayerTTL</code>, <code>EmptyRoomTTL</code> 설정과 <code>PhotonNetwork.ReconnectAndRejoin()</code>을 활용한 부드러운 재접속 구현 방법을 학습했습니다. 
- <b>캐릭터 위치 동기화 최적화</b>를 위한 보간(Interpolation)과 예측(Extrapolation) 기법을 <code>OnPhotonSerializeView</code>에서 구현하는 방법을 배웠습니다.

### 주요 개념 정리

- <b>Late-joiner (레이트 조인)</b> 
  - 설명: 게임이 진행 중인 방에 뒤늦게 입장한 유저
  - 예시: 기존 유저들이 상자를 파괴하거나 문을 열어둔 상태에서 새로 들어온 유저는 기본 씬 상태(닫힌 문, 멀쩡한 상자)를 보게 됨
  - 사용되는 상황: 멀티플레이어 게임에서 게임 진행 중 신규 플레이어가 접속할 때
  - 헷갈릴 수 있는 점: 단순 RPC는 현재 접속자에게만 전달되므로 과거 이벤트를 받지 못함
- <b>Buffered RPC</b> 
  - 설명: 서버가 RPC 호출을 기억해 나중에 들어온 유저에게도 재실행하는 방식
  - 예시: 문 열림 RPC를 버퍼링하여 늦게 들어온 유저에게도 문이 열린 상태로 보여줌
  - 사용되는 상황: 간단한 상태 전달이 필요할 때
  - 헷갈릴 수 있는 점: 이벤트가 많아지면 버퍼가 쌓이고 중복 실행이나 버퍼 정리 문제 발생 가능
- <b>Custom Properties</b> 
  - 설명: 방이나 플레이어의 현재 상태를 Key-Value 형태로 서버에 저장하는 방식
  - 예시: 문 열림 여부(<code>doorOpen = true</code>), 상자 파괴 여부(<code>boxDestroyed = true</code>) 등을 저장
  - 사용되는 상황: 결과가 남는 요소(문 열림, 상자 파괴, 퍼즐 클리어)를 관리할 때
  - 헷갈릴 수 있는 점: RPC는 연출용(애니메이션)으로 사용하고, 실제 상태는 Custom Properties로 관리하는 것이 안전
- <b>Race Condition (경쟁 조건)</b> 
  - 설명: 두 개 이상의 클라이언트가 동시에 같은 자원에 접근하여 충돌이 발생하는 상황
  - 예시: 클라이언트 A와 B가 동시에 같은 아이템을 주우려 할 때 아이템이 복사되거나 에러 발생
  - 사용되는 상황: 필드 아이템 획득, 오브젝트 상호작용 등
  - 헷갈릴 수 있는 점: 클라이언트가 직접 확정하면 안 되고 마스터 클라이언트를 경유해야 함
- <b>PlayerTTL (Player Time To Live)</b> 
  - 설명: 끊긴 플레이어 actor를 일정 시간 동안 inactive 상태로 유지하는 설정 (밀리초 단위)
  - 예시: <code>PlayerTtl = 30000</code> (30초)
  - 사용되는 상황: 모바일 환경에서 네트워크 전환(Wi-Fi↔LTE)이나 터널 통과 시 일시적 단선
  - 헷갈릴 수 있는 점: 0보다 크게 설정해야 복구 가능 시간이 생김
- <b>Interpolation (보간)</b> 
  - 설명: 수신한 위치 값을 바로 적용하지 않고 현재 위치에서 목표 위치까지 부드럽게 이동시키는 기법
  - 예시: <code>Vector3.Lerp</code>, <code>SmoothDamp</code>, <code>Quaternion.Slerp</code> 사용
  - 사용되는 상황: 네트워크 패킷 도착 간격으로 인한 끊김(Jittering) 현상 방지
  - 헷갈릴 수 있는 점: <code>Update</code>에서 매 프레임 보간 처리 필요
- <b>Extrapolation (예측)</b> 
  - 설명: 받은 위치와 속도를 기반으로 현재 위치를 예측하는 기법
  - 예시: <code>받은 위치 + 속도 * 지연 시간</code>
  - 사용되는 상황: 지연 시간을 보상하여 더 정확한 위치 표현
  - 헷갈릴 수 있는 점: 100\~200ms 정도로 제한하고, 실제 위치와 크게 차이 날 경우 순간 보정 필요

### 수업 흐름별 정리

### 1. 레이트 조인 및 상태 동기화 문제 

- 설명: 방에 뒤늦게 입장한 유저가 기존 유저들이 변경한 월드 상태를 볼 수 없는 문제
- 예시: 기존 유저들이 상자를 파괴하고 문을 열었지만, 새로 들어온 유저는 닫힌 문과 멀쩡한 상자를 봄
- <code>중요:</code> 단순 RPC는 현재 방에 접속 중인 클라이언트에게만 전달되고 결과 상태를 서버에 저장하지 않음 

### 2. Buffered RPC vs Custom Properties 

- 설명: Late-joiner 문제를 해결하는 두 가지 방법의 비교
- 예시: Buffered RPC는 이벤트를 기억하지만 버퍼 관리 문제 발생, Custom Properties는 현재 상태만 저장하여 안정적
- <code>중요:</code> 소규모 팀에서는 Custom Properties로 상태 관리, RPC는 연출(애니메이션)용으로 사용하는 구조가 권장됨 

### 3. 소유권 이전과 경쟁 조건 방지 

- 설명: 두 유저가 동시에 필드 아이템을 주우려 할 때 발생하는 경쟁 조건 처리
- 예시: 마스터 클라이언트가 PhotonNetwork.InstantiateRoomObject로 생성한 아이템을 두 클라이언트가 동시에 Pick up 시도
- <code>중요:</code> 클라이언트는 획득 요청만 보내고, 마스터 클라이언트가 검증 후 가장 먼저 도착한 요청만 처리 

### 4. 마스터 클라이언트 경유 방식 워크플로우 

- 설명: "요청 → 마스터 검증 → 상태 잠금 → 획득 확정 → 전체 동기화 → 아이템 제거" 순서
- 예시: 마스터 클라이언트가 <code>isPicked = true</code>로 상태를 잠그고, RPC로 결과 전파
- 중요한 이유: <code>RequestOwnership()</code>만으로는 중복 획득을 막기 어려워 상태 체크와 잠금 과정 필수

### 5. 모바일 환경의 일시적 단선 처리 

- 설명: Wi-Fi↔LTE 전환이나 터널 통과 시 1\~2초 단선 후 복구 처리
- 예시: <code>RoomOptions.PlayerTtl = 30000</code>, <code>EmptyRoomTtl = 30000</code> 설정
- <code>중요:</code> 동일한 <code>UserId</code> 유지 필수, <code>OnDisconnected</code>에서 <code>PhotonNetwork.ReconnectAndRejoin()</code> 호출 

### 6. 캐릭터 위치 동기화 최적화 

- 설명: PhotonTransformView 사용 시 레이턴시 100ms 이상에서 Jittering 현상 발생
- 예시: <code>OnPhotonSerializeView</code>에서 <code>stream.SendNext(transform.position)</code> 직접 구현
- <code>중요:</code> 수신 즉시 대입하지 않고 목표 위치 저장 후 <code>Update</code>에서 <code>Vector3.Lerp</code>로 보간 

### 7. 보간과 예측 구현 

- 설명: 네트워크 패킷 도착 간격으로 인한 끊김 현상 방지 기법
- 예시: <code>PhotonNetwork.Time - info.SentServerTime</code>으로 지연 시간 계산 후 위치 예측
- 중요한 이유: 전송률을 무작정 높이지 않고 클라이언트 측 보간과 짧은 예측으로 대역폭과 품질 균형 유지

- 헷갈리는 이유: 둘 다 Late-joiner 문제를 해결하지만 방식이 다름

<b>문제 1. \[레이트 조인 및 상태 동기화 문제\]</b>

<b>상황: 방에 뒤늦게 입장한 유저(Late-joiner)가 있습니다. 게임 진행 중 기존 유저들이 상자를 파괴하거나 문을 열어두었는데, 새로 들어온 유저는 상자가 멀쩡히 남아있거나 문이 닫혀있는 상태로 보입니다. 기존 유저들은 이 문을 열 때 PhotonView.RPC를 사용해 다른 클라이언트들에게 연출을 실행하도록 구현해 둔 상태입니다.</b>

<b>질문: 단순 RPC 호출 방식의 어떤 한계 때문에 이 문제가 발생했는지 실무 관점에서 짚어내고, 이를 해결하기 위해 1) Buffered RPC를 사용하는 방법과 2) Custom Properties를 사용하는 방법 중 소규모 팀에서 동기화 버그를 방지하고 유지보수하기에 더 권장되는 방식은 무엇인지 그 이유와 함께 설명하시오.</b>

단순 RPC 호출 방식은 현재 방에 접속해 있는 클라이언트에게만 문 열림이나 상자 파괴 같은 이벤트를 전달할 뿐, 그 결과 상태를 서버에 저장하지 않는다. 따라서 뒤늦게 입장한 Late-joiner는 과거 RPC를 받지 못해 기본 씬 상태인 닫힌 문과 멀쩡한 상자를 보게 된다. Buffered RPC를 사용하면 서버가 RPC 호출을 기억해 나중에 들어온 유저에게도 재실행할 수 있지만, 이벤트가 많아질수록 버퍼가 쌓이고 중복 실행이나 버퍼 정리 문제가 생길 수 있다. 따라서 소규모 팀에서는 문 열림, 상자 파괴, 퍼즐 클리어 여부처럼 결과가 남는 요소를 Custom Properties에 현재 상태로 저장하는 방식이 더 권장된다. RPC는 문 열림 애니메이션 같은 연출용으로 사용하고, 실제 월드 상태는 Custom Properties로 관리하는 구조가 동기화 버그를 줄이고 유지보수하기에 가장 안전하다.

<b>문제 2. \[소유권(Ownership) 이전과 경쟁 조건\]</b>

<b>상황: 필드에 드랍된 아이템 오브젝트가 있습니다. 이 오브젝트는 마스터 클라이언트(Master Client)가 PhotonNetwork.InstantiateRoomObject로 생성한 상태입니다. 이때 클라이언트 A와 클라이언트 B가 동시에 이 아이템을 줍기 위해 상호작용(Pick up)을 시도했습니다.</b>

<b>질문: 두 유저가 동시에 아이템을 획득 처리하여 아이템이 복사되거나, 서버에서 에러가 나는 ‘경쟁 조건(Race Condition)’을 방지해야 합니다. PhotonView.RequestOwnership을 활용하거나 마스터 클라이언트를 경유하는 방식 중, 가장 안전하게 소유권을 체크하고 아이템 획득 처리를 완료하는 실무적인 워크플로우(로직 순서)를 서술하시오.</b>

<br />필드 아이템 획득은 클라이언트가 직접 확정하지 않고, 마스터 클라이언트를 최종 판정자로 두는 방식이 가장 안전하다. 각 클라이언트는 아이템 획득 요청만 마스터 클라이언트에게 보내고, 마스터 클라이언트는 해당 아이템이 아직 획득되지 않았는지 검사한 뒤 가장 먼저 도착한 유효 요청에 대해서만 <code>isPicked = true</code>로 상태를 잠근다. 그 후 획득자를 확정하고 모든 클라이언트에게 결과를 RPC로 전파하여 해당 유저에게만 인벤토리 보상을 지급하고, 나머지 클라이언트에서는 아이템을 제거한다. <code>RequestOwnership()</code>을 사용할 수도 있지만, 단순 소유권 이전만으로는 중복 획득을 막기 어렵기 때문에 반드시 마스터 클라이언트 또는 Custom Properties의 CAS 방식으로 아이템 상태를 먼저 체크하고 잠그는 과정이 필요하다. 따라서 실무적으로는 “요청 → 마스터 검증 → 상태 잠금 → 획득 확정 → 전체 동기화 → 아이템 제거” 순서로 처리하는 것이 가장 안전하다.<br /><br />

<b>문제 3. \[모바일/무선 환경의 일시적 단선 처리\]</b>

<b>상황: 모바일 멀티플레이어 게임을 서비스 중인데, 유저들이 Wi-Fi에서 LTE로 전환되거나 터널을 지날 때 1\~2초간 네트워크가 끊겼다가 복구되는 현상이 빈번히 발생합니다. 기본 설정 상태에서는 단선 즉시 방에서 튕겨 나가고 플레이어 오브젝트가 파괴되어 유저 경험이 매우 나빠집니다.</b>

<b>질문: 유저가 일시적인 단선 후 기존 방으로 부드럽게 재접속(Seamless Reconnect)할 수 있도록 하기 위해, Photon의 특정 설정(예: PlayerTTL, EmptyRoomTTL)을 어떻게 다루어야 하며, 스크립트 단에서 PhotonNetwork.ReconnectAndRejoin()을 활용해 복구하는 프로세스를 간략히 설계하시오.</b>

<br />모바일 환경의 일시적 단선을 부드럽게 처리하려면 방 생성 시 <code>RoomOptions.PlayerTtl</code>을 0보다 크게 설정해 끊긴 플레이어 actor를 일정 시간 inactive 상태로 유지해야 한다. 또한 마지막 유저가 끊겨 방이 비는 상황까지 고려해 <code>EmptyRoomTtl</code>도 설정하여 방 자체가 즉시 제거되지 않도록 한다. 예를 들어 <code>PlayerTtl = 30000</code>, <code>EmptyRoomTtl = 30000</code>처럼 30초 정도의 복귀 가능 시간을 둘 수 있다. 클라이언트는 동일한 <code>UserId</code>를 유지해야 하며, <code>OnDisconnected</code>에서 복구 가능한 단선이면 <code>PhotonNetwork.ReconnectAndRejoin()</code>을 호출한다. 재접속에 성공하면 <code>OnJoinedRoom</code>에서 기존 플레이어 상태와 방 상태를 복원하고, 실패하면 <code>Reconnect()</code> 또는 로비 복귀 처리를 수행한다. 즉, “단선 감지 → actor와 room 유지 → ReconnectAndRejoin 시도 → 성공 시 상태 복원 → 실패 시 일반 재접속/로비 복귀” 순서로 설계하는 것이 실무적으로 안전하다.<br /><br />

<b>문제 4. \[캐릭터 위치 동기화 최적화 및 보간\]</b>

<b>상황: 1인 개발 특성상 빠른 구현을 위해 플레이어 캐릭터에 PhotonTransformView를 붙여서 위치를 동기화하고 있습니다. 테스트 결과, 네트워크 레이턴시(Ping)가 100ms 이상으로 올라가자 다른 플레이어의 움직임이 뚝뚝 끊기는(Jittering) 현상이 발생합니다. 그렇다고 Photon 핑계를 대며 전송률(Serialization Rate)을 무작정 높이면 대역폭 과부하가 올 수 있습니다.</b>

<b>질문: OnPhotonSerializeView를 직접 구현한다고 가정할 때, 단순히 stream.SendNext(transform.position)을 받는 즉시 위치에 대입하는 방식의 문제점을 해결하기 위해 수신 측 클라이언트에서 적용해야 하는 구체적인 보간(Interpolation/Lerp) 및 예측(Extrapolation) 구현 아이디어를 실무적인 관점에서 기술하시오.</b>

<code>OnPhotonSerializeView</code>에서 위치 값을 수신한 즉시 <code>transform.position</code>에 대입하면, 네트워크 패킷이 도착하는 순간마다 캐릭터 위치가 끊겨 보이는 Jittering이 발생한다. 따라서 수신 측에서는 받은 위치를 바로 적용하지 않고 목표 위치로 저장한 뒤, <code>Update</code>에서 <code>Vector3.Lerp</code>, <code>SmoothDamp</code>, <code>Quaternion.Slerp</code> 등을 사용해 부드럽게 보간해야 한다. 또한 위치뿐 아니라 회전, 속도, 서버 전송 시간을 함께 활용하여 <code>PhotonNetwork.Time - info.SentServerTime</code>으로 지연 시간을 계산하고, <code>받은 위치 + 속도 * 지연 시간</code> 형태로 현재 위치를 예측할 수 있다. 다만 Extrapolation은 실제 위치와 크게 어긋날 수 있으므로 100\~200ms 정도로 제한하고, 일정 거리 이상 차이가 날 경우에는 순간 보정해야 한다. 더 안정적인 방식은 여러 위치 스냅샷을 버퍼에 저장한 뒤 약간 과거 시점을 기준으로 두 스냅샷 사이를 보간하는 것이다. 전송률을 무작정 올리기보다는 적절한 SerializationRate와 수신 측 보간, 짧은 예측, Snap 보정을 함께 사용해야 대역폭과 움직임 품질을 균형 있게 관리할 수 있다.<br /><br />

# 문제 1. 레이트 조인 및 상태 동기화 문제

## 아주 쉽게 말하면

게임 방 안에 친구들이 먼저 들어와 있었어요.

친구 A가 상자를 부쉈어요.

> “쾅! 상자 부서졌어!”

친구 B가 문을 열었어요.

> “끼익, 문 열렸어!”

그런데 나중에 친구 C가 방에 들어왔어요.

문제는 친구 C가 그때 방에 없었기 때문에,

예전에 누가 외쳤던 말을 못 들었어요.

그래서 친구 C 화면에는 이렇게 보입니다.

```txt
기존 유저 화면:
상자 부서짐
문 열림

늦게 들어온 유저 화면:
상자 멀쩡함
문 닫힘
```

즉, <b>나중에 들어온 사람은 예전에 있었던 일을 모른다</b>는 것이 문제입니다.

---

## RPC는 무엇인가?

<code>RPC</code>는 쉽게 말하면 <b>방 안에 있는 친구들에게 지금 바로 외치는 말</b>입니다.

```txt
photonView.RPC("OpenDoor",RpcTarget.All);
```

이건 이런 뜻입니다.

> “지금 방 안에 있는 사람들아, 문 여는 동작을 실행해!”

그런데 이 말은 <b>지금 방 안에 있는 사람들만 듣습니다.</b>

나중에 들어온 사람은 그 말을 못 들어요.

그래서 단순 RPC만 쓰면 Late-joiner는 문이 열렸는지, 상자가 부서졌는지 모르게 됩니다.

---

## 왜 문제가 생기는가?

RPC는 <b>사건을 전달하는 기능</b>입니다.

예를 들면,

```txt
문 열어!
상자 부숴!
폭발 이펙트 보여줘!
소리 재생해!
```

이런 “순간 행동”을 전달하는 데 좋습니다.

하지만 RPC는 기본적으로 이런 상태를 저장하지 않습니다.

```txt
문이 현재 열려 있다.
상자가 현재 부서져 있다.
퍼즐이 현재 클리어되어 있다.
아이템이 현재 사라져 있다.
```

즉,

```txt
RPC = 지금 일어난 일을 알려주는 방송
Custom Properties = 현재 상태를 적어두는 칠판
```

이라고 생각하면 됩니다.

---

# Buffered RPC 방식

## Buffered RPC는 무엇인가?

Buffered RPC는 그냥 외치는 것이 아니라,

<b>말한 내용을 녹음해 두는 방송</b>입니다.

```txt
photonView.RPC("OpenDoor",RpcTarget.AllBuffered);
```

이렇게 하면 기존 유저들이 문을 열었을 때, Photon 서버가 이 RPC를 기억해 둡니다.

나중에 들어온 유저에게도,

> “아까 문 열렸었어. 너도 OpenDoor 실행해.”

라고 다시 알려줍니다.

그래서 Late-joiner도 문이 열린 상태를 볼 수 있습니다.

---

## Buffered RPC의 단점

처음에는 좋아 보입니다.

하지만 문제가 있습니다.

Buffered RPC는 <b>현재 상태 하나만 저장하는 게 아니라, 과거에 했던 행동들을 계속 쌓아두는 방식</b>입니다.

예를 들어 이런 일이 있었다고 해볼게요.

```txt
문 열기
상자 1 부수기
상자 2 부수기
상자 3 부수기
몬스터 죽이기
아이템 먹기
퍼즐 클리어하기
```

이걸 전부 Buffered RPC로 저장하면, 나중에 들어온 유저는 이걸 하나씩 다시 실행해야 합니다.

마치 선생님이 새로 온 아이에게 이렇게 말하는 것과 비슷합니다.

> “자, 네가 없을 때 있었던 일 100개를 처음부터 다시 보여줄게.”

처음에는 괜찮지만, 게임이 커질수록 복잡해집니다.

문제도 생길 수 있습니다.

```txt
같은 연출이 두 번 실행됨
버퍼가 너무 많이 쌓임
어떤 RPC를 지워야 할지 헷갈림
나중에 들어온 유저의 입장 시간이 길어짐
```

그래서 Buffered RPC는 간단한 상황에서는 쓸 수 있지만,

상태가 많이 쌓이는 게임에서는 관리가 어려워집니다.

---

# Custom Properties 방식

## Custom Properties는 무엇인가?

Custom Properties는 쉽게 말하면 <b>게임 방의 칠판</b>입니다.

칠판에 이렇게 적어두는 겁니다.

```txt
door_01_open = true
box_03_destroyed = true
puzzle_01_clear = true
```

뜻은 이렇습니다.

```txt
door_01_open = true
1번 문은 열려 있다.

box_03_destroyed = true
3번 상자는 부서져 있다.

puzzle_01_clear = true
1번 퍼즐은 클리어되어 있다.
```

그러면 나중에 들어온 유저는 과거에 무슨 일이 있었는지 하나씩 다시 볼 필요가 없습니다.

그냥 칠판만 보면 됩니다.


<blockquote markdown="1">


“아, 1번 문은 열려 있구나.”

“아, 3번 상자는 이미 부서졌구나.”

</blockquote>


그리고 자기 화면 상태를 바로 맞출 수 있습니다.

---

## 문 열림 예시

문을 열 때 이렇게 상태를 저장합니다.

```txt
Hashtableprops=newHashtable
{
    {"door_01_open",true }
};

PhotonNetwork.CurrentRoom.SetCustomProperties(props);
```

이 뜻은,

> “방의 상태표에 1번 문은 열림이라고 적어줘.”

입니다.

Late-joiner가 들어오면 이 값을 읽습니다.

```txt
if ((bool)PhotonNetwork.CurrentRoom.CustomProperties["door_01_open"])
{
door.OpenImmediately();
}
```

이 뜻은,

> “칠판을 봤더니 문이 열려 있다고 되어 있네? 그럼 내 화면에서도 문을 열어둬야겠다.”

입니다.

---

# 문제 1에서 더 좋은 방식은?

소규모 팀에서는 <b>Custom Properties 방식이 더 좋습니다.</b>

이유는 아주 간단합니다.

문, 상자, 퍼즐, 아이템 같은 것은 단순한 연출이 아니라 <b>게임 월드의 현재 상태</b>이기 때문입니다.

```txt
문 열림 = 상태
상자 파괴됨 = 상태
퍼즐 클리어됨 = 상태
아이템 사라짐 = 상태
```

이런 것은 RPC로 과거 행동을 계속 저장하기보다,

Custom Properties로 현재 상태만 저장하는 것이 관리하기 쉽습니다.

---

## 가장 좋은 구조

실제로는 둘을 같이 쓰면 좋습니다.

```txt
RPC = 지금 보고 있는 유저들에게 문 열림 애니메이션 보여주기
Custom Properties = 문이 열렸다는 결과 상태 저장하기
```

즉,

```txt
기존 유저:
RPC로 문 열림 애니메이션을 본다.

나중에 들어온 유저:
Custom Properties를 보고 문이 이미 열린 상태로 맞춘다.
```

이 구조가 가장 안전합니다.

---

## 문제 1 최종 답안 느낌

> 단순 RPC는 현재 방에 있는 클라이언트에게만 문 열림이나 상자 파괴 같은 이벤트를 전달한다. 나중에 들어온 Late-joiner는 과거 RPC를 받지 못하므로 기본 씬 상태를 보게 된다. Buffered RPC를 사용하면 과거 RPC를 나중에 들어온 유저에게도 실행할 수 있지만, 이벤트가 많아질수록 버퍼가 쌓이고 중복 실행이나 관리 문제가 생길 수 있다. 따라서 소규모 팀에서는 문 열림, 상자 파괴, 퍼즐 클리어 여부처럼 결과가 남는 요소를 Custom Properties에 현재 상태로 저장하는 방식이 더 권장된다. RPC는 연출용, Custom Properties는 상태 저장용으로 분리하는 것이 유지보수와 동기화 안정성 면에서 좋다.

# 문제 2. 소유권 이전과 경쟁 조건

## 아주 쉽게 말하면

바닥에 사탕이 하나 떨어져 있습니다. 🍬

친구 A가 사탕을 집으려고 했어요.

친구 B도 동시에 사탕을 집으려고 했어요.

둘 다 자기 마음대로

> “이 사탕 내 거야!”

라고 해버리면 어떻게 될까요?

문제가 생깁니다.

```txt
A도 사탕을 얻음
B도 사탕을 얻음
사탕은 하나였는데 두 개가 된 것처럼 보임
```

이게 바로 <b>경쟁 조건</b>, Race Condition입니다.

즉, 여러 사람이 동시에 같은 물건을 가지려고 할 때,

누가 진짜로 가져갔는지 정하지 않으면 문제가 생깁니다.

---

## 아이템 획득에서 하면 안 되는 것

클라이언트 A가 자기 화면에서 바로 이렇게 하면 위험합니다.

```txt
AddItemToInventory();
PhotonNetwork.Destroy(item);
```

왜냐하면 B도 거의 동시에 똑같이 할 수 있기 때문입니다.

그러면 둘 다 자기 화면에서는 성공했다고 생각합니다.

```txt
A 화면: 내가 먹었다!
B 화면: 나도 먹었다!
서버: 잠깐, 사탕은 하나였는데?
```

그래서 아이템 획득은 각 클라이언트가 마음대로 확정하면 안 됩니다.

---

# 가장 안전한 방식

가장 안전한 방식은 <b>마스터 클라이언트가 선생님 역할을 하는 것</b>입니다.

아이템을 먹고 싶은 사람은 선생님에게 말합니다.

```txt
A: 선생님, 저 사탕 먹어도 돼요?
B: 선생님, 저도 사탕 먹어도 돼요?
```

선생님은 먼저 도착한 요청을 보고 판단합니다.

```txt
선생님:
사탕이 아직 있네?
그럼 A에게 줄게.
이제 사탕은 없음으로 표시!
```

그다음 B가 요청하면,

```txt
선생님:
이미 A가 가져갔어.
B는 실패.
```

이렇게 하면 사탕이 두 개로 복사되지 않습니다.

---

# 실제 로직 순서

## 1단계. 클라이언트는 요청만 보낸다

A와 B는 아이템을 바로 먹지 않습니다.

그냥 마스터 클라이언트에게 요청합니다.

```txt
photonView.RPC(
"RequestPickupItem",
RpcTarget.MasterClient,
itemViewID,
PhotonNetwork.LocalPlayer.ActorNumber
);
```

뜻은 이겁니다.

> “마스터 클라이언트님, 제가 이 아이템 먹어도 되나요?”

---

## 2단계. 마스터 클라이언트가 아이템 상태를 확인한다

마스터는 아이템이 이미 먹혔는지 확인합니다.

```txt
if (isPicked)
{
return;
}
```

뜻은 이겁니다.

```txt
이미 누가 먹었으면 거절
아직 남아 있으면 다음 단계 진행
```

---

## 3단계. 마스터가 먼저 아이템을 잠근다

가장 중요한 부분입니다.

마스터는 보상을 주기 전에 먼저 아이템을 잠급니다.

```txt
isPicked=true;
```

이 뜻은,

> “이 아이템은 이제 누가 가져가는 중이니까 다른 사람은 못 가져감!”

입니다.

이걸 먼저 해야 합니다.

순서가 중요합니다.

```txt
좋은 순서:
아이템 상태 확인
→ 아이템 잠금
→ 획득자 확정
→ 보상 지급
→ 아이템 제거

나쁜 순서:
보상 지급
→ 아이템 제거
→ 나중에 잠금
```

나쁜 순서로 하면 짧은 순간에 다른 유저 요청이 끼어들 수 있습니다.

---

## 4단계. 마스터가 획득자를 확정한다

예를 들어 A의 요청이 먼저 왔다면,

```txt
획득자 = A
```

로 정합니다.

그리고 모든 클라이언트에게 말합니다.

```txt
photonView.RPC(
"ConfirmPickupItem",
RpcTarget.AllViaServer,
itemViewID,
pickedActorNumber
);
```

뜻은 이겁니다.

> “이 아이템은 A가 먹었습니다. 모두 화면에서 아이템을 없애세요.”

---

## 5단계. 획득한 사람만 인벤토리에 넣는다

모든 클라이언트가 결과를 받습니다.

```txt
if (PhotonNetwork.LocalPlayer.ActorNumber==pickedActorNumber)
{
AddItemToInventory();
}

HideOrDestroyItem(itemViewID);
```

뜻은 이렇습니다.

```txt
내가 획득자로 지정되었으면 인벤토리에 추가
내가 획득자가 아니면 그냥 아이템만 사라지게 처리
모든 사람 화면에서 아이템 제거
```

# RequestOwnership은 어떻게 봐야 할까?

<code>RequestOwnership()</code>은 쉽게 말하면,

> “이 물건을 제가 조종해도 되나요?”

라고 묻는 기능입니다.

하지만 아이템 획득에서는 단순히 조종권을 가져오는 것보다 더 중요한 것이 있습니다.

바로,

```txt
이 아이템이 아직 남아 있는가?
누가 먼저 요청했는가?
중복 획득이 발생하지 않는가?
```

입니다.

그래서 <code>RequestOwnership()</code>을 쓰더라도 마스터가 반드시 확인해야 합니다.

```txt
RequestOwnership 요청
→ 마스터가 아이템 상태 확인
→ 아직 안 먹혔으면 isPicked = true
→ 소유권 이전 또는 획득 확정
→ 전체에 결과 전파
```

즉, <b>소유권 이전만 믿으면 안 되고, 상태 잠금이 반드시 필요합니다.</b>

---

## 문제 2 최종 답안 느낌

> 필드 아이템 획득은 각 클라이언트가 직접 확정하지 않고, 마스터 클라이언트를 최종 판정자로 두는 방식이 가장 안전하다. 클라이언트 A와 B는 아이템을 바로 인벤토리에 넣지 않고 마스터 클라이언트에게 획득 요청만 보낸다. 마스터 클라이언트는 아이템이 이미 획득되었는지 검사하고, 아직 남아 있다면 먼저 <code>isPicked = true</code>로 상태를 잠근 뒤 가장 먼저 도착한 유효 요청자를 획득자로 확정한다. 이후 모든 클라이언트에게 결과를 전파하여 획득자에게만 보상을 지급하고, 모든 화면에서 아이템을 제거한다. <code>RequestOwnership()</code>을 사용할 수도 있지만, 단순 소유권 이전만으로는 중복 획득을 막기 어렵기 때문에 반드시 마스터 클라이언트가 상태를 체크하고 잠그는 과정이 필요하다.

# 문제 3. 모바일/무선 환경의 일시적 단선 처리

## 아주 쉽게 말하면

친구들이 놀이터에서 같이 놀고 있습니다.

그런데 친구 한 명이 잠깐 화장실에 갔어요.

선생님이 바로 이렇게 하면 안 좋겠죠?

> “이 친구는 나갔으니까 자리 치워!”

잠깐 뒤에 친구가 돌아왔는데, 자기 자리가 없어져 있으면 슬픕니다.

네트워크도 비슷합니다.

모바일 게임에서 유저가 Wi-Fi에서 LTE로 바뀌거나, 터널에 들어가면 1\~2초 정도 연결이 끊길 수 있습니다.

이때 게임이 바로 유저를 방에서 쫓아내고 플레이어 오브젝트를 지워버리면, 유저 경험이 나빠집니다.

그래서 Photon에게 이렇게 말해야 합니다.

> “유저가 잠깐 끊겨도 바로 지우지 말고, 조금만 기다려줘.”

이걸 위해 쓰는 설정이 <code>PlayerTTL</code>과 <code>EmptyRoomTTL</code>입니다.

---

# PlayerTTL이란?

<code>PlayerTTL</code>은 쉽게 말하면 <b>잠깐 끊긴 플레이어의 자리를 얼마나 오래 남겨둘지</b>입니다.

```txt
options.PlayerTtl=30000;
```

이건 이런 뜻입니다.

```txt
플레이어가 끊겨도 30초 동안은 자리를 남겨둬.
```

30초 안에 다시 돌아오면 기존 방으로 복귀할 수 있습니다.

---

## PlayerTTL이 0이면?

기본값처럼 <code>PlayerTTL</code>이 0이면, 끊기는 순간 바로 나간 것으로 처리될 수 있습니다.

```txt
연결 끊김
→ 플레이어 제거
→ 오브젝트 파괴
→ 다시 들어와도 기존 상태 복구 어려움
```

모바일 게임에서는 이러면 너무 불편합니다.

1\~2초 끊겼을 뿐인데 게임에서 쫓겨나는 느낌이 되기 때문입니다.

---

# EmptyRoomTTL이란?

<code>EmptyRoomTTL</code>은 쉽게 말하면 <b>방이 비었을 때 방 자체를 얼마나 오래 남겨둘지</b>입니다.

```txt
options.EmptyRoomTtl=30000;
```

이건 이런 뜻입니다.

```txt
방에 사람이 아무도 없어도 30초 동안 방을 지우지 마.
```

예를 들어 1인 방에서 유저가 잠깐 끊겼다고 해볼게요.

<code>PlayerTTL</code>만 있고 <code>EmptyRoomTTL</code>이 없으면, 플레이어 자리는 남아 있어도 방 자체가 없어질 수 있습니다.

그러면 다시 돌아갈 집이 사라진 셈입니다. 🏠

그래서 모바일에서는 보통 둘 다 설정합니다.

```txt
RoomOptionsoptions=newRoomOptions
{
PlayerTtl=30000,
EmptyRoomTtl=30000
};

PhotonNetwork.CreateRoom("Room_01",options);
```

---

# ReconnectAndRejoin이란?

<code>PhotonNetwork.ReconnectAndRejoin()</code>은 쉽게 말하면,

> “방금 끊긴 그 방으로 다시 돌아가게 해줘.”

라고 Photon에게 요청하는 함수입니다.

그냥 새로 접속하는 것이 아니라,

기존에 있던 방과 기존 플레이어 자리로 돌아가려고 하는 기능입니다.

---

# 재접속 과정

## 1단계. 방을 만들 때 TTL 설정

처음 방을 만들 때 이렇게 설정합니다.

```txt
RoomOptionsoptions=newRoomOptions
{
PlayerTtl=30000,
EmptyRoomTtl=30000
};

PhotonNetwork.CreateRoom("Room_01",options);
```

뜻은 이겁니다.

```txt
플레이어가 끊겨도 30초 기다려줘.
방이 비어도 30초 기다려줘.
```

---

## 2단계. 같은 유저인지 알아볼 수 있게 UserId 유지

Photon이 “아까 그 유저가 다시 왔구나”라고 알아야 합니다.

그래서 UserId를 고정해두는 것이 좋습니다.

```txt
PhotonNetwork.AuthValues=newAuthenticationValues(userId);
```

쉽게 말하면 이름표입니다.

```txt
이름표가 같아야
Photon이 같은 유저라고 알아봄
```

---

## 3단계. 연결이 끊기면 OnDisconnected에서 감지

```txt
publicoverridevoidOnDisconnected(DisconnectCausecause)
{
PhotonNetwork.ReconnectAndRejoin();
}
```

뜻은 이겁니다.

```txt
연결 끊김 감지
→ 바로 기존 방 재접속 시도
```

---

## 4단계. 재접속 성공 시 상태 복원

재접속에 성공하면 <code>OnJoinedRoom()</code>이 다시 호출됩니다.

```txt
publicoverridevoidOnJoinedRoom()
{
if (PhotonNetwork.LocalPlayer.HasRejoined)
    {
RestorePlayerState();
    }
}
```

여기서 해야 할 일은 다음과 같습니다.

```txt
플레이어 위치 복원
체력 복원
인벤토리 복원
문 상태 복원
상자 파괴 상태 복원
아이템 상태 복원
```

이 상태들은 보통 Custom Properties나 별도 데이터로 저장해두는 것이 좋습니다.

---

## 5단계. 재접속 실패도 처리해야 한다

항상 성공하는 것은 아닙니다.

예를 들어,

```txt
30초가 지나 PlayerTTL이 끝남
방이 삭제됨
인터넷이 너무 오래 끊김
UserId가 바뀜
```

이런 경우에는 기존 방으로 못 돌아갈 수 있습니다.

그러면 일반 재접속이나 로비 이동을 해야 합니다.

```txt
boolresult=PhotonNetwork.ReconnectAndRejoin();

if (!result)
{
PhotonNetwork.Reconnect();
}
```

---

## 문제 3 최종 답안 느낌

> 모바일 환경에서는 Wi-Fi와 LTE 전환, 터널 진입 등으로 1\~2초 정도의 일시적 단선이 자주 발생할 수 있다. 이때 기본 설정처럼 단선 즉시 플레이어를 방에서 제거하면 플레이어 오브젝트가 파괴되어 유저 경험이 나빠진다. 따라서 방 생성 시 <code>RoomOptions.PlayerTtl</code>을 0보다 크게 설정하여 끊긴 플레이어를 일정 시간 inactive actor로 유지하고, <code>EmptyRoomTtl</code>도 설정하여 방이 비어도 즉시 삭제되지 않도록 해야 한다. 예를 들어 두 값을 30초 정도로 설정할 수 있다. 클라이언트는 동일한 <code>UserId</code>를 유지해야 하며, <code>OnDisconnected</code>에서 <code>PhotonNetwork.ReconnectAndRejoin()</code>을 호출해 기존 방으로 재접속을 시도한다. 성공하면 <code>OnJoinedRoom</code>에서 위치, 체력, 인벤토리, 월드 상태를 복원하고, 실패하면 일반 재접속이나 로비 복귀 처리를 수행한다.

---

# 문제 4. 캐릭터 위치 동기화 최적화 및 보간

## 아주 쉽게 말하면

친구가 운동장에서 달리고 있습니다.

그런데 내가 친구를 매 순간 보는 게 아니라,

사진을 1초에 몇 장씩만 받는다고 생각해볼게요.

사진이 이렇게 도착합니다.

```txt
사진 1: 친구가 왼쪽에 있음
사진 2: 친구가 가운데 있음
사진 3: 친구가 오른쪽에 있음
```

그런데 사진이 올 때마다 친구 위치를 바로 순간이동시키면 이렇게 보입니다.

```txt
툭!
툭!
툭!
```

움직임이 부드럽지 않고 끊겨 보입니다.

이게 Jittering입니다.

---

# 왜 바로 대입하면 안 될까?

이렇게 하면 안 좋습니다.

```txt
transform.position=receivedPosition;
```

왜냐하면 네트워크 위치 정보는 매 프레임 오는 것이 아니기 때문입니다.

예를 들어 게임은 1초에 60번 화면을 그리는데,

네트워크 위치 정보는 1초에 10번 정도만 올 수 있습니다.

그러면 중간 움직임이 비어 있습니다.

```txt
화면은 60번 움직이고 싶음
위치 정보는 10번만 옴
중간이 비어서 끊겨 보임
```

그래서 수신 측에서 중간을 부드럽게 이어줘야 합니다.

이게 <b>보간</b>, Interpolation입니다.

---

# Interpolation, 보간이란?

보간은 쉽게 말하면 <b>중간 길을 만들어주는 것</b>입니다.

친구가 A 위치에서 B 위치로 갔다고 합시다.

```txt
A ---------------- B
```

위치 정보를 바로 B로 순간이동시키는 것이 아니라,

A에서 B까지 천천히 이동하게 만듭니다.

```txt
transform.position=Vector3.Lerp(
transform.position,
networkPosition,
Time.deltaTime*10f
);
```

이 뜻은,

> “현재 위치에서 목표 위치까지 부드럽게 따라가.”

입니다.

---

# 송신 측에서는 무엇을 보내야 할까?

위치만 보내면 정보가 부족합니다.

```txt
stream.SendNext(transform.position);
```

이것만 보내면 수신 측은 이렇게밖에 모릅니다.

```txt
상대가 어디에 있었는지
```

하지만 이런 것도 알면 더 좋습니다.

```txt
어느 방향을 보고 있었는지
얼마나 빠르게 움직이고 있었는지
```

그래서 보통 이렇게 보냅니다.

```txt
stream.SendNext(transform.position);
stream.SendNext(transform.rotation);
stream.SendNext(rb.velocity);
```

즉,

```txt
위치
회전
속도
```

를 함께 보냅니다.

---

# 수신 측에서는 어떻게 해야 할까?

받은 위치를 바로 넣지 말고, 목표 위치로 저장합니다.

```txt
networkPosition=receivedPosition;
networkRotation=receivedRotation;
networkVelocity=receivedVelocity;
```

그리고 <code>Update()</code>에서 천천히 따라가게 합니다.

```txt
privatevoidUpdate()
{
if (photonView.IsMine)return;

transform.position=Vector3.Lerp(
transform.position,
networkPosition,
Time.deltaTime*10f
    );

transform.rotation=Quaternion.Slerp(
transform.rotation,
networkRotation,
Time.deltaTime*10f
    );
}
```

이렇게 하면 다른 플레이어가 훨씬 부드럽게 움직입니다.

---

# Extrapolation, 예측이란?

예측은 쉽게 말하면,

> “상대가 지금쯤 여기쯤 왔겠지?”

하고 추측하는 것입니다.

네트워크로 받은 위치는 사실 “지금 위치”가 아니라 “조금 전 위치”입니다.

Ping이 100ms라면,

내가 받은 위치는 약 0.1초 전 상대의 위치일 수 있습니다.

그래서 속도를 이용해서 계산합니다.

```txt
예상위치=받은위치+속도*지연시간
```

코드로는 이렇게 볼 수 있습니다.

```txt
doublelag=PhotonNetwork.Time-info.SentServerTime;
networkPosition=receivedPosition+receivedVelocity* (float)lag;
```

뜻은 이겁니다.

```txt
받은 위치에서
지연된 시간만큼
속도 방향으로 조금 더 이동한 위치를 목표로 삼기
```

---

# 예측은 너무 많이 하면 안 된다

예측은 좋지만, 너무 오래 하면 위험합니다.

예를 들어 상대가 앞으로 가다가 갑자기 멈췄는데,

내 화면에서는 계속 앞으로 간다고 예측할 수 있습니다.

그러면 실제 위치와 내 화면 위치가 크게 달라집니다.

그래서 예측 시간은 짧게 제한해야 합니다.

```txt
floatmaxExtrapolationTime=0.2f;
```

보통 0.1초에서 0.2초 정도만 짧게 예측하는 것이 안전합니다.

```txt
floatlag=Mathf.Clamp(
    (float)(PhotonNetwork.Time-info.SentServerTime),
0f,
maxExtrapolationTime
);
```

---

# 너무 멀어지면 Snap 보정

부드럽게 이동하는 것도 중요하지만,

가끔은 바로 맞춰야 할 때가 있습니다.

예를 들어 상대가 순간이동했거나, 리스폰했거나, 넉백을 크게 당했다면,

Lerp로 천천히 따라가면 이상해 보입니다.

그래서 너무 멀리 떨어져 있으면 즉시 위치를 맞춥니다.

```txt
floatdistance=Vector3.Distance(transform.position,networkPosition);

if (distance>snapDistance)
{
transform.position=networkPosition;
}
```

쉽게 말하면,

```txt
조금 차이남 → 부드럽게 따라가기
너무 많이 차이남 → 바로 위치 맞추기
```

입니다.

---

# 스냅샷 버퍼 방식

더 좋은 방식은 위치 기록을 여러 장 모아두는 것입니다.

사진첩처럼요. 📸

```txt
10.0초 위치 A
10.1초 위치 B
10.2초 위치 C
```

그리고 현재 시간을 바로 그리지 않고, 아주 조금 과거를 그립니다.

예를 들어 현재가 10.3초라면 10.2초 위치를 그립니다.

왜냐하면 0.1초 정도 뒤에서 보면, 이미 받은 위치 정보가 있어서 두 위치 사이를 부드럽게 이어줄 수 있기 때문입니다.

```txt
A와 B 사이를 부드럽게 이동
B와 C 사이를 부드럽게 이동
```

이 방식은 패킷이 조금 불규칙하게 와도 움직임이 덜 흔들립니다.

## 문제 4 최종 답안 느낌

> <code>OnPhotonSerializeView</code>에서 위치를 수신한 즉시 <code>transform.position</code>에 대입하면, 네트워크 패킷이 도착하는 순간마다 캐릭터가 순간이동하듯 움직여 Jittering이 발생한다. 따라서 수신 측에서는 받은 위치를 바로 적용하지 않고 목표 위치로 저장한 뒤, <code>Update</code>에서 <code>Vector3.Lerp</code>, <code>SmoothDamp</code>, <code>Quaternion.Slerp</code> 등을 사용해 부드럽게 보간해야 한다. 또한 위치뿐 아니라 회전, 속도, 서버 전송 시간을 함께 보내면 <code>PhotonNetwork.Time - info.SentServerTime</code>으로 지연 시간을 계산하고, <code>받은 위치 + 속도 * 지연 시간</code> 형태로 현재 위치를 예측할 수 있다. 다만 Extrapolation은 실제 위치와 어긋날 수 있으므로 100\~200ms 정도로 제한하고, 일정 거리 이상 차이가 나면 Snap으로 즉시 보정해야 한다. 더 안정적인 방식은 여러 위치 스냅샷을 버퍼에 저장한 뒤 약간 과거 시점을 기준으로 두 스냅샷 사이를 보간하는 것이다.
