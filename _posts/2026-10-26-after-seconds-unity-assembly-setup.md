## 오늘의 목표

After Seconds는 맞힌 대상과 3초 뒤 자리를 바꾸는 규칙을 중심으로 만드는 1인칭 퍼즐 액션 게임입니다. 오늘은 연구소 공간과 에셋 방향을 정리하고, Unity에서 게임 규칙을 구현하기 위한 코드 계층을 나누었습니다.

현재는 초기 프로젝트를 준비하는 단계입니다. 기능을 한꺼번에 구현하기보다 **직접 분석 → 의사코드 → 작은 구현 → 확인** 순서로 진행하기로 했습니다.

## 연구소 시안과 에셋 후보 정리

먼저 연구소의 외관·지하 단면과 6개 층 평면도 시안을 만들었습니다. 전체 이미지는 공간의 분위기와 층 사이 관계를 살펴보는 용도로 두고, 기존 방별 배치와 치수는 따로 유지했습니다. 이미지에 나타난 문 위치나 통로가 실제 퍼즐에서도 적절한지는 이후 그레이박스로 확인해야 합니다.

에셋은 완성된 방을 한 덩어리로 생성하는 대신 문짝, 문틀, 레일, 장비 본체처럼 부위별로 나누는 방향을 정했습니다. 공통 스타일 문구를 고정하고 대상 설명만 교체해 후보 사이의 톤을 맞추었습니다.

오늘 생성한 후보는 무거운 궤짝 본체, 관제 콘솔 베이스, 원심분리기 본체, 에어록 문짝, 회색 플레이어 더미, 주황색 경비 더미입니다. 이미지와 3D 생성 결과는 확인했지만, Unity 반입과 실제 크기·피벗·충돌체·리깅 검수는 아직 하지 않았습니다.

이 내용을 기획서 V0.09에 반영하고, Unity 6000.4.0f1과 URP 17.4.0으로 초기 프로젝트를 준비했습니다.

## 계층의 책임부터 나누기

기존 Unity 프로젝트의 어셈블리 분리 방식을 참고하면서, After Seconds에서는 게임 규칙 계산을 Unity 기능에서 분리하는 방향으로 정리했습니다.

특히 예약 큐와 교환 판정은 나중에 미리보기에서도 사용할 계산입니다. 같은 규칙을 실제 진행과 예측에 각각 구현하면 결과가 달라질 수 있으므로, 순수 C#으로 계산하는 계층을 따로 두려고 합니다.

| 계층 | 담당할 일 | 예시 |
| --- | --- | --- |
| Define | 공통 데이터와 계약 | 대상 ID, 상태, 예약 데이터, 규칙 설정값 |
| Simulator | 시간과 게임 규칙 계산 | 예약 순서 처리, 교환 판정 |
| System | Unity 기능과 규칙 데이터 연결 | 입력, Raycast, Transform 반영 |
| UI | 전달받은 정보 표시 | 탄약, 예약 목록, 남은 시간 |
| Manager | 세션 생성·종료·재시작 | 설정과 예약 큐 생성, 초기화 |
| Presenter | 요청과 결과의 전달 | 명중 대상의 교환 요청, 결과를 표시 쪽에 전달 |

예를 들어 교환이 일어나면 Simulator가 두 대상의 위치 데이터를 바꾸고, System이 그 결과를 실제 Unity 오브젝트에 반영하도록 나눕니다. Presenter는 이 요청과 결과를 연결합니다. 이 흐름은 앞으로 구현할 설계이며, 오늘 교환 기능까지 만든 것은 아닙니다.

## 폴더 생성에서 참조 설정까지

처음에는 여섯 계층의 폴더와 asmdef를 만들었습니다. 파일을 확인해 보니 각 asmdef에 이름만 저장되어 있어, 순수 C# 계층의 엔진 참조 제한과 계층 사이 참조를 별도로 설정해야 했습니다.

폴더는 코드를 분류하고, asmdef는 어떤 어셈블리의 타입을 사용할 수 있는지 정합니다. 따라서 폴더 생성 다음에는 실제 참조 방향을 설정하는 작업이 필요했습니다.

오늘 저장한 설정은 다음과 같습니다.

- `DefineAD`: `No Engine References`를 켜고 프로젝트 내부 참조는 비워 두었습니다.
- `SimulatorAD`: 같은 옵션을 켜고 `DefineAD`를 참조하도록 설정했습니다.
- `SystemAD`, `UI_AD`, `ManagerAD`, `PresenterAD`: 어셈블리를 생성한 초기 상태로 두었습니다. 실제 코드에서 필요해질 때 허용 범위에 맞춰 참조를 추가합니다.

현재 참조 방향은 `SimulatorAD → DefineAD`입니다. Simulator에서 Define의 데이터를 사용하고, Define은 Simulator를 참조하지 않습니다. `No Engine References`는 UnityEngine과 UnityEditor 참조가 자동으로 추가되지 않게 하는 옵션입니다. 두 계층이 Unity 기능에 기대지 않도록 만드는 출발점입니다. [Unity 공식 asmdef 옵션 설명](https://docs.unity3d.com/6000.4/Documentation/Manual/class-AssemblyDefinitionImporter.html)

기본 SampleScene도 프로젝트 전용 씬 폴더로 이동했습니다. 씬의 내용과 GUID는 유지됐고, 빌드 설정에 저장된 씬 경로도 새 위치를 가리키는 것을 확인했습니다.

## 오늘 확인한 범위

확인은 저장된 파일을 기준으로 진행했습니다.

- asmdef 여섯 개가 생성되어 있습니다.
- `DefineAD`와 `SimulatorAD`에 `noEngineReferences: true`가 저장되어 있습니다.
- `SimulatorAD`의 GUID 참조가 실제 `DefineAD`를 가리킵니다.
- 이동한 씬의 내용과 GUID, 빌드 설정의 경로를 확인했습니다.

게임 규칙을 구현한 C# 파일은 아직 없습니다. Unity Console의 오류 유무와 실제 컴파일·플레이 테스트도 이번 기록에서는 확인하지 않았습니다. 오늘 완료한 범위는 폴더와 어셈블리 생성, 두 순수 C# 계층의 참조 설정까지입니다.

## 다음 작업

다음에는 Unity Console 상태를 확인하고, Define에서 대상 하나를 어떤 데이터로 표현할지 분석합니다. 대상의 식별자, 현재 상태와 위치, 규칙 설정, 예약 데이터에 필요한 최소 필드를 먼저 적어 볼 예정입니다.

그다음 `ScheduleSwap`, `AdvanceTo`, `ExecuteSwap` 의사코드를 작성합니다. 같은 시각의 예약 순서, 시간이 처리 시각을 지나친 경우, 움직이거나 사라진 대상, 재시작 시 초기화를 어떻게 다룰지 설명한 뒤 작은 구현으로 확인하려고 합니다.

손의 힘이 3초 뒤 적용되는 A안과 즉시 적용되는 B안은 **프로토타입으로 비교한 뒤 결정**합니다. 지금은 그 비교를 진행할 기반인 계층 분리와 데이터 설계부터 이어갑니다.
