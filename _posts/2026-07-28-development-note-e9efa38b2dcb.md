## 프로젝트 개요

- <b>프로젝트명:</b> 침몽도시: 루시드 다이버(Lucid Diver)
- <b>진행 기간:</b> 2026.06.11 \~ 2026.07.28
- <b>팀명 / 팀원 구성:</b> REMnants — 장수영(CP), 우성혁(CD), 김남해(PD), 송예찬(PM), 강다영(TD)
- <b>본인 역할:</b> PM 업무와 기획·개발 업무를 병행
- <b>한 줄 소개:</b> P0/P0.5 우선순위와 일정 흐름을 관리하는 한편, 기획자·개발자로서 세계관 속 포식자 ’꿈식자’를 실제 플레이를 압박하는 프로덕션 AI로 구현했습니다.

PM 업무와 에너미 AI 업무는 서로 다른 역할 축입니다. PM으로는 일정과 협업 흐름을 관리했고, 별도의 기획자·개발자 역할로 꿈식자의 콘셉트과 AI를 설계·구현했습니다.

## 프로젝트 목표 및 결과

### 1. 초기 목표

프로젝트의 목표는 완성형 게임 전체를 만드는 것이 아니라, <b>PvE 익스트랙션 루프와 서브컬처 캐릭터 애착 요소가 하나의 플레이 사이클에서 결합될 수 있는지 검증하는 버티컬 슬라이스</b>를 완성하는 것이었습니다.

- <b>PM 목표</b>
  - 7주 안에 검증해야 할 P0 범위를 명확히 하고 P0.5와 구분
  - 전체 일정, 주별 마일스톤, 일별 진행 상황을 한 흐름으로 연결
  - 지연·이월 항목과 협업 일정을 지속적으로 갱신
- <b>기획·개발 목표</b>
  - 꿈식자를 단순히 맵을 돌아다니는 장애물이 아니라 꿈과 기억을 먹는 세계관 속 포식자로 설계
  - 기본 적이라는 성격에 맞게 2\~3마리가 배회하며 플레이어의 이동 경로와 탈출 판단을 압박
  - 시야·소리·마지막 인지 위치처럼 추적의 근거를 드러내고, 플레이어에게 우회와 이탈 가능성도 제공

초기 몬스터 콘셉트 문서에서는 꿈식자를 다음과 같이 정의했습니다.

> “침몽도시 골목길을 2\~3마리씩 배회하는 하위 침식체”

이후 P0.5 명세에서 소리 조사, 추격 기억, 먹잇감 차단 이동, 루시드 낙인과 복귀 조건을 연결해 익스트랙션 장르의 시간·경로 압박을 강화했습니다.

### 2. 최종 결과물

- 인트로에서 로비·출격 준비·인게임·결과로 이어지는 버티컬 슬라이스 플레이 흐름
- 이동→전투→루팅→아이템→탈출을 행동 이벤트로 학습하는 튜토리얼 런타임
- 스폰→순찰→감지→조사→추격→공격→재탐색→복귀가 이어지는 꿈식자 AI 행동 루프
- 시야·근접·소리 감지, 소음 앵커 조사, 시간 기반 어그로, 예측 추격, 2단 돌진 공격, 개별 순찰 복귀
- 전체 일정표, 주별 마일스톤, 일별 일정, 개인 개발일지와 주간 개발일지가 연결된 업무 기록 체계
- 발표에 사용할 상태별 이미지·GIF, 트러블슈팅 Before/After와 인터랙티브 FSM 참고 시안

### 3. 목표 대비 성과

#### 정량 지표

- 총 프로젝트 기간: 약 7주
- 개인 개발일지: 저장소 기준 <b>33개 작성일</b> 기록
- PM 주간 개발일지: <b>5개 주차</b>의 최신본 운영
- 꿈식자 런타임 상태: <code>Idle</code>, <code>Patrol</code>, <code>Investigate</code>, <code>Return</code>, <code>Chase</code>, <code>Attack</code>, <code>Dead</code>의 <b>7개 enum 상태</b>
- 발표용 행동 흐름: 스폰을 포함한 <b>8단계 흐름</b>으로 시각화
- 상태별 시연 GIF 8종과 대표 트러블슈팅 Before/After 4종 제작

> 스폰은 FSM enum 상태가 아니라 생성과 초기화 단계입니다. 재탐색은 별도 enum을 늘리지 않고 <code>Investigate</code> 상태와 마지막 인지 위치 기억을 재사용했습니다.

#### 정성 지표

- <b>PM 성과:</b> 일정표를 단순 일정 목록으로 두지 않고, 전체 일정→주별 마일스톤→일별 일정→개인 개발일지→주간 개발일지→다음 일정 조정으로 이어지는 업무지도로 구성했습니다.
- <b>기획 성과:</b> 익스트랙션에서 오래 탐색할수록 위험이 누적되고, 전투·우회·탈출을 판단하게 만드는 적의 역할을 구체화했습니다.
- <b>개발 성과:</b> 테스트용 더미 에너미를 기초로 실제 게임용 FSM과 기억·감지·이동·전투·복귀 모듈을 설계하고 안정화했습니다.
- <b>문서화 성과:</b> 기획 의도, 실제 구현, 협업 범위, 발표용 시각자료를 서로 교차 확인할 수 있는 근거로 남겼습니다.

## 스크럼 회고

### 1. 협업 방식

PM 업무지도

![PM 업무지도](/assets/img/uploads/notion/9422fab630e3355bbc96ae13a676e155f3c3177a5537a105367710e64b340d67.png)

- <b>Notion 운영 허브:</b> 전체 일정표→주별 마일스톤→일별 일정표→팀원 일일 개발일지→PM 주간 개발일지를 연결했습니다.
- <b>P0/P0.5 분리:</b> 기능의 중요도와 안정화 시점을 기준으로 반드시 검증할 범위와 후속 확장 범위를 구분했습니다.
- <b>주간 갱신:</b> 팀원의 진행·이슈·이월 항목을 주간 개발일지로 취합하고 다음 주 일정에 반영했습니다.
- <b>역할 병행:</b> PM 일정 관리와 기획·개발 실무를 분리해서 설명하고, 각 역할에서 발생한 작업을 별도로 기록했습니다.
- <b>Git·문서 기반 공유:</b> 구두 합의만으로 끝내지 않고 명세, 개발일지, 코드와 실행 결과를 함께 남겼습니다.

### 2. 잘 진행된 점

#### 업무 공유 구조를 한 흐름으로 연결했다

전체 일정과 개인 작업 기록을 따로 관리하지 않고 위에서 아래로 연결했습니다. 덕분에 특정 기능이 어느 주차 목표에 속했는지, 왜 이월되었는지, 다음 일정에 어떤 영향을 주는지를 추적할 수 있었습니다.

#### 기획 의도를 직접 실행 가능한 구조로 검증했다

꿈식자를 “무리형 포식자”라고 문서에 쓰는 데서 끝내지 않고, 각 개체가 자기 루트와 기억을 가지면서도 같은 자극에 반응해 경로를 압박하도록 구현했습니다. 문서와 실행 결과의 오차를 직접 확인하고 수정할 수 있었습니다.

#### 작은 기능부터 프로덕션 구조로 확장했다

테스트용 더미 에너미를 출발점으로 감지·추격을 먼저 확인한 뒤, 소리 조사·어그로·랜덤 순찰·복귀·분산 접근과 전투 피드백을 단계적으로 쌓았습니다. 한 번에 모든 행동을 넣기보다 상태와 책임을 나누면서 문제 범위를 좁혔습니다.

#### 협업 범위를 구분해 기록했다

프로덕션 FSM의 설계·구현은 제 대표 범위로 정리하되, AI 모듈 분리와 2연격 조율은 강다영 TD와의 협업 영역, 이미지·리깅·애니메이션은 다른 팀원의 리소스 기여로 구분했습니다. 튜토리얼 역시 우성혁 CD·장수영 CP의 기획안과 제 런타임 구현을 분리했습니다.

### 3. 개선이 필요했던 점

#### PM과 실무를 병행하며 개인 작업 시간이 흔들렸다

일정 점검, 문서 취합과 이슈 조율 중에도 AI와 튜토리얼 구현을 진행해 작업 전환 비용이 컸습니다. 일부 날에는 관리 업무와 개발 업무가 서로의 집중 시간을 침범했습니다.

<b>개선 방향:</b> 다음 프로젝트에서는 PM 고정 시간과 개인 구현 블록을 캘린더에 분리하고, 긴급하지 않은 진행 보고는 정해진 시간에 일괄 처리하겠습니다.

#### 초기에 예상 작업량과 완료 조건이 충분히 세분화되지 않았다

“에너미 AI 구현”처럼 큰 단위로 계획하면 감지, 기억, 조사, 전투, 복귀와 안정화 비용이 일정에 충분히 드러나지 않았습니다.

<b>개선 방향:</b> 기능을 상태·전환 조건·데이터·연출·QA로 나누고, 각 항목의 DoD와 예상 시간을 담당자가 직접 제시하도록 하겠습니다.

#### 문서의 최신 기준을 찾기 어려운 시기가 있었다

콘셉트 초안, P0/P0.5 명세, 개발일지와 발표 자료가 빠르게 늘면서 초안과 채택본의 경계가 흐려질 수 있었습니다.

<b>개선 방향:</b> 문서마다 <code>상태</code>, <code>소유자</code>, <code>최종 수정일</code>, <code>상위 기준 문서</code>를 표시하고, 초안은 정식 채택 여부를 명시하겠습니다.

#### 정량 검증과 발표 증거 수집이 후반에 집중됐다

AI 행동의 Before/After, 플레이 테스트 횟수, 상태별 정상 전환과 같은 증거를 초기부터 같은 형식으로 축적하지 못했습니다. 최종 발표 준비 단계에서 영상 구간을 다시 찾고 GIF를 제작하는 비용이 발생했습니다.

<b>개선 방향:</b> 주간 빌드마다 대표 행동 영상과 실패 사례를 함께 저장하고, QA 항목과 통과 여부를 수치로 기록하겠습니다.

## 프로젝트 기여

### 1. 프로젝트 관리 — PM

전체 일정 구조

![전체 일정 구조](/assets/img/uploads/notion/ec116d24ab1785dad5e02bd789a8c8087e5861020a29190bce8fd05aa80346d3.png)

주별 마일스톤

![주별 마일스톤](/assets/img/uploads/notion/da51e16574b04de2696440bc0e327147586c84018e1f77b65ec5fbcd8a871a8b.png)

- 전체 일정, 주별 마일스톤과 일별 실적 관리
- P0/P0.5 우선순위, 안정화 게이트와 이월 항목 관리
- 팀원별 일일 개발일지 취합과 PM 주간 개발일지 작성
- 협업 일정과 기능 간 선후 관계 조정
- 개발 결과와 발표 근거가 연결되도록 문서·에셋 정리

### 2. 기획 — 꿈식자 및 초기 콘셉트 초안

- <b>직접 기획·구현:</b> 꿈식자의 세계관 역할, 2\~3마리 무리형 위협, 감지·조사·추격·공격·복귀 규칙
- <b>검수 전 초안 작성:</b> 프로젝트 초기 핵심 플레이, 몬스터, 캐릭터 역할군, 기본·전용 무장, 방어구, 아이템·오브젝트 콘셉트
- <b>캐릭터 콘셉트·원화 가이드 초안:</b> 성격과 전투 역할·능력 연결, 시각 키워드 제안
- <b>기존 기획 후속 보완:</b> 김남해 PD의 메인 시나리오·프롤로그·인트로 구성 이후 필요한 부분을 이어받아 초안 보완

꿈식자를 제외한 초기 콘셉트 문서는 <b>정식 채택본이 아니라 초안 작성 범위</b>로 구분합니다. 캐릭터 수집·해금·감상 흐름과 게임 UI·이미지 리소스 개선 방향은 제 담당 범위에 포함하지 않습니다.

### 3. 개발 — 꿈식자 AI 설계·구현

콘셉트에서 플레이 경험까지

![컨셉에서 플레이 경험까지](/assets/img/uploads/notion/5c8f3daccc6b1a44b2d4f756738435c48be2284b2a75ffbbffb77319e856e9fa.png)

```txt
스폰·초기화
→ 통제된 랜덤 순찰
→ 시야·근접·소리 감지
→ 소음 앵커 조사
→ 이동 방향 기반 추격
→ 전조 후 2단 돌진 공격
→ 마지막 인지 위치 재탐색
→ 개별 패트롤 루트 복귀
```

- 스폰 지점별 패트롤 루트와 시작 인덱스 연결
- 패트롤 포인트 반경 안에서 도달 가능한 NavMesh 후보를 선택하는 랜덤 순찰
- 시야각·거리·Raycast 차폐, 근접 인지와 소리 인식 분리
- 플레이어 좌표가 아닌 소음 앵커 위치를 조사하는 간접 인지

### 1. FSM 상태 정의

<code>EnemyStatus</code>는 현재 행동을 명시적으로 보관하고 실제 상태 전환 순간에만 인지·조사·공격 VFX를 발생시킵니다.

```cs
public enum EnemyState
{
    Idle,
    Patrol,
    Investigate,
    Return,
    Chase,
    Attack,
    Dead
}

public void SetNowState(EnemyState state)
{
    if (nowState == state)
        return;

    EnemyState previousState = nowState;
    nowState = state;

    switch (state)
    {
        case EnemyState.Chase:
            if (previousState != EnemyState.Attack)
                VFXService.Instance?.Play(GameplayVFXIds.EnemyDetected, transform.position, transform.rotation);
            break;
        case EnemyState.Investigate:
            VFXService.Instance?.Play(GameplayVFXIds.EnemyInvestigate, transform.position, transform.rotation);
            break;
        case EnemyState.Attack:
            VFXService.Instance?.Play(GameplayVFXIds.EnemyAttackTelegraph, transform.position, transform.rotation);
            break;
    }
}
```

if (hasTargetAwareness && isInsideChaseArea)
{
    memory.UpdateTargetTracking(currentTarget);
    sightLostStartTime = -1f;

        maxAggro,
        currentAggro + aggroRecoveryPerSecond * tickDelta);
}
else if (now - sightLostStartTime >= sightLossGraceTime)
{
    currentAggro = Mathf.Max(
        0f,
        currentAggro - aggroDecayPerSecond * tickDelta);
}

if (currentAggro <= 0f)
{
    if (!isSearchingLastKnownTarget)
    {
        isSearchingLastKnownTarget = true;
        lostTargetSearchEndTime = now + lostTargetSearchDuration;

    if (now < lostTargetSearchEndTime)

        locomotion.FacePosition(self, memory.LastKnownTargetPosition, onLookDirEvent);
        status.SetNowState(EnemyStatus.EnemyState.Investigate);
        return;
    }

## 트러블슈팅 모음

### 1. 소음 조사 좌표에서 멈추는 문제

1. <b>문제 상황</b>
   - 꿈식자가 소음 위치로 접근하다 이동을 멈추고 다음 상태로 넘어가지 못했습니다.
2. <b>원인</b>
   - 소음의 월드 좌표가 실제로 도달 가능한 NavMesh 위치와 어긋날 수 있었고, 이동 실패를 종료하는 제한 시간도 부족했습니다.
3. <b>해결</b>
   - 조사 좌표를 NavMesh 위 유효 위치로 보정했습니다.
   - 최대 조사 이동 시간을 추가해 도달하지 못해도 조사 상태를 종료하고 복귀 흐름으로 이어지게 했습니다.
4. <b>검증</b>
   - 이동 가능한 조사 지점에서는 도착 후 주변 확인을 수행하고, 실패 시에도 FSM 전체가 멈추지 않는 것을 Before/After GIF로 확인했습니다.

> 원문의 하위 기록은 별도 글로 이전했습니다.

### 2. 여러 개체가 같은 위치에 겹치는 문제

1. <b>문제 상황</b>
   - 여러 꿈식자가 같은 플레이어 좌표를 목표로 사용해 한 지점에 겹치고, 무리형 포식자가 아니라 한 덩어리처럼 보였습니다.
2. <b>원인</b>
   - 모든 개체가 같은 목표 좌표와 접근 경로를 사용했습니다.
3. <b>해결</b>
   - 런타임 개체 ID를 기준으로 플레이어 주변 접근 슬롯을 나누고, 도달 가능한 NavMesh 위치만 사용했습니다.
   - 공격 후에도 자기 접근 슬롯으로 재정렬하게 해 돌진 종료 지점에서 겹치지 않도록 했습니다.
4. <b>검증</b>
   - 여러 개체가 다른 방향에서 접근하고 길목을 압박하는 모습을 씬 뷰와 게임 뷰에서 비교했습니다.

> 원문의 하위 기록은 별도 글로 이전했습니다.

### 3. 돌진 공격이 벽·NavMesh 경계를 넘는 문제

1. <b>문제 상황</b>
   - 빠른 돌진 과정에서 공격 목적지가 벽 너머나 이동 불가능한 지점에 잡히면 꿈식자가 장애물을 관통하거나 경계 밖으로 밀릴 수 있었습니다.
2. <b>원인</b>
   - 공격 방향과 거리만으로 최종 좌표를 결정하면 실제 충돌 지점과 NavMesh 경계를 충분히 반영하지 못했습니다.
3. <b>해결</b>
   - SphereCast로 벽 충돌 지점을 먼저 확인하고 최종 목적지를 NavMesh 위로 보정했습니다.
   - 돌진 종료 후 짧은 재정렬 유예를 적용해 즉시 복귀 판정과 전투 흐름이 충돌하지 않게 했습니다.
4. <b>검증</b>
   - 좁은 길과 벽 근처에서 연속 돌진을 반복해 벽 너머로 이동하지 않는지 확인했습니다.

### 4. 튜토리얼 팝업 입력이 게임 플레이로 전달되는 문제

1. <b>문제 상황</b>
   - 튜토리얼 안내를 닫는 입력이 사격이나 이동에도 동시에 전달될 수 있었습니다.
2. <b>원인</b>
   - UI 확인과 게임 플레이 입력이 같은 프레임에 함께 처리됐습니다.
3. <b>해결</b>
   - 튜토리얼 전용 입력 차단 소스를 추가하고, 안내 단계가 끝날 때만 안전하게 해제했습니다.
4. <b>검증</b>
   - 팝업 확인 중 사격·이동이 실행되지 않고, 단계 종료 후에는 정상적으로 입력이 복구되는지 확인했습니다.

## 배운 점 / 성장한 점

### 1. 새로 학습한 기술

- FSM을 단순한 <code>switch</code> 문이 아니라 상태, 기억, 감지, 이동, 전투 책임이 협력하는 구조로 설계하는 방법
- NavMesh 후보 보정과 완전 경로 검증을 이용한 통제된 랜덤 순찰
- 시야·근접·소리 감지를 분리하고 소음 앵커로 간접 인지를 만드는 방법
- 마지막 위치 기억, 어그로 회복·감소와 활동 반경을 이용한 추격 종료 설계
- 개체별 접근 슬롯을 이용한 군집 분산
- JSON 단계 데이터와 입력 차단을 이용한 튜토리얼 런타임 구현
- 개발 기록을 이미지·GIF·영상과 연결해 포트폴리오 근거로 전환하는 방법

### 2. 개인적인 성장

가장 크게 성장한 부분은 <b>기획 의도를 구현 가능한 규칙으로 번역하는 능력</b>입니다. “꿈을 먹는 포식자”라는 표현만으로는 플레이 경험이 만들어지지 않았습니다. 무엇을 보고 듣는지, 어느 위치를 조사하는지, 언제 추격을 포기하는지, 무리가 어떻게 흩어지고 다시 복귀하는지를 상태와 수치로 나눠야 했습니다.

또한 깊이 파고드는 성향을 기능 확장에만 쓰지 않고, 문제의 원인을 확인하고 구조를 정리하는 데 사용하는 법을 배웠습니다. 동작을 더 많이 넣는 것보다 플레이어가 행동의 이유를 납득할 수 있고, 실패해도 FSM이 멈추지 않으며, 팀이 수정 가능한 구조를 만드는 것이 중요했습니다.

PM 역할에서도 일정표를 작성하는 것 자체보다, 팀원이 지금 무엇을 하고 있고 그 결과가 다음 작업에 어떤 영향을 주는지를 공유하는 일이 핵심임을 체감했습니다.

### 3. 팀 / 협업 측면 인사이트

- PM 역할과 기획·개발 역할은 병행할 수 있지만, 책임과 성과는 분리해서 설명해야 합니다.
- 아이디어의 소유권, 구현의 소유권과 리소스 기여는 서로 다를 수 있으므로 문서에 명시해야 합니다.
- 큰 기능명보다 상태 전환 조건과 완료 기준을 공유할 때 협업 오해가 줄어듭니다.
- 구두 보고보다 개발일지, 코드, GIF와 Before/After가 더 정확한 공통 언어가 됩니다.
- 최종 발표 자료는 마지막에 새로 만드는 것이 아니라 개발 과정에서 축적한 증거를 편집해 만드는 것이 효율적입니다.
