# 2026-07-03\_level\_box\_random\_spawn\_enemy\_refactor\_and\_combo

## 1. 문서 개요

이 문서는 2026년 7월 3일 기준으로 진행한 <code>레벨 아이템 상자 랜덤 스폰 시스템</code>, <code>에너미 AI 스크립트 구조화</code>, <code>2연격 공격 구현</code> 작업 내용을 정리한 기록 문서이다.

이번 작업의 목적은 다음 세 가지를 동시에 달성하는 것이었다.

첫째, 레벨 내 아이템 상자가 무작위로 생성되되 특정 구역별로 생성 밀도를 조절할 수 있는 구조를 만드는 것이다. 단순히 아무 위치에 상자를 뿌리는 방식이 아니라, 구역별 스폰 포인트와 보장 생성 수, 추가 랜덤 생성 수를 분리해 디자이너가 인스펙터에서 조절 가능한 구조를 만드는 데 초점을 두었다.

둘째, 기존에 하나의 <code>EnemyMovement</code> 스크립트 안에 몰려 있던 적 AI 책임을 역할별 모듈로 분리해, 이후 기능 확장과 디버깅이 쉬운 구조로 재정리하는 것이다. 특히 이후에 추가될 순찰, 먹잇감 차단 이동, 루시드 낙인 같은 기능이 들어왔을 때 현재 구조를 무너뜨리지 않고 확장 가능하도록 기반을 다지는 것이 중요했다.

셋째, 기존 단일 공격 흐름을 2연격 기반으로 확장하고, 각 스윙 타이밍마다 별도의 돌진과 판정을 넣을 수 있도록 애니메이션 이벤트 기반 전투 구조로 전환하는 것이다. 단순히 공격을 두 번 재생하는 수준이 아니라, 공격 애니메이션 1회 재생 안에서 1타와 2타를 각각 독립된 이벤트로 받아 처리하도록 설계했다.

## 2. 상세 작업 내용

### 2.1 레벨 아이템 상자 랜덤 스폰 구조 설계 및 반영

이번 작업에서 레벨 아이템 상자 스폰은 <code>스폰 시작 책임</code>과 <code>구역별 배치 책임</code>을 분리하는 방향으로 정리했다.

게임 시작 시 실제 스폰을 시작하는 진입점은 기존 <code>SpawnManager</code>가 맡고, 각 존마다 “몇 개를 기본으로 깔고, 추가로 몇 개를 랜덤 분배할지”는 별도의 박스 스폰 전용 구조에서 관리하도록 구성했다.

핵심 아이디어는 레벨을 여러 존으로 나누고, 각 존 안에 실제로 상자를 생성할 수 있는 스폰 포인트들을 미리 배치해 두는 것이다. 그 위에 구역별 설정값으로 <code>guaranteedSpawnCount</code>, <code>maxSpawnCount</code>, <code>randomWeight</code>, <code>densityMultiplier</code> 같은 값을 두어, 특정 구역은 최소 생성 수를 보장하고 나머지는 가중치 기반으로 배분되도록 설계했다.

이 구조를 통해 다음과 같은 요구사항을 충족했다.

- 창고 구역처럼 “무조건 상자가 나오게” 하고 싶은 구역은 <code>guaranteedSpawnCount</code>로 보장 생성
- 존별 분위기 차이를 위해 생성량 편차를 두고 싶은 경우 <code>randomWeight</code>와 <code>densityMultiplier</code>로 추가 생성량 배분
- 전체 맵 상자 수는 레벨 단위 총량으로 잡고, 구역별 가중치에 따라 나눠서 배치
- 레벨 형태가 정사각형이든 직사각형이든, 구역 개념과 스폰 포인트 구조만 유지되면 동일한 방식으로 운용 가능

특히 이번 구조는 “게임 시작 시 한 번만 생성”하는 방식이기 때문에, 상자 수가 아주 많지 않은 한 오브젝트 풀링이 반드시 필요한 구조는 아니라고 판단했다. 대신 추후 구역 진입 시 동적 생성 방식으로 바뀌거나, 생성/삭제가 자주 반복되는 구조로 변경될 경우 오브젝트 풀 연동 여지를 남겨 두는 방향으로 정리했다.

### 2.2 에너미 AI 스크립트 구조화

기존 적 AI는 감지, 조사, 추적, 공격, 방향 제어, 코루틴 흐름이 <code>EnemyMovement</code> 안에 강하게 결합되어 있었다.

이번 작업에서는 프리팹 연결을 깨지 않기 위해 <code>EnemyMovement</code>는 그대로 유지하되, 실제 책임을 내부 모듈로 분리하는 구조로 리팩터링했다.

분리된 책임은 다음과 같다.

- <code>EnemyBrain</code>
  - 적의 상위 의사결정 담당
  - 현재 타겟 확보, 조사 상태 진입, 추적 전환, 공격 시작 여부 판단
- <code>EnemyPerception</code>
  - 시야 범위, 인지 유지 범위, 청각 범위 관리
  - 플레이어를 새로 발견하는 로직과 이미 인지한 타겟을 놓치지 않는 거리 판정 분리
- <code>EnemyNoiseListener</code>
  - 소음 자극 등록, 조사 목표 관리, 강제 조사 유지 시간 관리
  - 조사 중 더 높은 우선순위 소음이 들어올 때의 반응 처리
- <code>EnemyLocomotion</code>
  - NavMesh 이동, 정지, 방향 회전, 공격 중 짧은 돌진 처리
  - 일반 이동과 공격용 lunge 이동을 같은 축에서 관리
- <code>EnemyCombat</code>
  - 공격 시작 거리, 실제 타격 거리, 쿨다운, 스윙별 데미지, 스윙별 돌진 값 관리
  - 2연격 전투 흐름과 각 스윙 이벤트 처리 담당
- <code>EnemyMathUtility</code>
  - 평면 거리, 평면 방향 계산 같은 공용 유틸리티 제공

이 과정에서 <code>EnemyMovement</code>는 더 이상 모든 로직을 직접 수행하는 스크립트가 아니라, 프리팹 호스트이자 모듈 연결 지점으로 역할이 축소되었다. 즉, 실제 AI 기능은 모듈에서 수행하고 <code>EnemyMovement</code>는 다음 책임만 가진다.

- 모듈 초기화
- 필수 컴포넌트 확인
- 브레인 루프 시작
- 글로벌 노이즈 이벤트 구독
- 애니메이션 이벤트와 전투 모듈 연결
- 사망 시 루프 정지 및 사망 이벤트 전달

이 구조를 통해 이후 기능 확장 방향도 명확해졌다.

예를 들어 순찰은 <code>EnemyBrain</code>의 상태 분기와 <code>EnemyLocomotion</code>의 이동 경로 제어를 확장하면 되고, 먹잇감 차단 이동은 별도의 전술 모듈을 추가하거나 <code>EnemyCombat</code> 전단의 추적 상태를 보강하는 방향으로 넣을 수 있다. 루시드 낙인도 감지나 전투 정보에 개입하는 별도 모듈로 분리할 수 있게 되었다.

### 2.3 2연격 공격 구현

이번 작업에서 적 공격은 기존 단발 공격 구조에서 <code>1회 공격 애니메이션 + 2개의 스윙 이벤트</code> 구조로 변경되었다.

처음에는 코드에서 공격을 두 번 재생하는 방식으로 접근했지만, 실제로는 플레이어가 기대하는 “오른팔 한 번, 왼팔 한 번”의 스윙 타이밍과 맞지 않아 체감이 어색해질 수 있었다.

이 문제를 해결하기 위해 공격 흐름을 다음처럼 재설계했다.

- 공격 시작 시 <code>EnemyCombat.RunCombo()</code>가 한 번만 공격 상태를 시작함
- <code>EnemyAnimator.PlayAttack()</code>를 통해 공격 애니메이션은 한 번만 재생됨
- 공격 애니메이션 클립 <code>Monster-Monster_Attack.anim</code> 안에 이벤트 2개를 배치
  - <code>GetAttack1</code>
  - <code>GetAttack2</code>
- 각 이벤트가 들어오면 <code>EnemyAnimator</code>가 <code>OnAttackSwing</code> 이벤트를 발생
- <code>EnemyPresenter</code>가 이를 받아 <code>EnemyMovement.HandleAttackSwing(int swingIndex)</code>로 전달
- <code>EnemyMovement</code>는 <code>EnemyCombat.ExecuteSwing(...)</code>를 호출해
  - 1타 또는 2타에 맞는 돌진 거리
  - 1타 또는 2타에 맞는 돌진 시간
  - 1타 또는 2타에 맞는 데미지를 적용하도록 구성했다

이 구조를 통해 공격 애니메이션은 하나지만, 실제 전투 행위는 두 개의 분리된 타격 단계로 처리할 수 있게 되었다.

즉, “공격을 두 번 재생하는 구조”가 아니라 “애니메이션 안의 두 번 휘두름에 각각 의미를 부여하는 구조”가 만들어진 것이다.

현재 스윙 타이밍은 공격 클립 기준으로 다음처럼 설정되었다.

- <code>GetAttack1</code> : 첫 번째 스윙 시점
- <code>GetAttack2</code> : 두 번째 스윙 시점

각 이벤트는 해당 타이밍에 짧은 돌진과 근접 판정을 함께 실행한다.

이를 통해 2연격이 시각적으로도, 실제 판정 구조로도 분리된 상태가 되었다.

### 2.4 공격 거리, 돌진 거리, 애니메이션 이벤트 튜닝 포인트 정리

이번 작업에서 적 전투 체감은 여러 값이 동시에 영향을 주는 구조로 정리되었다.

즉, 공격이 언제 시작되는지, 얼마나 멀리 달려드는지, 실제로 언제 데미지가 들어가는지는 서로 다른 인스펙터 값과 애니메이션 이벤트 위치가 함께 결정한다.

현재 주요 튜닝 포인트는 다음과 같다.

- <code>attackStartRange</code>
  - 플레이어가 이 범위 안에 들어오면 공격 시작 가능
- <code>attackHitRange</code>
  - 실제로 데미지가 적용되는 거리
- <code>firstSlashLungeDistance</code>
  - 1타 돌진 거리
- <code>secondSlashLungeDistance</code>
  - 2타 돌진 거리
- <code>firstSlashLungeDuration</code>
  - 1타 돌진 시간
- <code>secondSlashLungeDuration</code>
  - 2타 돌진 시간
- <code>secondSlashTurnLimit</code>
  - 2타 직전 플레이어 방향으로 얼마나 더 꺾을 수 있는지
- <code>Monster-Monster_Attack.anim</code> 이벤트 위치
  - 각 스윙 타이밍의 실제 돌진/판정 시작 시점

이 값들의 관계를 정리하면 다음과 같다.

- 공격 시작이 너무 늦다
  - <code>attackStartRange</code> 증가
- 너무 먼 거리에서 허공에 공격한다
  - <code>attackStartRange</code> 감소
- 돌진이 짧다
  - <code>firstSlashLungeDistance</code>, <code>secondSlashLungeDistance</code> 증가
- 돌진이 너무 순간이동처럼 보인다
  - <code>Duration</code>도 함께 증가
- 두 스윙이 너무 붙어 보인다
  - 공격 클립 안의 <code>GetAttack2</code> 이벤트를 뒤로 이동
- 두 번째 공격이 목표를 잘 못 따라간다
  - <code>secondSlashTurnLimit</code> 증가

즉, 이번 구조는 단순히 “적이 두 번 때린다” 수준이 아니라, 디자이너가 인스펙터와 애니메이션 이벤트만으로 전투 템포를 비교적 세밀하게 조정할 수 있는 상태를 목표로 정리되었다.

## 3. 구조 정리 및 반영 방향

이번 작업의 핵심은 두 가지였다.

첫째, 레벨 배치 요소인 상자 스폰도 단순 랜덤이 아니라 <code>시작 책임</code>과 <code>구역별 배치 책임</code>을 나누는 구조로 정리했다는 점이다.

이는 앞으로 레벨 디자인이 더 복잡해지더라도, 특정 구역 보장 생성과 전체 분포 조절을 한꺼번에 유지할 수 있게 만든 기반이다.

둘째, 적 AI 역시 단일 스크립트 중심 구조에서 역할별 모듈 구조로 분리했다는 점이다.

이로 인해 이후 AI 확장 방향이 “기존 스크립트에 계속 if를 추가하는 방식”이 아니라, 기능별 모듈을 보강하는 방식으로 전환되었다.

특히 이번 2연격 구현은 단순 기능 추가를 넘어, 애니메이션과 전투 로직의 연결 구조를 재정리한 작업이었다.

기존에는 공격 애니메이션과 실제 판정이 거의 1대1로 단순 연결되어 있었지만, 이번에는 하나의 공격 클립 안에 여러 스윙 단계를 정의하고, 그 단계별로 서로 다른 움직임과 판정을 적용할 수 있는 구조를 갖추게 되었다.

이 구조는 이후 다음과 같은 확장에 유리하다.

- 3연격, 차징 후 베기 같은 다단 히트 확장
- 각 스윙마다 다른 데미지/경직/넉백 적용
- 특정 스윙만 방향 보정 허용
- 특정 스윙에만 루시드 낙인, 차단 이동, 디버프 부여
- 보스 전용 패턴에서도 같은 이벤트 기반 전투 구조 재사용

## 4. 검증 결과

현재 코드 기준으로 다음 항목이 반영된 상태를 확인했다.

- 레벨 상자 랜덤 스폰 구조 설계 반영
- 구역별 상자 스폰 수 조절용 인스펙터 값 도입
- <code>EnemyMovement</code> 기반 적 AI 구조의 모듈형 리팩터링
- <code>EnemyBrain</code>, <code>EnemyPerception</code>, <code>EnemyNoiseListener</code>, <code>EnemyLocomotion</code>, <code>EnemyCombat</code>, <code>EnemyMathUtility</code> 추가
- <code>EnemyAnimator</code>, <code>EnemyPresenter</code>, <code>EnemyMovement</code>, <code>EnemyCombat</code> 간 이벤트 기반 연결 정리
- 공격 클립 이벤트 <code>GetAttack1</code>, <code>GetAttack2</code> 기반 2연격 스윙 처리 연결
- 신규 스크립트 메타 파일 및 주석 정리 반영

추가로 C# 컴파일 기준 검증에서 임시 프로젝트 빌드를 수행했을 때 <code>경고 0</code>, <code>오류 0</code>으로 통과한 상태를 확인했다.

다만 Unity 플레이 체감 기준으로는 여전히 튜닝이 필요한 영역이 남아 있다.

예를 들어 2타 돌진 거리, 2타 이벤트 시점, 공격 시작 거리, 실제 타격 거리, 죽음 연출 시각화는 실제 플레이를 통해 계속 조절해야 하는 부분이다.

## 5. 결과 및 정리

이번 작업을 통해 레벨 요소와 적 AI 양쪽 모두에서 “기능 구현”보다 “구조 정리”에 더 큰 진전이 있었다.

상자 랜덤 스폰은 구역 기반 레벨 디자인에 대응 가능한 방식으로 정리되었고, 적 AI는 감지, 조사, 이동, 전투 책임이 분리되면서 이후 확장 가능성이 커졌다.

또한 2연격은 단순히 공격 횟수를 늘린 것이 아니라, 애니메이션 이벤트와 실제 전투 로직을 단계별로 연결하는 구조를 만든 것이 핵심 성과였다.

즉, 이번 작업은 상자 스폰 튜닝 기반을 마련하고, 적 AI를 확장 가능한 모듈 구조로 바꾸고, 다단 히트 전투 구조를 도입한 작업으로 정리할 수 있다.

## 6. 후속 작업 계획

다음 단계에서는 먼저 실제 Unity 플레이 테스트를 통해 전투 체감과 배치 체감을 조정할 필요가 있다.

상자 스폰 쪽에서는 다음 항목이 후속 점검 대상이다.

- 존별 스폰 포인트 밀도와 실제 생성 수 체감 확인
- 보장 생성 수와 추가 랜덤 생성 수의 밸런스 조정
- 전체 맵 상자 수가 탐색 템포와 잘 맞는지 검증

적 전투 쪽에서는 다음 항목이 후속 조정 대상이다.

- 1타와 2타 돌진 거리/속도 튜닝
- 공격 시작 거리와 실제 타격 거리의 괴리 조정
- 두 스윙 이벤트 위치 미세 조정
- 사망 시 이동 차단, 콜라이더 비활성화, 죽음 연출 개선
- 이후 순찰, 먹잇감 차단 이동, 루시드 낙인 기능 추가를 위한 상태 분기 확장

장기적으로는 현재 정리된 모듈 구조를 바탕으로 적 AI를 더 명확한 전술 단위로 분리하고, 보스 패턴이나 특수 개체에도 동일한 전투 이벤트 구조를 재사용하는 방향으로 확장하는 것이 적절하다.
